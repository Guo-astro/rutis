# 跨运行时同步调用与死锁策略（TLA+）

[English](README.en.md)

用 TLC 穷举"多个语言运行时经 Rust 宿主互相同步调用"的交错，回答多语言设计 §九 留下的问题：两个候选策略哪个能消除卡死。对应 issue #208，质量规范 Q11.2、Q6.2.8、Q6.8.3，现状 §7.1（风险 P10、C6）。

## 模型

- **参与者**：Rust 宿主（中继）和 3 个运行时，每个运行时标为可重入或不可重入。每个运行时和 Rust 之间一个会话，每个方向按顺序送达（socket 的顺序）。
- **运行时**：单线程，一个调用栈。只有栈顶在跑。栈顶发起同步调用后，线程一边等一边读进来的帧（pump）：
  - 回复：标记对应的调用已返回；它在栈顶时才能继续；
  - 调用：空闲时直接执行；在等待中时，可重入的运行时全部嵌套执行，不可重入的只执行 `path` 里有自己等待号的，其余放到一边，栈空后再执行。
  - 正在跑（不在等待）的栈顶不读帧。
- **Rust**：按会话顺序读帧。收到同步调用后转发到目标运行时的会话，`path` 先加上调用号再按 `rebase` 改写；收到返回后把结果送回调用方。Rust 不会让任何运行时多等：每个转发都在自己的线程或已在等待这条链的线程上执行。
- **调用号**：每个会话各自编号（`node:n` 由运行时分配，`rust:n` 由 Rust 分配），所以两个会话里会出现相同的 `node:1`。模型另外给每个调用记一份真实的祖先链（只用来写不变式），和线协议里的 `path` 分开，这样能检查运行时和 Rust 的判断是否正确。
- **策略**（常量 `Policy`）：
  - `current`：现状，不做任何检测；
  - `A`：Rust 拒绝两个不可重入运行时之间的同步调用（回 `refused`）；
  - `B`：Rust 在每次转发同步调用前，用自己看得到的信息建等待图，这次转发会让等待成环时不转发，直接回 `SyncWaitCycle`；
  - `Bchain`：B 去掉"栈顺序"那类边，用来说明这类边是必须的。

### 等待图

节点是 Rust 已转发、还没返回的调用；边 c → d 表示 c 要等 d 完成。成环即卡死。

| 边 | 含义 | Rust 能否看到 |
| --- | --- | --- |
| 链 | d 是在 c 之下发起的（d 的 `path` 含 c 的号） | 能：`path` 改写后带会话标签，Rust 能解开 |
| 放到一边 | c 进入一个不可重入、正在等待、且 c 不在其链上的运行时 y，c 要等 y 发出的所有调用 | 能：y 发出的未完成调用都在 Rust 手里；y 是否可重入由能力 `reentrant-sync` 得知 |
| 栈顺序 | c 和 d 先后进入同一个运行时 y，d 已经在 y 上开始执行（y 发出的某个调用的 `path` 含 d），c 要等 d：栈是后进先出 | 能：同一会话的帧有序。如果 c 先返回，c 的返回一定先于 d 之下发出的任何帧到达 Rust |

模型里有两份图：`TrueSucc` 用运行时的真实栈和队列（只用于判断），`RustSucc` 只用 Rust 自己的状态（策略 B 实际能做的）。

`TrueSucc` 是 `NoFalseCycle` 的判据，所以它只能包含真实存在的等待。第一版漏了两类真实的边：被延后的调用还要等之后才开始、正在栈上执行的进来调用；栈上某个调用还要等压在它上面、尚未发出调用的进来调用。审阅后已补上（`OnStack` 和最后一类边），全部配置重跑结果不变。补上之后仍可能有遗漏的边，只会让 `NoFalseCycle` 更严格（把真实的环判成不成环，从而报告误报），不会掩盖误报。

## 简化

- 所有跨运行时调用都是同步的。异步调用不阻塞调用方，不会单独造成卡死；但策略 B 实现时必须能区分同步和异步，见"待定"。
- 同一运行时内部的调用不经过 Rust，不建模。
- 只建模服务调用和函数（回调）调用；两者在 Rust 侧都是"从一个会话转发到另一个会话"，模型不区分。`await`、引用计数、取消、会话关闭不建模。
- Rust 的线程不是受限资源：每个转发要么在等待这条链的线程上，要么在新线程上执行。实现里 `RowService` 的同步转发占用会话执行器的一个工作线程；执行器是 `current_thread` 或线程数很少时，Rust 自身也可能成为瓶颈，这里没有覆盖。
- Rust 自己发起的同步调用（Rust 插件同步调用某个运行时，而不是转发）不建模。
- 每个活动（一次执行中的调用）默认只发起一个同步调用；`policy-b-2node-seq` 允许先后两个。
- 运行时可以在任何时刻开始一个顶层活动（定时器、事件），总数受 `MaxRoots` 限制。
- 规模：3 个运行时，调用链 ≤ 3 跳，同时存在的顶层调用 ≤ 2；B 另外在 3 个顶层、链 ≤ 4 跳、每个活动两次调用的配置上跑过。

## 不变式

| 名字 | 内容 |
| --- | --- |
| 不死锁 | TLC 的死锁检查：还有未完成的调用时，总有参与者能继续。全部完成后的状态用 `Done` 原地停留，不算死锁。模型里的每个行为都是有限的（顶层调用数、调用号、链长、每个活动的调用数都有上限，除 `Done` 外每一步都让这些计数或队列向完成推进），所以"没有死锁"等价于"每个调用最终都会完成"，不需要另写活性性质 |
| `RoutingSound` | 一个调用被当作某条等待链上的调用执行（不可重入运行时嵌套执行它，或 Rust 把它交给某个等待中的线程）时，它确实属于那条链。也就是反向调用回到发起它的那一方，不会因为两边都有 `node:1` 而走错 |
| `ChainRecognised` | 不可重入运行时不会把自己链上的调用放到一边 |
| `NoFalseCycle` | 策略 B 回 `SyncWaitCycle` 时，加上这次转发后真实等待图确实成环 |
| `NoLegitimateRefused` | 策略 A 不拒绝合法调用。**合法**定义为：转发它不会让真实等待图成环 |
| `NeverCycle` | 只用于确认 B 的检测确实会触发（预期被违反） |

## 结果

| --- | --- | --- | --- | --- |
| `current-1node-1python` | n, p | 通过 | 606 | <1 s |
| `current-2node` | n1, n2, p | **死锁**（反例 1） | 1,006 | <1 s |
| `current-1node` | n, p1, p2 | **死锁**（反例 2） | 8,908 | 1 s |
| `current-reentrant` | p1, p2, p3 | 通过 | 88,824 | <1 s |

| `policy-a-2node` | n1, n2, p | **死锁**（同反例 2 的形状） | 3,066 | <1 s |

### 反例

1. **两个 Node 运行时交叉同步调用**（`current-2node`）。n1 同步调用 n2 的服务，同时 n2 同步调用 n1 的服务。两个调用都不在对方的链上，各自被放到一边，互相等待。这是 §九 已知的情况。
2. **可重入运行时上的栈顺序**（`current-1node`，A、Bchain 同理）。
   1. n 同步调用 p2 的服务 `s1`；
   2. `s1` 同步调用 p1（任何需要一点时间的调用）；
   3. p1 自己（比如定时器）同步调用 p2 的服务 `s2`。p2 正在等，可重入，于是把 `s2` 嵌套在 `s1` 上面执行；
   4. `s2` 同步调用 n 的服务。n 正在等 `s1`，这个调用不在它的链上，放到一边；
   5. `s1` 等的调用已经返回，但 `s2` 在栈顶，`s1` 要等 `s2` 返回；`s2` 等 n；n 等 `s1`。卡死。

   这说明"叶子运行时都可重入"本身不能消除卡死：可重入把"放到一边"换成了"压在下面"，只要还有一个不可重入的运行时，就能成环。只有一个 Cordis 运行时也会发生。
3. **不改写 `path`**（`current-norebase`）。n1 和 n2 都在等各自的 `node:1`；n1 的调用转到 n2 时 `path` 是 `["node:1"]`，n2 把它当成自己的 `node:1` 链上的调用，嵌套执行了。现在的 `rebase` 防止的正是这个；`current-2node` 等配置在改写开着时 `RoutingSound` 成立。
4. **A 拒绝不会卡死的调用**（`policy-a-refusals`）。n1 同步调用 n2，n2 空闲，没有任何别的调用，A 仍然拒绝。

## 推荐：策略 B（含栈顺序）

维护者已采用（写入[多语言设计](../../docs/design-multilang-runtimes-2026-10-03.md) §九，实现见 #228）。

理由：

- **A 不够**：A 本来设想的组合（一个 Cordis 运行时，其余都可重入）仍然会卡死（反例 2）；同时它会拒绝不会卡死的调用（反例 4），并要求以后每种新语言都可重入，把"调用别的服务时不要持有锁"的负担推给所有插件作者。
- **B 在模型范围内消除了卡死，而且不误报**：所有 B 配置（含可重入、不可重入、全不可重入的组合，以及更大的规模）都没有死锁，`NoFalseCycle` 成立。被拒绝的只有真正会卡死的那一次调用，它的调用方得到 `SyncWaitCycle` 后返回，其他调用继续。
- **B 只用 Rust 已有的信息**：转发记录、`path`（改写后带会话标签）、每个会话里帧的顺序、运行时是否可重入。不需要运行时报告自己的栈，不改线格式里已有的字段。
- **栈顺序那类边不能省**：只看链和"放到一边"（`Bchain`）会漏掉反例 2。
- 新语言的运行时可以自己选可重入或不可重入，只要如实声明。

B 实现时需要满足的条件（模型的前提）：

1. 宿主范围内一张等待表，记录所有已转发、未返回的同步调用（来源会话和调用号、目标会话和调用号、解开标签后的链）；
2. 返回在读帧的顺序里登记：同一会话里，先到的返回必须先于后到的调用从表里移除；
3. 每次转发同步调用前检查，成环则不转发，回 `SyncWaitCycle`，消息里写出环上的调用；
4. 每个运行时是否可重入要可靠：endpoint 格式用握手里的 `reentrant-sync`；compat 格式没有能力列表，由运行时插件的配置给出（Node 运行时为否）；
5. 只把**同步**等待算进图（见"待定"）。

## 待定

- **区分同步和异步调用（已定）**：现在的 `invoke`/`call` 帧不说明调用方是否在同步等待，把异步调用算成等待会误报。维护者决定在调用帧上加一个字段，标明调用方在同步等待；只有带这个字段的调用计入等待图（#228，兼容方式在那里定）。模型假设这个字段已经存在：模型里所有调用都是同步调用，都带这个字段，Rust 直接知道哪些调用是同步等待。异步调用没有建模。
- **Rust 自己发起的同步调用**和**有界的 Rust 执行器**（`current_thread`）都可能把 Rust 自己变成环上的一环，模型没有覆盖。
- **B 的开销**：每次同步转发都要在全局表上做一次可达性检查；表的大小等于正在进行的同步调用数，通常很小，但需要实测。
- 被拒绝的调用方收到 `SyncWaitCycle` 后如果马上重试，可能反复成环；是否需要退避由调用方决定，模型不覆盖。

## 怎么运行

需要 Java 11 以上和 `tla2tools.jar`（[v1.7.4](https://github.com/tlaplus/tlaplus/releases/tag/v1.7.4)，sha256 `936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88`）。jar 不要提交进仓库。

```sh
mise install java@temurin-21
curl -sSLo /tmp/tla2tools.jar https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar
TLA2TOOLS=/tmp/tla2tools.jar mise exec java@temurin-21 -- specs/cross-runtime-sync/run.sh            # 全部配置，约 1 分钟
TLA2TOOLS=/tmp/tla2tools.jar mise exec java@temurin-21 -- specs/cross-runtime-sync/run.sh policy-b-2node   # 单个配置
```

`run.sh` 把每个配置的结果和 `expected.txt` 比较，全部符合时退出码为 0；日志和反例写在 `TLC_OUT`（默认一个临时目录）。不用脚本，在本目录下直接跑一个配置：

```sh
java -cp /tmp/tla2tools.jar tlc2.TLC -workers auto -config current-1node.cfg CrossRuntimeSync.tla
```

## 维护

多语言设计 §五、§九 或 M1 §七 修改时，或 `rpc.rs`、`session.mjs`、`peer.py` 改变同步等待期间执行哪些调用的规则时，同步修改这个模型和 `expected.txt`（规范 Q11.2.3）。
