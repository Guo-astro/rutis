# 宿主的插件面：生成 Python 类型和契约检查，生成内容用宿主的名字

[English](design-host-contract-types-2026-10-27.en.md)

状态：定稿，未实现。日期：2026-10-27。基准：`main` `5abffe99`（0.18 #677 已合并）。排期：0.19。

- 错误 `data` 的形状（宿主用 serde 属性改）、运行时的错误名（`CordisError`，G11）、#670 的内容、`rutis-host dev`（跑的是真宿主）。

## 一、现象

宿主持有者做了 deskmate（[评估报告](https://github.com/arcships/rutis/issues/663#issuecomment-6411076725)）：Rust 宿主用 `#[rutis::service]` 提供 `notes`（`put(key, value: String)`、`get(key) -> Option<String>`）和 `tools`（`register(name, description, handler)`，`handler` 是 `Fn(String) -> BoxFuture<Result<String, ToolError>>`），交给第三方用 TypeScript 或 Python 写插件。卡在三处：

1. **Python 没有类型**，宿主手写了 Protocol。
2. **测试通过，装进宿主却失败**：给 `notes.put` 传数字、处理函数返回 `undefined`、`handler` 不是函数、插件自己也提供 `notes`。宿主手写了约 160 行严格假服务（TS、Python 各一份）。
3. **声明里露出 rutis**：文件头 `Generated by rutis-bridge (build::Exports) …`，错误接口叫 `RustError`。

## 二、真实宿主已经报什么，测试工具没报什么

本稿只做一件事：测试工具在真实宿主会失败的地方也失败。逐项对照现在的代码：

| 情况 | 真实宿主（现在） | 测试工具（现在） | 本稿 |
| --- | --- | --- | --- |
| 参数类型或个数不对 | `bad-argument`（serde 解码，`BadArgument`） | 假服务什么都接受 | 按契约描述检查 |
| 该是函数的参数不是函数 | `bad-argument` | 不报 | 同上（"函数"是描述里的一种类型） |
| 处理函数的结果类型不对 | 宿主调用它时 serde 解码失败 | 不报 | 同上 |
| 调用契约里没有的方法（例如假服务上给测试用的 `tools.run`） | `no-method` | 假服务上有就能调 | 只放行契约里的方法 |
| 插件 `ctx.provide` 宿主已经提供的名字 | 拒绝（与 Cordis 的 `service "notes" has been registered` 相同） | 不报 | **不需要契约**：测试工具对 `services` 里已有的名字拒绝 `provide`，默认就做 |

前四项需要知道宿主的 Rust 类型，测试工具里没有，所以要一份从 Rust 生成的描述。第五项是测试工具本身和真实宿主（以及 Cordis）不一致，直接修。

## 三、决策

| # | 决策 | 章节 |
| --- | --- | --- |
| H1 | 生成器从同一份推导结果多写两样：Python 类型模块、契约描述（一个 JSON）。`Exports` 加 `.python(file)`、`.contract(file)`；`rutis-host types` 加 `--python <file>`、`--contract <file>`。不给新选项时输出与现在逐字相同 | 四 |
| H2 | Python 类型：服务是 `Protocol`，结构体是 `TypedDict`，只有名字的枚举是 `Literal`；支持 Python 3.10；`.declared_python(path, py)` 对应现有的 `.declared` | 4.2 |
| H3 | 测试工具的 `load` / `host` 加 `contract` 选项；有它时检查 §二 前四项，错误码和 `data` 与真实宿主相同。没有它时行为不变 | 五 |
| H4 | 测试工具对 `services` 里已有的名字拒绝插件的 `provide`，与真实宿主和 Cordis 一致；不需要 `contract` | 五 |
| H5 | 契约描述是测试工具的内部格式，不是公开规范：只写类型，带格式版本号；描述不了的类型一律放行，检查永远不比真实宿主严 | 六 |
| H6 | 文件头、错误接口名由宿主设：`.header(text)` / `--header`、`.error_name(name)` / `--error-name`；不设时与现在相同（issue 评论已定），Python 用同样的默认 | 4.3 |

## 四、生成什么

### 4.1 怎样生成

```sh
rutis-host types . -o types/deskmate.d.ts --python types/deskmate.py \
  --contract types/deskmate.contract.json \
  --header "Generated by deskmate; do not edit." --error-name DeskmateError
```

`build.rs` 里同样是 `Exports::new().typescript(…).python(…).contract(…).header(…).error_name(…)`。`.generate()` 至少要有一种输出。

### 4.2 Python 类型

与现有 TypeScript 一一对应：`Option<T>` → `T | None`；`Vec<T>`、`HashMap<String, T>`、元组 → `list`、`dict[str, T]`、`tuple`；整数 / 浮点 → `int` / `float`；`serde_json::Value` → `Any`；可省略的字段放进 `total=False` 的父类（3.10 没有 `NotRequired`）；带数据的枚举是 `TypedDict` 的 `Union`；回调参数是 `Callable[[A], R | Awaitable[R]]`；`rutis::Definition` 是 `rutis.Plugin`；错误码是 `Literal[…]`，错误接口是 `rutis.RemoteError` 的别名。

插件作者写 `notes: Notes = ctx.use("notes")`，由编辑器或 pyright 检查，不写也照样运行（`ctx.use` 不带类型参数，所以不生成 `Services` 总表）。`.declared` 的类型没有 Python 版本时写 `Any` 并警告；评估里的宿主为透明包装类型用了 `.declared`，所以需要 `.declared_python`。示例 `examples/marked-services` 的测试检查生成的 `.py` 是最新的并通过 `pyright --strict`，与现有的 `.d.ts` + `tsc --strict` 一样。

### 4.3 宿主的名字

| 位置 | 默认（与现在相同） | 设了以后 |
| --- | --- | --- |
| TS / Python 文件头 | `Generated by rutis-bridge (build::Exports) from the Rust sources; do not edit.` | `<header>` |
| 错误接口 / 别名 | `RustError` | `<error_name>` |

`error_name` 不是合法标识符或与生成的其他名字、现有 `RESERVED` 表重名时生成失败，写明重名的是什么。方法返回 `rutis::Result` 时运行时的错误名是 `CordisError`（G11 不变），别名仍叫 `CordisErrorThrown`；宿主不想让它出现，就返回自己的错误类型——写进 Rust 宿主指南。

## 五、测试工具

```ts
import contract from '../types/deskmate.contract.json' with { type: 'json' }
const t = await load(plugin, { contract, services: { notes: fakeNotes(), tools } })
```

```python
contract = json.loads((ROOT / "types/deskmate.contract.json").read_text())
async with load(plugin, contract=contract, services={"notes": FakeNotes(), "tools": tools}) as t: ...
```

- 有 `contract` 时，契约里的每个服务交给插件之前包一层：插件调用的方法必须在契约里（否则 `no-method`）；参数先按 `strict` 复制，再按描述检查（否则 `bad-argument`，`data` 的 `service`、`method`、`argument` 与真实宿主相同）；函数参数被调用时，它的结果按描述检查，失败时调用它的一方（宿主的假服务）拿到 `bad-argument`。少给的参数按缺失检查（`Option` 可以省略），多给的报 `bad-argument`，与 `marked.rs` 相同。
- 文字用真实宿主 `BadArgument` 的同一种写法（`notes.put: argument 2 should be a string, got 42`）。嵌套很深的值，真实宿主的文字带 serde 的原话，测试工具只保证错误码和 `data` 相同。
- `provide` 的名字已在 `services` 里时拒绝：`PluginTestError: wordcount: notes is already provided by the host`（H4，默认就做）。
- 假服务仍是 `services` 里的普通对象；它由宿主模板给，还是插件作者用 #670 的写法自己写，都一样被检查。
- 插件作者要写的 rutis 特有的东西：多一个 `contract` 选项，宿主的模板里已写好。代价是测试多读一个 JSON 文件；描述是数据，不执行代码。

## 六、契约描述与一致性

- **内部格式**：由生成器从 TypeScript 用的同一份推导结果写出，只给同一个大版本的测试工具读，不写规范、不承诺稳定；带 `version`，测试工具不认识时报错并让作者升级 `@arcships/rutis` / `rutis`。
- **只描述能确定的类型**：字符串、布尔、`null`、浮点、整数（按 Rust 类型的范围）、`Option`、列表、元组、字符串键的映射、结构体（serde 改名后的字段名、可省略、`deny_unknown_fields`）、只有名字的枚举、函数（参数与结果）、插件定义。其余——带数据的枚举、`flatten`、`.declared` 的类型、手写 `Deserialize`、`deserialize_with`、`serde_json::Value`——都是"任意值"，放行。检查只会比真实宿主宽，不会冤枉一个能在宿主里跑的插件。
- **怎样验证一致**：用现有的 `examples/marked-services`（它已经在真实宿主上跑 TS 和 Python 行，并检查 `.d.ts` 是最新的）。给 `Calendar` 补上覆盖上一条每种类型的参数；同一组错误调用由行在真实宿主上发一次、在 Node 和 Python 测试工具里带它生成的契约描述发一次，比较错误码、`data` 与顶层的文字。生成的契约描述同 `.d.ts` 一样提交并检查是最新的。不另建夹具 crate 和用例表。

## 七、开发者看到什么

**宿主持有者**

```text
$ rutis-host types . --python types/deskmate.py
warning: notes::Text has no Python type: declare it with .declared_python (written as Any)

$ rutis-host types . --error-name Services
error: --error-name Services is a name the declarations already use
```

**插件作者**（`node --test` 与 `pytest` 文字相同；不给 `contract` 时除最后一行外输出不变）

| 测试里 | 测试失败的文字 |
| --- | --- |
| `notes.put('k', 42)` | `BindingError: notes.put: argument 2 should be a string, got 42` |
| `tools.register('wc', 'count', 'not a function')` | `BindingError: tools.register: argument 3 should be a function, got "not a function"` |
| 处理函数返回 `undefined`，测试调用 `tools.run('wc', 'a b')` | `BindingError: tools.register: argument 3 returned undefined, should be a string` |
| 插件调用 `tools.run(…)` | `BindingError: tools has no method run (methods: register)` |
| 插件 `ctx.provide('notes', …)` | `PluginTestError: wordcount: notes is already provided by the host` |

错误码在 `error.code` 里，文字里不出现 rutis、Rust、serde 的原文。Python 里 `await notes.put("k", 42)` 由 pyright 标出。

## 八、兼容

- 不给新选项时，`rutis-host types` 与 `Exports` 的输出逐字不变；测试工具不给 `contract` 时行为不变。
- 唯一的行为变化是 H4：测试给了 `notes`、插件又提供 `notes`，以前测试通过，现在失败——装进真实宿主本来就失败。写进更新说明，不进《迁移到 0.19》。
- 协议、内核、loader、各语言运行时不变。#692 若改了测试工具的入口名，`contract` 随新入口走。
