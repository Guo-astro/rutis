# 宿主的插件面：生成 Python 类型和契约检查，生成内容用宿主的名字

[English](design-host-contract-types-2026-10-27.en.md)

状态：草案，未实现。日期：2026-10-27。基准：`main` `103c0d22`（0.17.2 之后）。排期：0.19。
Issue：[#684](https://github.com/arcships/rutis/issues/684)（属于 [#663](https://github.com/arcships/rutis/issues/663) 的 O2、O5）。
与 0.18 的关系：建在 [0.18 的诊断](design-diagnostics-2026-10-26.md) 上——契约检查报的错误用它 §4.3 的错误码（`bad-argument`、`no-method`）和 §8.1 的文字，不出现它 §4.5 的禁用词；不改 0.18 定下的错误类型名（G11）。[0.18 的配置 Schema](design-config-schema-2026-10-27.md) 把"生成配置表单或类型"划给本 issue，本稿不做（理由见 §三 H8）。

范围外：
- 插件之间的服务契约、通用的类型层（[设计哲学](design-philosophy.md) §七 原则 6；#223 已拒绝），理由见 §四。
- Go、Swift、Kotlin 的类型和契约检查（宿主持有者评估只用到 TypeScript 和 Python；以后怎样加见 §五 5.4）。Bun 的插件用同一个 `@arcships/rutis` 测试工具，自动可用，不另做。
- 插件配置的类型或表单（没有使用方，见 H8）。
- 宿主的业务规则（例如"至少注册一个工具"）：不是类型，宿主写在自己的假服务里。
- 假服务的行为（`notes` 存在哪、`tools.run` 怎样调处理函数）：是宿主的业务，仍由宿主写，用现有的 `services` 选项交给测试工具。
- 错误 `data` 的形状（`{AlreadyRegistered: {…}}`）：它就是宿主的 Rust 类型的 serde 形式，宿主用 serde 的属性（`tag`、`rename_all`）改，生成器照着写。
- 运行时抛出的错误名（`CordisError`、`RustError` 作为 `error.name` 的值）：0.18 G11 定下不变；本稿只改声明里的名字。
- 插件作者自己的依赖怎样造假、测试工具直接听事件、`rutis-host call`（#670）。
- `rutis-host dev` 里用契约检查：`dev` 跑的是真宿主，本来就是真实的转换规则。
- 自审时删掉的：Python 的 `Services` 总表（`ctx.use` 不带类型参数，用不上）；同时检查 mypy 与 pyright（只留 pyright）；生成假服务的代码（行为是宿主的业务，检查用数据描述就够）。

## 一、开发者要做成什么

宿主持有者做了 deskmate：Rust 写的宿主，用 `#[rutis::service]` 提供 `notes`（`put(key: String, value: String)`、`get(key) -> Option<String>`）和 `tools`（`register(name, description, handler)`，`handler` 是 `Fn(String) -> BoxFuture<Result<String, ToolError>>`）。他把类型声明、模板和测试交给第三方插件作者，作者用 TypeScript 或 Python 写插件。

现在卡在三处（[评估报告](https://github.com/arcships/rutis/issues/663#issuecomment-6411076725)）：

1. **Python 没有类型**。`rutis-host types` 只写 TypeScript，宿主手写了一份 Python Protocol，Rust 一改就对不上。
2. **测试通过，装进宿主却失败**。测试工具不知道宿主的 Rust 类型：给 `notes.put` 传数字、处理函数返回 `undefined`、`handler` 不是函数、插件自己也提供 `notes`，测试都通过；进了宿主才失败。宿主为此手写了约 160 行严格的假服务（TypeScript 和 Python 各一份）。
3. **声明里露出 rutis**。文件头写着 `Generated by rutis-bridge (build::Exports) from the Rust sources`，错误接口叫 `RustError`。

## 二、现在有什么

| 已有 | 在哪里 | 本稿怎样用 |
| --- | --- | --- |
| 生成器：读宿主 crate 的源码，找出 `#[rutis::service]` 类型，按 serde 的属性推出每个值跨边界的形式（内部的 `Ty` 与结构体、枚举的声明），再写成 TypeScript | `crates/rutis-bridge/src/build/exports.rs`（`build::Exports`） | 同一份推导结果多写两样：Python 类型、契约描述 |
| `Exports::declared(path, ts)`：生成器推不出时由宿主写出某个 Rust 类型的 TS | 同上 | 加一个 Python 版本 |
| `rutis-host types [dir] [-o file]` | `crates/rutis-host/src/main.rs` | 加几个选项 |
| 真实宿主的值转换：宏生成的分发代码用 serde 把收到的值解码成 Rust 参数，把结果编码回去 | `crates/rutis-bridge/src/marked.rs`、`#[rutis::service]` | 是规则的唯一来源；契约检查必须与它一致（§六） |
| 测试工具：`load` / `host`，`services` 给假服务，`strict` 让值像跨进程那样复制；检查 `inject`、`provides` | `node/rutis/src/testing.mjs`、`python/rutis/rutis/testing.py` | 加一个 `contract` 选项 |

缺的只是：生成器多两种输出，测试工具多一步检查。不新增协议、内核或运行时的东西。

## 三、决策

| # | 决策 | 章节 |
| --- | --- | --- |
| H1 | 生成器从同一份推导结果写三样：TypeScript 声明（现有，内容不变）、Python 类型模块（新）、契约描述（新，一个 JSON 文件）。`Exports` 加 `.python(file)`、`.contract(file)`；`rutis-host types` 加 `--python <file>`、`--contract <file>` | 五 |
| H2 | Python 类型是一个可以导入的 `.py` 模块：服务是 `Protocol`，结构体是 `TypedDict`，只有名字的枚举是 `Literal`；支持 Python 3.10（与 SDK 相同） | 5.2 |
| H3 | 契约检查装进现有测试工具，入口是 `load` / `host` 的 `contract` 选项，值是读进来的契约描述；假服务的行为仍由 `services` 给 | 六 |
| H4 | 有 `contract` 时检查五件事：参数类型、结果类型（含处理函数的结果）、该是函数的参数是函数、只有契约里的方法、插件不能提供契约里的服务名；报的错误和真实宿主相同 | 6.2 |
| H5 | 规则只有一个来源：真实宿主的 serde 解码。契约描述只说"类型是什么"，不写规则；一份用例表 `specs/host-contract/cases.json` 同时跑真实宿主和两个测试工具，结果与文字逐字相同。描述不了的类型一律放行，检查永远不比真实宿主更严 | 七 |
| H6 | 生成内容里的名字由宿主定：`.header(text)` / `--header` 换文件头，`.error_name(name)` / `--error-name` 换错误接口名；**不设就和现在完全一样**（文件头、`RustError`），Python 用同样的默认 | 5.3 |
| H7 | 0.19 只做 TypeScript（Node、Bun）和 Python；其他语言以后按同一份契约描述和用例表加 | 5.4 |
| H8 | 不生成插件配置的类型或表单：配置是插件作者自己的 Schema，不是宿主的 Rust 服务，评估里也没有人要 | — |

## 四、这不是通用类型层，也不是插件之间的契约

原则 6 说契约只约定服务名和方法形状，不建通用的类型层；#223 拒绝了跨插件的服务契约（兼容与替换是作者的事）。本稿与它们不冲突：

- **来源是宿主自己的 Rust 代码**。生成的是宿主用 Rust 写的、自己提供的服务的声明和检查，就像 `rutis-host types` 现在写 TypeScript 一样。没有新的类型语言让任何人去写，宿主只写 Rust，插件作者只写本语言。
- **只描述一种已经存在的规则**。宿主收到值时本来就用 serde 解码，类型不对就失败；契约描述只是把这件事提前到测试里。值跨语言的规则仍然由 rutis 统一（原则 6 的后半句）。
- **不进运行时**。契约描述只给测试工具读；内核、loader、各语言运行时、协议都不读它，插件之间也不交换它。插件提供的服务没有契约描述，它们的兼容仍是作者的事。

## 五、生成什么

### 5.1 怎样生成

```sh
rutis-host types . -o types/deskmate.d.ts \
  --python types/deskmate.py \
  --contract types/deskmate.contract.json \
  --header "Generated by deskmate from its services; do not edit." \
  --error-name DeskmateError
```

`build.rs` 里同样：

```rust
rutis_bridge::build::Exports::new()
    .typescript("types/deskmate.d.ts")
    .python("types/deskmate.py")
    .contract("types/deskmate.contract.json")
    .header("Generated by deskmate from its services; do not edit.")
    .error_name("DeskmateError")
    .declared("notes::Text", "string")
    .declared_python("notes::Text", "str")
    .generate()?;
```

- 只给 `-o` 时（或 `build.rs` 只给 `.typescript`）输出与现在逐字相同。`rutis-host types` 不给任何文件时照旧把 TypeScript 打到标准输出。
- `.generate()` 至少要有三种文件中的一种。
- `.declared_python(path, python)`：与 `.declared` 相同的用途（生成器推不出的类型，例如手写 `Serialize` 的透明包装类型）。只给 `.declared` 不给 Python 版本时，Python 里写 `Any` 并打印一条警告。`.declared` 的类型在契约描述里是"任意值"（宿主在方法里自己检查，见 H5）。评估里的宿主就是这样用 `Exports::declared` 的。

### 5.2 Python 类型

对照 TypeScript 现有的写法：

| Rust（serde 形式） | TypeScript（现有） | Python |
| --- | --- | --- |
| `#[rutis::service]` 类型 | `interface Notes { put(…): Promise<void> }` | `class Notes(Protocol): async def put(self, key: str, value: str) -> None: ...` |
| 结构体 | `interface Entry { … }` | `class Entry(TypedDict)`；可省略的字段放进 `total=False` 的父类（3.10 没有 `NotRequired`） |
| 只有名字的枚举 | `"a" \| "b"` | `Literal["a", "b"]` |
| 带数据的枚举 | 对象的并集 | `TypedDict` 的 `Union` |
| `Option<T>` | `T \| null` | `T \| None` |
| 整数 / 浮点 / `u64` 以上 | `number` / `number \| bigint` | `int` / `float` / `int` |
| `Vec<T>`、`HashMap<String, T>`、元组 | `T[]`、`Record<string, T>`、`[A, B]` | `list[T]`、`dict[str, T]`、`tuple[A, B]` |
| `serde_json::Value` | `unknown` | `Any` |
| 回调参数 `impl Fn(A) -> BoxFuture<Result<R, E>>` | `(arg0: A) => R \| Promise<R>` | `Callable[[A], R \| Awaitable[R]]` |
| `rutis::Definition` | 插件类型 | `rutis.Plugin` |
| 错误 `Err(E)` | `ProblemThrown = RustError<"Problem", codes, data>` | `ProblemCode = Literal[…]`；方法的 docstring 写 `Raises RustError with name "Problem"` |
| 错误接口 | `interface RustError` | `RustError = rutis.RemoteError`（别名，`except RustError as e` 与 `e.code`、`e.data` 照常用） |

插件作者写 `notes: Notes = ctx.use("notes")`，由编辑器或 pyright 检查；不写也照样运行。Python 的 `ctx.use` 不带类型参数，所以不生成 TypeScript 那样的 `Services` 总表。生成的模块通过 `pyright --strict`（实施时两个示例都检查，与 TypeScript 的 `tsc --strict` 一样）。

### 5.3 宿主的名字

| 位置 | 默认（与现在相同） | 宿主设了以后 |
| --- | --- | --- |
| TypeScript 文件头 | `// Generated by rutis-bridge (build::Exports) from the Rust sources; do not edit.` | `// <header>` |
| Python 文件头 | `# Generated by rutis-bridge (build::Exports) from the Rust sources; do not edit.` | `# <header>` |
| 错误接口 / 别名 | `RustError` | `<error_name>`；各 `<Name>Thrown` 写成 `<error_name><"Name", …>` |
| 契约描述 | 不含文件头和平台名字 | — |

- `error_name` 必须是合法的标识符，不能与生成的其他名字或保留名重名（现有的 `RESERVED` 表），否则生成失败并写明重名的是什么。
- `<Name>Thrown` 别名本身仍按错误类型命名（它对应运行时 `error.name` 的值）。方法返回 `rutis::Result` 时运行时的名字是 `CordisError`，0.18 G11 定下不变，所以别名仍叫 `CordisErrorThrown`；宿主不想让它出现，就让方法返回自己的错误类型。这写进 Rust 宿主指南。
- 默认不变是 issue 评论定下的（避免已有的 TypeScript 代码要改）；Python 是新的，用同样的默认，一个设置管两种语言，规则只有一条。

### 5.4 其他语言以后怎样加

加一种语言 = 生成器多一种输出（从同一份推导结果写）+ 那种语言的测试工具读同一份契约描述 + 跑同一份用例表。契约描述和用例表不用改。等某个宿主要给 Go、Swift 或 Kotlin 的插件作者交材料时再加。

## 六、测试工具里的契约检查

### 6.1 入口

TypeScript（Node 与 Bun 都用 `@arcships/rutis/testing`）：

```ts
import { load } from '@arcships/rutis/testing'
import contract from '../types/deskmate.contract.json' with { type: 'json' }
import { fakeNotes, fakeTools } from './fakes.ts'   // 宿主模板里的假服务行为

const tools = fakeTools()
const t = await load(plugin, { contract, services: { notes: fakeNotes(), tools } })
assert.equal(await tools.run('wordcount', 'a b c'), '3 words')
```

Python：

```python
contract = json.loads((ROOT / "types/deskmate.contract.json").read_text())
async with load(plugin, contract=contract, services={"notes": FakeNotes(), "tools": tools}) as t:
    assert await tools.run("wordcount", "a b c") == "3 words"
```

- `contract` 是 `load` 与 `host`（TypeScript）、`load`（Python）的选项，与 `services`、`strict` 并列。一个 `host()` 里所有行共用它。
- 没有 `contract` 时行为与现在完全相同。
- 假服务仍然是 `services` 里的普通对象，用本语言写；它是宿主模板给的，还是插件作者用 #670 的写法自己写的，都一样被检查。
- 契约里有、但测试没给的服务，插件 `inject` 了它时照旧报 `the plugin injects notes: give the test a service notes`。
- 插件作者要写的 rutis 特有的东西：多一个 `contract` 选项。宿主的模板里已经写好，作者照抄即可。代价是测试多读一个 JSON 文件；描述是数据，不执行任何代码。

### 6.2 查什么

有 `contract` 时，契约里的每个服务在交给插件之前包一层：

| 时机 | 检查 | 与真实宿主 |
| --- | --- | --- |
| 插件调用方法 | 方法在契约里 | 否则 `no-method`，与真实宿主相同 |
| 插件调用方法 | 每个参数按契约的类型检查（先按 `strict` 复制，再检查复制后的值，即宿主收到的值） | 否则 `bad-argument`，调用失败；插件拿到的错误与真实宿主相同 |
| 参数该是函数 | 是函数；它被调用时，结果按契约检查 | 不是函数是 `bad-argument`；结果不对时，调用它的一方（宿主的假服务或测试）拿到 `bad-argument` |
| 假服务返回 | 结果按契约检查 | 宿主自己的假服务写错了也会被发现 |
| 插件 `ctx.provide` | 名字不在契约里 | 否则这一行加载失败，`load` 拒绝；真实宿主同样让这一行失败 |

参数个数：少了按缺的参数是 `undefined` / `None` 检查（`Option` 的参数可以省略，与 serde 相同）；多了报 `bad-argument`，与真实宿主相同。

### 6.3 与 #670 的边界

#670 管插件作者自己的依赖（别的插件的服务）怎样在测试和 `dev` 里用本语言造假，以及 `t.on`、`rutis-host call`。本稿管宿主提供的服务：宿主生成契约描述，交给插件作者，测试工具按它检查。两者在测试工具上的交点只有一个：`services` 里的对象无论怎样写出来，名字在 `contract` 里就被检查。本稿不改 `services` 的形式，也不加别的入口。

## 七、和真实宿主一致

规则写在一处：真实宿主的 serde 解码。保证一致的办法：

1. **契约描述只写类型，不写规则**。类型的词汇是固定的：`string`、`boolean`、`null`、`any`、`number`（浮点）、`{int: [最小, 最大]}`（按 Rust 整数类型的范围）、`{option}`、`{list}`、`{tuple}`、`{map}`、`{ref: 名字}`、`{function: {args, result}}`、`plugin`；具名类型是 `{struct: {fields, deny_unknown}}` 或 `{enum: {tagging, variants}}`（`tagging` 是 serde 的四种：外部、`tag`、`tag`+`content`、`untagged`）。描述由生成器从 TypeScript 用的同一份推导结果写出，TypeScript 声明与契约描述不会各说各的。
2. **检查器每种语言一份，按描述走**，在各自的测试工具里（Node 一份，Python 一份）。
3. **一份用例表锁住三方**：`specs/host-contract/cases.json`，每条是 `{ service, method, args | result, then: "ok" | { code, message } }`，针对一个夹具 crate（`crates/rutis-bridge/tests/fixtures/contract`，覆盖上面每个词汇、serde 的 `rename_all`、`default`、`deny_unknown_fields`、四种枚举写法、`u8` 越界、`1.5` 给整数、Python 的 `True` 给整数、回调结果）。
   - 真实宿主：rutis-bridge 的测试把每条用例经会话值交给夹具服务的真实分发代码，比较结果与文字；
   - Node、Python 测试工具：读夹具生成的契约描述，跑同样的用例，逐字比较。
   文字以真实宿主为准：0.18 #677 改写后的 `bad-argument` 文字是什么，表里就记什么，检查器跟着表。
4. **描述不了的就放行**：`.declared` 的类型、手写 `Deserialize`、`deserialize_with`、`serde_json::Value` 在描述里都是 `any`。这样检查只会比真实宿主宽，不会比它严，测试不会冤枉一个能在宿主里跑的插件。用例表里也有这几种，验证"放行"。
5. **生成器变了，用例表跟着跑**：夹具的契约描述在 CI 里重新生成并与提交的版本比较，与 TypeScript 现在的做法一样。

## 八、开发者看到什么

**宿主持有者**

```text
$ rutis-host types . -o types/deskmate.d.ts --python types/deskmate.py --contract types/deskmate.contract.json --error-name DeskmateError
(三个文件写好，没有输出)

$ rutis-host types . --python types/deskmate.py
warning: notes::Text has no Python type: declare it with .declared_python (written as Any)

$ rutis-host types . --error-name Services
error: --error-name Services is a name the declarations already use
```

**插件作者**（TypeScript，`node --test`；Python 的 `pytest` 文字相同，错误类型是 `BindingError` / `PluginTestError`）

| 第三方测试里 | 测试失败的文字 |
| --- | --- |
| `notes.put('k', 42)` | `BindingError: notes.put: argument 2 should be a string, got 42` |
| `tools.register('wc', 'count', 'not a function')` | `BindingError: tools.register: argument 3 should be a function, got "not a function"` |
| 处理函数返回 `undefined`，测试调用 `tools.run('wc', 'a b')` | `BindingError: tools.register: argument 3 returned undefined, should be a string` |
| `notes.putt('k', 'v')` | `BindingError: notes has no method putt (methods: get, put)` |
| 插件 `ctx.provide('notes', …)` | `PluginTestError: wordcount: notes is already provided by the host`（`load` 拒绝） |
| 宿主的假 `notes.get` 返回数字 | `BindingError: notes.get returned 42, should be a string or null` |

- 这些与装进 deskmate 后看到的相同（真实宿主的输出另带行名前缀，见 0.18 §七）。错误码在 `error.code` 里（`bad-argument`、`no-method`），不在文字里。
- 不出现 rutis、Rust、serde 的原文、内部 id。
- 不给 `contract` 的测试，输出与现在相同。

**插件作者的编辑器**：Python 里 `await notes.put("k", 42)` 被 pyright 标出 `Argument of type "Literal[42]" cannot be assigned to parameter "value" of type "str"`；TypeScript 与现在一样由 `tsc` 标出。
