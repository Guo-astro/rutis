# 统一事件：一个逻辑总线

[English](design-events-2026-10-18.en.md)

状态：方案（2026-10-18），取代 #340、#358、#359 的草稿，以及 `requirements-protocol-plugins` §5 的事件边界规则 2–5。不保留旧行为。

## 一、目标

不论插件是哪种形态——Rust 内核插件、Cordis 插件、Node / Bun / Python / Go 的叶子插件、远程运行时，还是另一个节点上的插件——事件都只有**一套规则、一种用法**，并且对开发者无感：

> 一个事件在哪里发出、监听器在哪里，结果都和所有监听器在同一个进程里一样。

做不到的情况只有一种：物理上不可能（同步等待成环、同步等待一个已经断开的对端）。这时明确报错，从不悄悄换成别的行为（设计哲学 §7 原则 7）。

## 二、现状（2026-10-18，`ffd6e8b3`）

今天只有 Rust 内核总线内部是一套规则。其他路径各自一套，彼此不通或只通一半：

| 路径 | 能用的方式 | 键 | 问题 |
| --- | --- | --- | --- |
| Rust 进程内 | emit / parallel / serial / waterfall / 同步 bail、waterfall | 类型（`EventKey<E>`）、名字、实例 | 自身也有不一致：非实例监听器不按存活过滤、卸载不等；`parallel` 的错误按完成顺序 |
| Cordis ↔ rutis | 一律当 `parallel`；同步 `bail` 报错；`waterfall` 变成一段异步 | 生成的类型 | 分发方式丢失（#340）；只能转发没有返回值的事件；`internal/*` 不能过（#359） |
| rutis → 叶子运行时 | 只有嵌入方手动 `Process::emit`，对面按 `parallel` | 字符串 | 不接 rutis 总线；rutis-host 配置里没有入口；拨入实例没有 |
| 叶子运行时 → rutis | **不存在** | — | 叶子 `ctx.emit` 只在本进程里 |
| 运行时 ↔ 运行时 | **不存在** | — | 每个进程一条孤立的总线 |
| 节点 ↔ 节点 | 当 `parallel`，只能 JSON | `NodeEvent` 动态名 | 方式丢失；新值类型被拒；断线时静默丢弃；实例之间串台 |

叶子插件只有 `on` / `emit`。四种语言连这两个的行为都不一致：`emit` 等不等监听器、出错是抛出 / 返回 / 结束进程、卸载时等不等正在跑的监听器、只有一个错误时要不要包一层，各不相同。

真实插件需要的远不止"通知"。已发布的 dsh 插件约 30 处监听，用了 `waterfall`（中间件、变换）、`serial`（取第一个结果）、`parallel`（等全部完成的屏障），并大量依赖作用域：事件只在自己的会话、agent 范围内往上传。还有 7 处手写了"一个监听器出错不影响别人"的 emit。

## 三、模型

### 1. 一个逻辑总线

一个宿主上的全部监听器——Rust 插件的、每个运行时进程里每个插件的、经节点连接引进来的——组成**一个逻辑总线**。rutis 是这个总线的中心：每个运行时把自己的监听器登记给宿主，就像 0.12 起服务会自动登记一样。

- **登记是自动的。** 插件照常写 `ctx.on(name, listener)`，什么都不用声明。
- **分发按全局的监听器表执行。** 发出事件时，rutis 按登记顺序执行这个名字的全部监听器。本进程的直接调用；别处的作为一次调用发过去，调用方式按分发方式而定。
- **本地快速路径。** 一个名字的监听器都在发出方的进程里时，在本地分发，不经过宿主。宿主把"哪些名字在别处也有监听器"推给各运行时，运行时据此决定走本地还是经宿主。

### 2. 事件 = 名字 + 参数 + 作用域

- **名字**是字符串，所有语言、所有路径通用。惯例是 `area/verb`，比如 `session/created`。
- **参数**按值类型规则跨边界（0.11 的十种值、按引用传对象和函数）。节点之间也一样，不再限于 JSON。
- **作用域**是发出方所在的实例。规则只有一条：**监听器收到自己作用域、以及其下所有作用域里发出的事件**。根上的监听器收到全部事件；租户 t1 里的监听器收不到 t2 的事件。这正是 dsh-scope 的写法（"事件只往上传，不往下传"），也修掉了今天实例之间串台的问题。
- **过滤**：发出时可以带一个过滤函数，对每个监听器调用一次，传入这个监听器的描述（插件名、行 id、作用域链），返回是否送达。过滤函数在**发出方的进程里**执行，监听器的描述由逻辑总线提供，所以它对任何地方的监听器都一样有效，不需要跨进程调用。五种语言用同一个机制；Cordis 的 `Context.filter`（`thisArg` 上的过滤）接到这里：对 Cordis 自己的监听器传它的上下文，对别处的监听器传一个代表它的上下文（带作用域与插件信息）。作用域规则是默认过滤，自定义过滤在它之上再筛。
- **Rust 的类型化事件**：事件类型以 `Event::NAME` 作为跨语言的名字，参数按 serde 编解码。类型是 Rust 的语言特性，保留；跨语言时按名字对应。

### 3. 五种分发方式，处处同义

语义以 Cordis 为准（真实插件都按它写）。下表就是全部规则，与监听器在哪里无关：

| 方式 | 发出方得到 | 执行 | 返回值 | 监听器出错 |
| --- | --- | --- | --- | --- |
| `emit` | 立即返回，不等 | 按登记顺序调用每个监听器；同一发出方、同一名字的事件按发出顺序到达每个监听器 | 忽略 | **不影响发出方、不影响其他监听器**；在监听器所在的一侧报告（宿主的错误汇集、运行时的 stderr 状态行）。不再结束进程 |
| `parallel` | 等全部完成 | 按登记顺序启动，异步部分重叠 | 忽略 | 全部跑完；有失败时把错误按**登记顺序**汇总抛出（各语言的汇总错误类型） |
| `serial` | 第一个"有结果"的返回值 | 按登记顺序逐个等待 | 返回值不是 `null` / `undefined` / `false`（Rust：`Some`）就停止并返回它 | 抛出并停止 |
| `waterfall` | 最外层监听器的返回值 | 由外向内，每个监听器拿到 `next`；`next` 可以是另一个进程里的函数（按引用传） | 链式传递；不调 `next` 就否决其余 | 抛到发出方；`next` 调两次报错 |
| `bail`（同步） | 第一个有结果的返回值，同步 | 按登记顺序同步调用；别处的监听器作为**同步调用**执行（和服务的同步方法同一套机制，参加等待环检测） | 同 `serial` | 抛出并停止；等待成环（`SyncWaitCycle`）或对端断开时明确报错。**遇到异步监听器**（JS 返回 Promise、Python 返回协程、Rust 异步监听器）**明确报错**，各语言相同 |

Rust 的 `waterfall_sync` 与同步 `bail` 同理。

"有结果"的判断各语言相同：返回 `null` / `undefined`（Python `None`、Go `nil`、Rust `None`）或 `false` 表示没有结果，其余都算有结果。Rust 的 `Some(false)` 也算没有结果，与其他语言一致。

**一张监听器表。** 一个监听器登记一次，可以被任何方式分发；由发出方决定方式（Cordis 本来如此）。`waterfall` 里监听器从参数拿到 `next`。Rust 去掉单独的 waterfall 登记（`on_waterfall*`），监听器统一为：

```rust
ctx.events().on(&ctx, &key, |ctx, event: &E, call: Call<E::Value>| async move {
    // call.mode()：这次是哪种方式；call.next(..)：仅 waterfall 可用，其他方式调用即报错
    Ok(None) // 或 Ok(Some(v))
})
```

同步监听器用 `on_sync` 登记（同一张表，标记为同步），可以被所有方式调用；异步监听器不能被同步 `bail` / `waterfall_sync` 调用。

### 4. 每种语言的写法

每种语言都有这五种方式，写法是这门语言的原生写法：

| | 监听 | 发出 |
| --- | --- | --- |
| Rust | `ctx.events().on(&ctx, &key, ..)`、`on_sync` | `emit` / `parallel` / `serial` / `waterfall` / `bail_sync` / `waterfall_sync` |
| Node（含 Cordis 插件）、Bun | `ctx.on(name, fn)` | `ctx.emit` / `await ctx.parallel` / `await ctx.serial` / `ctx.waterfall` / `ctx.bail`（Cordis 插件就是 Cordis 自己的 API；Bun 没有 Cordis，只有叶子插件） |
| Python | `ctx.on(name, fn)` | `ctx.emit` / `await ctx.parallel` / `await ctx.serial` / `await ctx.waterfall` / `ctx.bail` |
| Go | `ctx.On(name, fn)` | `ctx.Emit` / `ctx.Parallel` / `ctx.Serial` / `ctx.Waterfall` / `ctx.Bail` |

各语言的测试工具提供同样的方式，并对同一份期望文件比对（与值类型的做法相同）。

### 5. 监听器的生命周期

- 监听器属于登记它的插件（行），插件卸载即注销，各语言一致。
- **卸载时等正在运行的监听器结束**，最多等到关闭截止时间，同时发出取消信号（Go 的 context、Python 的任务取消、JS 的 AbortSignal）。今天 Go 和 Rust 的实例监听器是这样，其余不是，统一为这一种。
- 卸载后发出的事件不再到达它；正在发往它的调用以传输错误失败一次，和调用服务一样。

### 6. 断开与失败

- 运行时进程或节点断开时，它的监听器从逻辑总线上撤下，就像它们的插件卸载了一样。之后的事件不再发给它们——这与"监听器不在了"在进程内的含义一致，不是静默丢失。
- 正在进行的一次分发里，发往断开一侧的调用失败一次：`parallel` / `serial` / `waterfall` / `bail` 把错误交给发出方；`emit` 在报告里记一行。
- 不加调用超时（与服务调用一致）。

### 7. 框架事件

`internal/*` 仍是每个运行时自己的框架内部机制，不跨边界：它们传的是只在那个进程里有意义的东西（监听器登记钩子、属性访问代理）。

跨语言需要的框架信息，以普通事件的形式发布在保留的 `rutis/` 名字空间下，所有语言都能监听：

| 事件 | 参数 |
| --- | --- |
| `rutis/service` | 服务名、作用域、出现还是撤下 |
| `rutis/row` | 行 id、作用域、状态（Pending / Running / Failed / Stopped） |
| `rutis/runtime` | 运行时名、状态（running / down + 原因） |

插件不能发出 `rutis/*`，只能监听。Cordis 插件在本进程内用的 `internal/dispatch`、`internal/service` 不变；从别处到达的事件在调用本进程的监听器之前，由 Node 运行时以 rutis 的方式名触发一次 `internal/dispatch`，所以它的校验插件照常看得到它们。

### 8. 节点之间

另一个节点上的监听器，经节点连接成为本节点逻辑总线上的条目，规则与本机完全相同（五种方式、作用域、值类型、断开）。

节点之间共享哪些事件，由节点连接已有的 `export` / `import` 决定，与服务相同：按名字或前缀。原来的 `events: {out, in}` 合并进去。

## 四、物理上做不到的地方

只有同步等待：同步 `bail` / `waterfall_sync` 等待别处的监听器时，成环报 `SyncWaitCycle`，对端断开报传输错误，与同步服务调用相同；遇到异步监听器报错。除此之外没有边界规则，规则就是第三节。

## 五、不保留旧行为

- **协议**：事件协议升级为新版本（监听器登记、带方式与过滤的分发、对监听器的调用、`rutis/*` 事件）。与 0.12 及更早的运行时、节点混用时，挂载 / 连接直接失败，信息写明升级哪一端。不留旧路径。
- **删除的配置与 API**：`RuntimePlugin::emits` / `LocalRuntime::emits`、`Mount.emits` / `events`、Cordis 挂载与生成器的 `events` / `emits`、节点连接的 `events: {out, in}`、Rust 的 `on_waterfall*`。写了直接报错，错误里给出替代写法；`docs/migration-0.13` 列出全部变化。
- **行为变化**（发布说明写明）：`emit` 的监听器出错不再结束进程、不再中断其他监听器；Go 的 `Emit` 不再等待监听器；Rust `parallel` 的错误按登记顺序；Rust 所有监听器按存活过滤、卸载时等待；`Some(false)` 不再算有结果；同步 `bail` 遇到异步监听器报错（Cordis 原来把 Promise 当结果）。
- **事件边界规则**：`requirements-protocol-plugins` §5 的规则 2–5 删除，由本文第三节取代；保证登记表 `boundary/5.2`–`5.5` 改写。

## 六、实现

一次做完，一起合并，一个版本发布：

1. **先定协议规格**：帧格式、能力、监听器描述、调用与取消、`rutis/*` 事件。写进 `design-protocol-plugins` 与运行时契约（`.agents/skills/rutis-new-runtime/references/runtime-contract.md`），作为各实现的共同依据。
2. **同时实现**：Rust 内核与 bridge（逻辑总线、别处监听器条目、一张监听器表、过滤、作用域、修复不一致）；Node（Cordis 插件经 Cordis `internal/listener` 登记，Cordis 的五种方式直接用）与 Bun；Python、Go（五种方式、过滤、卸载等待、测试工具）；节点连接（`export` / `import` 管事件）。
3. **一套测试**：事件期望文件，五种语言的真实运行时与测试工具都对它比对；矩阵覆盖"发出方 × 监听器所在 × 方式 × 作用域 × 过滤 × 断开"；两节点与 netem 场景加事件；原边界规则测试删除或改写。
4. **文档**：各语言指南加"事件"一节；插件 API、迁移说明、保证登记表、agent skills。
5. **整体评审、发布门预演、发布。**

Swift 与 Kotlin 的 SDK 在这之后开始，直接按新协议实现。

## 七、依据

- 设计哲学 §7：原则 1（模型在 Rust 内核实现一次）、原则 7（做不到的写成规则，不悄悄降级）、原则 10（显式优于隐式）。
- 值类型 V0：插件只写本语言原生的代码。
- 0.12 的服务自动对外：登记自动、声明可选。事件沿用同一做法。
- Cordis 4.0.4 `events.ts`：五种方式的参照语义。
