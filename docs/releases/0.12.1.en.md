# rutis 0.12.1

[中文](0.12.1.md) · [0.12.0 release notes](0.12.0.en.md)

0.12.1 fixes `build::Exports` in `rutis-bridge`: when the crate holding an exported type had a glob-import cycle, the generator never finished and `cargo build` hung ([#459](https://github.com/arcships/rutis/issues/459)). The other packages have no changes and move to 0.12.1 only to stay on the train.

## Fixes

- **`Exports::generate()` no longer hangs on glob-import cycles**: a crate root re-exporting its modules with `pub use m::*;` while the modules write `use crate::*;` (or `use super::*;`, or a longer cycle) is a common layout, and legal Rust. Looking up a name, the generator followed every glob without remembering which `(module, name)` pairs it was already resolving, and stopped only at a depth limit of 48. A name found only in the standard prelude (`Result`, `Vec`, `String`) therefore went round the cycle to that depth, branching once per glob at every level, and the build script ran at full CPU indefinitely. A lookup already under way is now not entered again (as rustc does: nothing on that path, then the prelude), and each name's result is computed once per generation. The six-module layout of #459 went from not finishing after more than five minutes to under a second for the generator.
- Two more found in the same review: type aliases that refer to each other (`type A = B; type B = A;`, which rustc refuses too) no longer overflow the generator's stack; the methods using them are left out with a build warning as before. A module whose `#[path]` leads back to a file being read no longer recurses without end; it is skipped with a build warning.

## Packages

All of these are at **0.12.1**: on crates.io `rutis`, `rutis-bridge`, `rutis-loader`, `rutis-host`, `rutis-sdk`, `rutis-dylib`, `rutis-dylib-meta`, `rutis-dylib-launcher`; on npm `@arcships/rutis`, `@arcships/rutis-runtime`, `@arcships/rutis-bun`, `@arcships/rutis-host` and the five platform packages; on PyPI `rutis`, `rutis-host`; the Go module `github.com/arcships/rutis/go/rutis` (tag `go/rutis/v0.12.1`); the `rutis-host` binaries on the release page. `rutis-cli` is still released separately.

## Compatibility

- Fully compatible with 0.12.0: no API, protocol or configuration changes; 0.12.0 and 0.12.1 hosts and runtimes work together. For crates without cycles the generated code is the same as with 0.12.0.
- Projects that use `rutis_bridge::build::Exports` in their `build.rs` should upgrade; other setups can stay on 0.12.0.
- Dylib: the SDK identity includes the package versions in its dependency tree. After rebuilding the SDK and the host with 0.12.1, dylib plugins built for 0.12.0 must be rebuilt with the new SDK; keeping the existing SDK bundle is unaffected.
