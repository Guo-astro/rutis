# rutis 0.12.0 (draft)

[中文](0.12.0.md) · [0.11.0 release notes](0.11.0.en.md)

> Draft: 0.12 is not released yet. Entries are added as changes land on main, and the notes are finalized before the release.

## New

- **Runtime state lines** ([#274](https://github.com/arcships/rutis/issues/274), [rutis-host](../guide/rutis-host.en.md#what-run-prints)): `rutis-host run` and `dev` print `runtime <name>: down (<reason>)` when a local runtime's (`node`, `py`, `bun`, Go's `go-<binary>`) process ends on its own or the runtime cannot start, the reason saying how the process ended, such as `runtime py: down (exited with signal: 9 (SIGKILL))`; and `runtime <name>: running` when it runs again. Before, only its rows going back to `waiting for its services` showed it. Runtimes the host stops (the host stopping, a Go runtime stopping when idle) print nothing. Rust library: `rutis-loader` gains `GoRuntimesHandle::states` (each Go runtime's state, without reading the binaries).
- **Changing the configuration while it runs** ([#274](https://github.com/arcships/rutis/issues/274), [rutis-host](../guide/rutis-host.en.md#changing-the-configuration-while-it-runs)): `rutis-host run` reads `rutis.json` again on SIGUSR1 on Unix (systemd: `ExecReload=/bin/kill -USR1 $MAINPID`); with `--watch-config` (off by default) it does when the file's content changed and stayed the same for 500 milliseconds, the way for Windows and Kubernetes ConfigMaps. All or nothing: the new rows are checked first, and a row failing after the replacement brings the old rows back; a broken configuration leaves the old one running and prints `rutis-host: reload rejected: <reason>; nothing changed`, an applied one `rutis-host: reloaded <file> (<n> rows changed)`. Rows added, removed and changed apply at once, those of an `instanced` group in every instance there is; a local runtime removed stops once its rows unloaded. `format`, `id`, `listen`, `runtimes.go`, `runtimes.remote` (`listen` and `instances` included) and a local runtime added or with changed settings cannot change this way: refused, saying to restart the host. SIGHUP is still a termination signal. Credentials are now read from the environment when a link dials or a far end dials in, so a peer row a reload adds connects too.
- **Restarting a crashed runtime** ([#274](https://github.com/arcships/rutis/issues/274), [rutis-host](../guide/rutis-host.en.md#when-a-runtime-ends)): `runtimes.node`, `runtimes.py` and `runtimes.bun` gain the optional field `restart`, saying what happens when the runtime's process ends on its own: `"no"` (the default, as before: its rows wait), `"on-failure"` (it is started again after a wait and its rows come back; the wait is 1 second, doubling each time up to 30 seconds, back to 1 second after 60 seconds of running, and one more end after 5 restarts within 5 minutes gives up, printing `runtime <name>: gave up after 5 restarts within 5 minutes`; the numbers are fixed, not configurable), `"exit"` (the other rows unload and the host exits with the new exit status 3, for its process manager to restart it). `dev` follows the same rules and defaults, with `restart` in `rutis.dev.json`. Go runtimes have no such setting yet.
- **Revoking an identity at runtime** ([#273](https://github.com/arcships/rutis/issues/273), [design](../design-remote-runtime-dial-2026-10-14.en.md#5-identity-layer)): Rust library only, the hook a future management service calls. In `rutis-bridge`, `Revocable::new(inner, revocations)` wraps an `Identity` (static links) or an `Admission` (access points), and `Revocations::revoke(&id)` / `revoke_all()` revokes while everything keeps running: only the connections accepted as that id close (calls in flight on them fail once, as when the network drops), a handshake routed before the revocation is not handed over, and later connections are refused exactly as a wrong token is (403, or close code 4003 for an access point's id), so the dialer waits 30 s as `AuthRejected`. Other peers, other connections on the same listener and local runtimes are untouched. For an access point with a shared token, revoking an id closes that connection; `revoke_all()` withdraws the token. `Identity` and `Admission` gain `revocations()`, defaulting to `None`. rutis-host has no command for it: its tokens come from the environment and cannot be revoked at runtime ([Connect Nodes](../guide/nodes.en.md#security)).

- **Published Cordis plugins use each other's services natively, and theirs reach rutis by themselves** ([#428](https://github.com/arcships/rutis/issues/428), [Cordis](../guide/cordis.en.md)): Cordis packages mounted from `rutis.json` (published ones without `rutis.provides` as well) use each other's services by Cordis's rules within one Node runtime, getting the objects themselves; before, a row depending on another stayed `waiting for its services`. The services they provide reach rutis without a declaration, used by name by other runtimes, nodes and Rust; the methods are the functions of the service object (its own and its prototype chain's, not `constructor`), called as `async`; a package declaring `rutis.provides` follows its declaration. When a service of that name already has another provider, the row providing it later fails (also when it provides it after loading, as `run`'s state lines show), naming both: `service <name> is already provided by <existing>: row <row> cannot provide it too`. `rutis-host check` prints `<service>: may be provided at runtime by rows that do not declare all they provide (<rows>, …)` for a service only such rows may provide, instead of `cannot run: nothing provides …`, adding `; between Cordis rows of one runtime it resolves in Cordis` when the row and one of those rows are Cordis rows. Leaf plugins too, see the next entry. Rust library: `rutis-bridge` gains `row_projection_of`, `ServiceEvents::announced`, `Projection::on_announced` / `service_keyed_occupied` / `take_refused`, `HostDispatch::provider`, `RowService::provided_by`, `RowSchema::announces` / `cordis` and `Projection::on_refused`; `rutis-loader` gains `Declared::announces` and `Supply::Announced`.
- **The services leaf plugins provide reach rutis by themselves; `provides` becomes optional** ([#442](https://github.com/arcships/rutis/issues/442), [Plugin API](../guide/plugin-api.en.md#ctx)): in all four SDKs (Node, Bun, Python, Go), what `ctx.provide(name, impl)` provides reaches rutis without a declaration, and plugins of other languages use it by name. Its methods are the public methods of the implementation: JavaScript, its own and its prototype chain's functions (not `constructor`); Python, callable attributes not starting with `_`; Go, exported methods; all called as `async`, fields not counting. A `provides` declaration still applies: it marks methods `sync` and lets `rutis-host check` know before running who provides what; existing plugins need no change. An undeclared service appears once its plugin runs, and rows depending on it wait for it as usual; `check` reports such a dependency as `may be provided at runtime by …`, not as a failure. On a name clash the plugin providing it later fails, naming both. The four templates of `rutis-host new` no longer declare `provides`, keeping a comment on when to write it. The undeclared services of rows in a dial-in instance (`instances` of `runtimes.remote`) are visible only inside that instance ([Connect Nodes](../guide/nodes.en.md#runtimes-that-connect-in)). The testing tools (`@arcships/rutis/testing`, the same one under Bun; `rutis.testing`; Go's `rutistest`) no longer require a declaration either: `service(name)` calls by the inferred methods, and the new `methods(name)` (Go: `Service.Methods()`) returns the methods rutis sees.

## Fixes

- **A listening link is registered once applied** ([#411](https://github.com/arcships/rutis/issues/411)): a listening link in `rutis-bridge` used to register on its listener only in the task it starts after being applied. With an access point already on that listener, a static peer dialing in before then was refused as an unknown credential (403), and the dialer waited 30 s as `AuthRejected` before retrying; now the registration is there once `LinkPlugin` is applied, and a refused registration (the name taken) is still `Stopped`. An access point orders connections as they were delivered: of two connections of one id delivered almost together, the later one could before be counted as the earlier.
- **Families registered together were announced as offered twice** ([#435](https://github.com/arcships/rutis/issues/435)): `Peer::register` in `rutis-bridge` put a family's handler in place and then, under another lock, recorded the number of the offer (`since`). Another feature registering on another thread in between announced the family already present but without its number, as 0, and only then with its real one. To the far end the family was offered anew: its `peer:` rows restarted, and one being applied could find `PeerRows` just withdrawn and stay failed. Only when an end registers two or more families at once (a link that both hosts and imports, say). The number is now put in place together with the handler, so an announcement always carries each family's own.
- **A plugin whose dependency was withdrawn just before its apply stayed failed** ([#438](https://github.com/arcships/rutis/issues/438)): when a plugin's dependencies were ready and its `apply` scheduled, and a dependency was withdrawn before it ran, an `apply` that read it with `require` / `require_as` and returned that read's error as is (`require(..)?`) left the plugin Failed; provided again by the same provider, the dependency had no new generation, so the plugin was not retried either. A `peer:` row reading `PeerRows` could meet this at the moment its host really closed or reopened, and so could Node, Python, Bun and Go rows reading their runtime's service. The kernel now treats that error as it treats `InjectUnsatisfied`: when this generation's read of the dependency really failed, the plugin waits again and loads when the dependency is back.
- **A Python runtime that never exited after its host was `kill -9`ed** ([#192](https://github.com/arcships/rutis/issues/192)): when the host was killed and a plugin's cleanup never returned, the Python runtime, at its deadline (`RUTIS_SHUTDOWN_TIMEOUT`), was to write a line on stderr and exit with 1; its stderr was a pipe to the host, so with the host gone the line could not be written (BrokenPipeError) and the process stayed. It now exits all the same. Unix only: on Windows the runtimes end with the host's Job Object.
- **A Python `listen:` runtime printed a traceback when a session ended because the network dropped** ([#434](https://github.com/arcships/rutis/issues/434), [Connecting nodes](../guide/nodes.en.md#a-language-runtime-on-another-machine)): when the controller's heartbeat timed out or the connection was reset, the node's stderr got the websockets library's log and a full traceback. It now prints one line, `rutis: session ended (<reason>); waiting for a controller`, for example `rutis: session ended (heartbeat timeout); waiting for a controller`, and `rutis: session ended (replaced by a new connection)` when a new connection takes over. A dropped network, a heartbeat timeout or a close by the far end no longer prints websockets' log; other unexpected errors are still printed with their traceback (starting with `rutis: websockets:`). In the `dial:` state lines, a heartbeat timeout's reason is now `heartbeat timeout` instead of `closed (1011): keepalive ping timeout`.

## Compatibility

- **`rutis.json`**: the format is still 1. `runtimes.node`, `runtimes.py` and `runtimes.bun` gain the optional field `restart`; earlier files need no change and mean the same; a file using it cannot be read by the 0.11 rutis-host. A misspelt field in these three runtimes now lists `restart` among the fields allowed.
- **Exit status**: 3 is new (a runtime whose `restart` is `"exit"` ended, and the host stopped). 0, 1 and 2 mean what they did.
- **Node runtime protocol**: the `mount` arguments gain `announce`, its reply's `features` gain `rows.announce`, a `service` call for an undeclared service carries a fourth argument `{ row, methods }`, and the `rows.schema` reply gains `announces`, and `cordis` for a Cordis plugin. All of it applies only when both sides are 0.12: a 0.11 host with a 0.12 Node runtime, or a 0.12 host with a 0.11 runtime, gets no undeclared services in rutis, as in 0.11.
- **Leaf plugins**: an undeclared `ctx.provide` used to panic in Go (`Provides does not declare it`), stay visible only in its process on the other runtimes, and fail the testing tools' `service(name)` ("not declared in provides"); now it reaches rutis. A 0.11 host sends no `announce` and still gets no undeclared services; a 0.11 runtime follows its declarations, as before; a plugin of the 0.11 SDK has no `announces` mark, so `check` takes its declaration as all it provides. The plugin entries of `rows.schema` and the Go manifest gain `announces`.
- **`check` output**: a service only Cordis rows without `rutis.provides` may provide was `cannot run: nothing provides …` with exit status 1; it is now a line `may be provided at runtime by …`, with exit status 0; so is one only leaf plugins without `provides` may provide. For a leaf plugin that declares `provides`, `check` still takes the declaration as all it provides.
- **Rust library**: `rutis_loader::Declared` gains the public field `announces`; code building it with a struct literal needs the field (or `..Default::default()`); the same for the new fields `announces` and `cordis` of `rutis_bridge::runtime::RowSchema`.
- **Credentials**: `rutis-host` now reads `RUTIS_TOKEN_<NODE>` / `RUTIS_TOKEN` when a link dials or a far end dials in; the values are the same as before (the environment does not change within the process), only the peer rows no longer have to be there at start.
