# rutis 0.12.0（草稿）

[English](0.12.0.en.md) · [0.11.0 发布说明](0.11.0.md)

> 草稿：0.12 还没有发布，这里随合入 main 的改动逐条补充，发布前定稿。

## 新增

- **运行时状态行**（[#274](https://github.com/arcships/rutis/issues/274)，[rutis-host](../guide/rutis-host.md#run-打印什么)）：`rutis-host run`、`dev` 在本机运行时（`node`、`py`、`bun`、Go 的 `go-<二进制>`）的进程自己结束或起不来时打印 `runtime <名字>: down (<原因>)`，原因写进程怎样结束，例如 `runtime py: down (exited with signal: 9 (SIGKILL))`；它重新运行时打印 `runtime <名字>: running`。过去只能看到它的行变成 `waiting for its services`。宿主停止运行时（停止宿主、Go 运行时空闲停下）不打印。Rust 库：`rutis-loader` 新增 `GoRuntimesHandle::states`（各 Go 运行时的状态，不读二进制）。
- **运行中改配置**（[#274](https://github.com/arcships/rutis/issues/274)，[rutis-host](../guide/rutis-host.md#运行中改配置)）：`rutis-host run` 在 Unix 上收到 SIGUSR1 时重新读 `rutis.json`（systemd：`ExecReload=/bin/kill -USR1 $MAINPID`）；加 `--watch-config`（默认关闭）时文件内容变化、稳定 500 毫秒后重新读，Windows 和 Kubernetes ConfigMap 用这种方式。全有或全无：新的行先检查，替换后有新失败的行就换回旧的行；配置写错时旧配置继续运行，打印 `rutis-host: reload rejected: <原因>; nothing changed`，成功时打印 `rutis-host: reloaded <文件> (<n> rows changed)`。行的增删改直接生效，`instanced` 分组里的行对每个已有实例生效；删掉的本地运行时在它的行卸载后停止。`format`、`id`、`listen`、`runtimes.go`、`runtimes.remote`（含 `listen`、`instances`）和新增或改了设置的本地运行时改不了，拒绝并提示重启宿主。SIGHUP 仍是终止信号。凭据改为在拨号和对端连进来时从环境变量读，重新读配置新增的节点行也能连上。
- **运行时崩溃后重启**（[#274](https://github.com/arcships/rutis/issues/274)，[rutis-host](../guide/rutis-host.md#运行时结束时)）：`runtimes.node`、`runtimes.py`、`runtimes.bun` 新增可选字段 `restart`，决定运行时进程自己结束时怎么办：`"no"`（默认，和以前一样，它的行等待）、`"on-failure"`（等待后重新启动，它的行随之恢复；等待 1 秒起每次翻倍、最多 30 秒，运行满 60 秒后从 1 秒重来，5 分钟内重启 5 次后再结束就放弃并打印 `runtime <名字>: gave up after 5 restarts within 5 minutes`；数值固定，不能配置）、`"exit"`（卸载其他行后以新的退出码 3 退出，由进程管理器重启整个宿主）。`dev` 用同样的规则和默认值，`restart` 写在 `rutis.dev.json`。Go 运行时还没有这个设置。
- **运行中吊销身份**（[#273](https://github.com/arcships/rutis/issues/273)，[设计](../design-remote-runtime-dial-2026-10-14.md#五身份层)）：只在 Rust 库里，是将来的管理服务要调用的钩子。`rutis-bridge` 的 `Revocable::new(内层, revocations)` 包住一个 `Identity`（静态 link）或 `Admission`（接入点），`Revocations::revoke(&id)` / `revoke_all()` 在一切照常运行时吊销：只关闭以这个 id 接受的连接（其上进行中的调用失败一次，与断网相同），吊销前已路由的握手不再移交，之后的连接与 token 错误时一样被拒（403，接入点的 id 为关闭码 4003），拨号方按 `AuthRejected` 每 30 秒重试。其他对端、同一监听器上的其他连接、本机运行时不受影响。共享 token 的接入点吊销一个 id 只关这条连接，`revoke_all()` 等于收回 token。`Identity`、`Admission` 新增 `revocations()`，默认 `None`。rutis-host 没有对应的命令：它的 token 来自环境变量，运行中不能吊销（[连接节点](../guide/nodes.md#安全)）。

- **已发布的 Cordis 插件按原生规则互用服务，提供的服务自动投到 rutis**（[#428](https://github.com/arcships/rutis/issues/428)，[Cordis](../guide/cordis.md)）：`rutis.json` 里挂载的 Cordis 包（已发布、没有 `rutis.provides` 的也一样）在同一个 Node 运行时里按 Cordis 的规则互相使用服务，拿到对象本身；过去依赖别的行的行一直停在 `waiting for its services`。它们提供的服务不用声明就投到 rutis，别的运行时、节点和 Rust 按名字使用，方法取服务对象上的函数（自身和原型链上的，不含 `constructor`），按 `async` 调用；包里写了 `rutis.provides` 时按声明。同名服务已有别的提供者时后提供的那一行失败（装载后才提供的也一样，`run` 的状态行写明），错误写明双方：`service <名字> is already provided by <已有的一方>: row <行> cannot provide it too`。`rutis-host check` 对只可能由这类行提供的服务打印 `<服务>: may be provided at runtime by rows that do not declare all they provide (<行>, …)`，不再报 `cannot run: nothing provides …`；这一行和可能提供它的行里有 Cordis 行时再补 `; between Cordis rows of one runtime it resolves in Cordis`。叶子插件同样如此，见下一条。Rust 库：`rutis-bridge` 新增 `row_projection_of`、`ServiceEvents::announced`、`Projection::on_announced` / `service_keyed_occupied` / `take_refused`、`HostDispatch::provider`、`RowService::provided_by`、`RowSchema::announces` / `cordis`、`Projection::on_refused`；`rutis-loader` 新增 `Declared::announces`、`Supply::Announced`。
- **叶子插件提供的服务自动对外，`provides` 声明变为可选**（[#442](https://github.com/arcships/rutis/issues/442)，[插件 API](../guide/plugin-api.md#ctx)）：Node、Bun、Python、Go 四种 SDK 的 `ctx.provide(name, impl)` 提供的服务不用声明就投到 rutis，别的语言的插件按名字使用。方法取实现对象上的公开方法——JavaScript：自身和原型链上的函数（不含 `constructor`）；Python：不以 `_` 开头的可调用属性；Go：导出方法——都按 `async` 调用，字段不算方法。`provides` 写了仍然生效：把方法标成 `sync`、让 `rutis-host check` 在运行前知道谁提供什么；已有插件不用改。没有声明的服务在插件运行后出现，依赖它的行照常等它出现；`check` 对这类依赖报 `may be provided at runtime by …`，不算失败。重名时后提供的插件失败，错误写明双方。`rutis-host new` 的四种模板不再声明 `provides`，只留一句注释说明何时需要写。拨入实例（`runtimes.remote` 的 `instances`）里的行没有声明的服务只在该实例内可见（[连接节点](../guide/nodes.md#连进来的运行时)）。测试工具（`@arcships/rutis/testing`，Bun 下同一个；`rutis.testing`；Go 的 `rutistest`）同样不再要求声明，`service(name)` 按推断的方法调用，新增 `methods(name)`（Go：`Service.Methods()`）返回 rutis 看到的方法。

## 修复

- **监听的 link 应用后即已注册**（[#411](https://github.com/arcships/rutis/issues/411)）：`rutis-bridge` 的监听 link 过去在应用后另起的任务里才注册到监听器。同一监听器上已有接入点时，在这之前连进来的静态对端被当作不认识的凭据拒绝（403），拨号方按 `AuthRejected` 等 30 秒才重试；现在 `LinkPlugin` 应用完成时注册已在，注册失败（名字已被占用）仍是 `Stopped`。接入点按连接送达的顺序计先后：同一 id 的两个连接几乎同时送达时，过去可能把后到的算成先到。
- **同时登记的功能族被宣告成两次提供**（[#435](https://github.com/arcships/rutis/issues/435)）：`rutis-bridge` 的 `Peer::register` 先放入族的处理者、再另取一把锁记下这次提供的编号（`since`）；别的功能（另一线程）恰在两步之间登记时，它的宣告里这个族已经在、编号却还没有，按 0 发出，随后才是真正的编号。对端看来这个族被重新提供了一次：`peer:` 行随之重启，正在应用的行可能读不到刚撤下的 `PeerRows` 而停在失败。只在一端同时登记两个以上的族时出现（如同一个 link 既开宿主又导入服务）。现在编号和处理者一起放入，宣告里的族总带着自己的编号。
- **依赖在应用前被撤下的插件停在失败**（[#438](https://github.com/arcships/rutis/issues/438)）：插件的依赖已就绪、`apply` 已排上，运行前依赖被撤下时，`apply` 用 `require` / `require_as` 读它、原样返回读取的错误（`require(..)?`）会让插件停在 Failed；同一个提供者再提供时依赖没有换代，插件也不重试。宿主真的关闭或重开的那一刻，`peer:` 行读 `PeerRows` 会遇到这种情况，Node、Python、Bun、Go 的行读各自运行时的服务也一样。现在内核把这个错误与 `InjectUnsatisfied` 同样对待：这一代读取依赖确实失败过时插件回到等待，依赖回来后照常装载。
- **Python 运行时在宿主被 `kill -9` 后一直不退出**（[#192](https://github.com/arcships/rutis/issues/192)）：宿主被强制结束、插件的清理一直不返回时，Python 运行时到截止时间（`RUTIS_SHUTDOWN_TIMEOUT`）要在 stderr 写一行再以 1 退出；stderr 是通到宿主的管道，宿主没了这一行写不出去（BrokenPipeError），进程就留了下来。现在写不出也照样退出。Unix 才有这个问题，Windows 上运行时随宿主的 Job Object 结束。
- **Python 运行时 `listen:` 的会话因断网结束时打印 traceback**（[#434](https://github.com/arcships/rutis/issues/434)，[连接节点](../guide/nodes.md#别的机器上的语言运行时)）：控制方因断网心跳超时、连接被重置时，节点的 stderr 上过去是 websockets 库的日志和完整 traceback。现在打印一行 `rutis: session ended (<原因>); waiting for a controller`，例如 `rutis: session ended (heartbeat timeout); waiting for a controller`；被新连接接替时打印 `rutis: session ended (replaced by a new connection)`。断网、心跳超时、对端关闭不再打印 websockets 的日志，其他意外错误仍带 traceback 打印（以 `rutis: websockets:` 开头）。`dial:` 的状态行里，心跳超时的原因也从 `closed (1011): keepalive ping timeout` 改为 `heartbeat timeout`。

## 兼容

- **`rutis.json`**：格式仍是 1。`runtimes.node`、`runtimes.py`、`runtimes.bun` 新增可选字段 `restart`，以前的文件不用改、含义不变；用了它的文件 0.11 的 rutis-host 读不了。这三个运行时里写错字段时，错误列出的可用字段多了 `restart`。
- **退出码**：新增 3（`restart` 为 `"exit"` 的运行时结束，宿主已停止）。0、1、2 的含义不变。
- **Node 运行时协议**：`mount` 参数新增 `announce`、回复的 `features` 新增 `rows.announce`，`service` 通知对没有声明的服务带第四个参数 `{ row, methods }`，`rows.schema` 的回复新增 `announces`，Cordis 插件另有 `cordis`。只在双方都是 0.12 时启用：0.11 的宿主配 0.12 的 Node 运行时，或 0.12 的宿主配 0.11 的运行时，没有声明的服务都不投到 rutis，和 0.11 一样。
- **叶子插件**：没有声明的 `ctx.provide` 过去在 Go 里 panic（`Provides does not declare it`）、在别的运行时只在本进程可见、在测试工具里 `service(name)` 报“not declared in provides”；现在都对外。0.11 的宿主不发 `announce`，没有声明的服务仍不投过去；0.11 的运行时按声明，和以前一样；0.11 的 SDK 写的插件没有 `announces` 标记，`check` 把它的声明当作它提供的全部。`rows.schema` 与 Go 清单里的插件条目新增 `announces`。
- **`check` 的输出**：只可能由没有声明 `rutis.provides` 的 Cordis 行提供的服务，过去是 `cannot run: nothing provides …` 并以 1 退出，现在是一行 `may be provided at runtime by …`，以 0 退出；没有声明 `provides` 的叶子插件提供的服务同样。声明了 `provides` 的叶子插件，`check` 仍把声明当作它提供的全部。
- **Rust 库**：`rutis_loader::Declared` 新增公开字段 `announces`，用结构体字面量构造它的代码要补上这个字段（或用 `..Default::default()`）；`rutis_bridge::runtime::RowSchema` 新增字段 `announces`、`cordis`，同样。
- **凭据**：`rutis-host` 改为拨号和对端连进来时才读 `RUTIS_TOKEN_<节点>` / `RUTIS_TOKEN`；读到的值和以前相同（环境变量在进程内不变），只是节点行不必在启动时就存在。
