# rutis 0.23.0

[中文](0.23.0.md) · [0.22.0 release notes](0.22.0.en.md)

**0.23.0 is being prepared (2026-11-19).** These notes cover only what is merged (`origin/main` `8e9975de`, 2026-11-19). The version numbers and the persisted sample are in the release pull request, and the parts of the release gate a local machine can run have been run; the whole gate (the PR's `release-dry-run` and `release.yml` on the tag), the two-machine network smoke and the pre-release agent trial (#663) have not, and "Before the release" lists them at the end.

0.23 is the beta before 1.0: the session protocol goes from 4 to 5, a cancel is resolved exactly once by the callee (the new `ack` frame), an asynchronous call says on the wire whether its result is waited for (`awaited`), and a protocol-4 or older host, runtime, node or SDK is refused at the handshake, so one deployment upgrades together. The plugin API is still 3, `rutis.json`'s `format` is still 1, and no public Rust API is removed or renamed. Events and the loader fix the withdrawal and delivery order around a row ending or unloading, the event hot path and `instance_rows` are faster, and the evidence gains Kani's first verdicts, Swift 6 strict concurrency, the Kotlin `RutisApp` Fray cases and the `call-lifecycle` cancel-acknowledgement model. Read [migrating to 0.23](../migration-0.23.en.md) before upgrading.

## What is in this release

| Work | Issue | What this release has |
| --- | --- | --- |
| Session protocol 5: cancel acknowledgement | [#1099](https://github.com/arcships/rutis/issues/1099) | The `ack` frame; a cancel is resolved exactly once by the callee: a call cancelled while queued, while running, and an `await` cancelled while waiting are all acknowledged, and after the `ack` no `return`/`throw` follows for that call; a reply written before the cancel was read is the resolution and no `ack` follows; an `ack` whose entry a crossed reply already cleared is ignored; a reply after the `ack` ends the session with a protocol error (`response for unknown call`). The caller clears the cancelled entry on the `ack`, so a long session that keeps cancelling queued calls no longer keeps every entry until it ends. Specification §7, §8, `SESS-57`, `SESS-61`, `SESS-79`; the `specs/call-lifecycle` configurations `call-gap-ack`, `call-mut-ack-then-reply`, `relay-healthy` and `relay-mut-ack-then-reply`; all seven implementations (Rust, Node, Bun, Python, Go, Swift, Kotlin) and the shared malformed matrix's wrong-type `ack` case. |
| The asynchronous `awaited` signal | [#1098](https://github.com/arcships/rutis/issues/1098) | A call frame (`invoke`, `call`, `get`, `await`) gains an optional boolean `awaited`: `false` means fired and forgotten (the caller will not wait for this result before the call that made it finishes); absent or `true` means it will. It is meaningful only for asynchronous calls and is ignored when `sync: true`. The host counts a call in the wait graph only when it is `sync` or an asynchronous call whose result will be waited for; a call that says `awaited: false` is an entry, no longer a hop because it appears on a marked chain, and a forward keeps the original signal. The absent field keeps the conservative reading, so an old caller can still be refused by a false cycle; saying `false` is what removes the edge. Specification `SESS-83`, `SESS-7`, `SESS-66`, §14 G7; the `specs/cross-runtime-sync` configurations `async-policy-b` and `async-forgotten-policy-b`; all seven implementations know the field, and a runtime writes `false` where it knows nobody waits. |
| Large frames across messages | [#1361](https://github.com/arcships/rutis/issues/1361), [#1363](https://github.com/arcships/rutis/issues/1363) | Protocol 5 gains a `chunk` frame: the whole frame's JSON bytes are split into `transfer`, `seq`, `last` and base64 `data`, at most 8 MiB each; the receiver reassembles, parses and dispatches only after the last chunk, and drops an incomplete transfer on disconnect. The `hello` capability `chunked` is required on both ends; Rust, Node, Bun, Python, Go, Swift and Kotlin all implement and declare it. `max_transfer` (`RUTIS_MAX_TRANSFER`) defaults to 256 MiB and is configurable; over it the call fails with the configured limit. Real cross-language 17 MiB arguments and returns, single execution and mid-transfer disconnect are covered. |

| Service-name boundary for runtime rows | [#1040](https://github.com/arcships/rutis/issues/1040) | `SpawnPlugin::undeclared`, `Session::undeclared` and `Mount::undeclared` take an `UndeclaredPolicy`: the default `Publish` (as in Cordis), `Refuse`, and `Allow(names)`. A refused name is not published; its row fails with a `ProvideError` that names the name and the row, while the runtime and its other rows keep running; an announcement inside an instance belongs to that instance only. This is a new host API and does not change the default; `loader/announced-services` and the open-host guide are updated. |
| Event order around a row ending or unloading | [#1088](https://github.com/arcships/rutis/issues/1088), [#1133](https://github.com/arcships/rutis/issues/1133), [#1318](https://github.com/arcships/rutis/issues/1318), [#1327](https://github.com/arcships/rutis/issues/1327), [#1295](https://github.com/arcships/rutis/issues/1295) | `rows.ended` / `rows.unload` withdraw the row's entries before letting its queued emits go, and the session's emit queue waits for the withdrawal (#1133); the kernel withdraws the entries synchronously on the calling thread, so no dispatch sent after the reply sees an ended row (#1318); an emit a row's cleanup stack hands over during unload is kept until delivery, and one still queued when the session ends fails with the session-ended error (#1327); an unload's reply no longer overtakes the dispatch its cleanup emits (#1088); a session that ends wakes those waiting for its ordered queue, so an unload does not hang (#1088); a memory channel writes both directions' close reason before waking, so a replaced connection reads 4002 on Windows too (#1295). |

Numbers are in "Verification and models". |

## Behaviour changes

| Where | Before | Now |
| --- | --- | --- |
| A call cancelled while queued (protocol 4) | Dropped, no reply; the caller's cancelled-table entry stayed until the session ended | Dropped, the method never runs, argument references are released, the callee sends `ack`, and the caller clears the entry ([#1099](https://github.com/arcships/rutis/issues/1099)) |
| A call cancelled while running | Ran to the end; the callee replied as usual or dropped it, implementation by implementation, and the caller discarded a late reply | Runs to the end; the result is dropped, the callee sends `ack`, and no reply follows |
| An `await` cancelled while waiting | Dropped without a reply | Dropped and acknowledged |
| The reply was written before the cancel was read | That reply was the late reply, discarded by the caller | That reply is the resolution; no `ack` follows, and the caller discards the reply |
| A reply arrives after the `ack` | (No `ack` existed) | `response for unknown call`: the session ends with a transport error, and in-flight calls fail with `peer-gone` |
| The far end speaks protocol 4 | It worked | `incompatible session: the far end speaks protocol 4, this side 5: upgrade the far end`; the link stops and is not retried |
| The WebSocket subprotocol | A dialer could say `rutis.4` | Only `rutis.5`; `rutis.4` is refused as an older dialer |
| A fired-and-forgotten asynchronous call | Counted as waited for, so `SyncWaitCycle` was occasionally reported by mistake | A call whose frame says `awaited: false` is an entry and no longer a hop; an ordinary asynchronous call the runtime cannot classify still omits the field and is read as waited for |
| A call argument or return over 16 MiB | The sender refused it and the call failed | With `chunked` on both ends it is split and reassembled transparently; all seven implementations support it, and an earlier end that does not declare it keeps the old limit ([#1361](https://github.com/arcships/rutis/issues/1361), [#1363](https://github.com/arcships/rutis/issues/1363)) |
| A dispatch after a row ends | The session's withdrawal was asynchronous, so a dispatch that arrived after the reply could still select the ended row | The kernel withdraws the entries synchronously on the calling thread, so no dispatch after the reply sees the row ([#1318](https://github.com/arcships/rutis/issues/1318)) |
| An emit a cleanup hands over during unload | Dropped with the row's queued emits, while `rows.unload` said Ok | The cleanup's emit is kept until delivery and other rows hear it; one still queued when the session ends fails with the session-ended error ([#1327](https://github.com/arcships/rutis/issues/1327)) |
| A runtime row announces a service it did not declare | Always published by name (Cordis compatibility) | The default is still `Publish`; when the host sets `Refuse` or `Allow(names)`, a refused name is not published and only that row fails, naming the name ([#1040](https://github.com/arcships/rutis/issues/1040)) |
| A memory channel that is replaced | Could read `Ok(None)` instead of 4002 | Both directions' close reason is written before waking; Windows reads 4002 too ([#1295](https://github.com/arcships/rutis/issues/1295)) |

Other fixes:

- **Python reload**: editing a file to the same length in the same second made the reload read a stale `.pyc`; a timestamp-changed module's `.pyc` is now removed and compiled again. The `.pyc` path comes from `importlib.util.cache_from_source`, which also works on Python 3.15, where `__cached__` is gone ([#1080](https://github.com/arcships/rutis/issues/1080)).
- **dsh**: a YAML number with a base prefix followed by a sign no longer panics; an expression nested more than 64 levels reports an error instead of overflowing the stack ([#1080](https://github.com/arcships/rutis/issues/1080)).
- **Swift fixtures and SDK**: a cancel waits for the `ack`, not `return`; the session and app fixtures mark `dispatch`/`apply` `@Sendable`; `receive` unwraps one `Result`; Security's certificates and identity cross tasks in immutable boxes ([#1099](https://github.com/arcships/rutis/issues/1099), [#1273](https://github.com/arcships/rutis/issues/1273)).
- **Session conformance cases**: a far end that does not connect or answer is bounded, and stale offers and replacement timing no longer make a case fail by chance; each `grant_rollback` proptest case uses a new link ([#1080](https://github.com/arcships/rutis/issues/1080)).
- **Cross-version tests**: under protocol 5, 0.19–0.22 peers are refused by release generation; before 0.19 the old texts and the `rutis-bridge/peer` row are still asserted ([#1080](https://github.com/arcships/rutis/issues/1080)).

## Explicitly not guaranteed

- **1.0's long-term contract is not in this release**: no Rust API stabilisation process, no redesign beyond plugin API 3, and no format beyond `rutis.json` `format` 1. 0.23 is a beta, not 1.0.
- **Large frames are enabled between all seven implementations**: Rust, Node, Bun, Python, Go, Swift and Kotlin declare `chunked`; an earlier end that does not declare it keeps the original 16 MiB single-message limit with any end; `max_transfer` defaults to 256 MiB and exceeding it fails explicitly ([#1361](https://github.com/arcships/rutis/issues/1361), [#1363](https://github.com/arcships/rutis/issues/1363)).
- **Protocol 5 is verified only within this repository's seven implementations**: a protocol-4 or older host, runtime, node or SDK is refused at the handshake (`SESS-79`), and no protocol-4/protocol-5 session exists; a peer that has seen an earlier protocol-5 prerelease build fails a call carrying `awaited` under `SESS-66` and must be replaced with a 0.23 build (`SESS-81`).
- **These wait-graph cases are still not guaranteed** (`SESS-40`): a synchronous call that does not mark `sync` on the frame is outside the check and may deadlock; a call that says `awaited: false` but actually waits for its result loses the edge and may deadlock; cross-host cycles, the cost of reentrancy, a mixed-version wait graph, and exhausting the host's worker threads are not guaranteed.
- **Unknown fields are not an extension mechanism** (`SESS-69`): an old implementation fails that call under `SESS-66`; a new frame or a changed meaning needs a protocol version bump, and a new capability is used only when declared.
- **Formal coverage is not complete yet**: 479 current protocol rules in the tracker are unverified and 364 are only partly verified; the 219 register rows and the 10 handwritten `ECA` rows have not been re-extracted; the remaining gaps are tracked by [#776](https://github.com/arcships/rutis/issues/776) and [#1270](https://github.com/arcships/rutis/issues/1270)–[#1274](https://github.com/arcships/rutis/issues/1274). Kani has no verdict for the constructors' error paths, `parse_boot`, or the `&str` wrappers of `boot_meta`/`is_sha256`; dylib has no shuttle model; the 6 models in `rutis-host` and `rutis-loader` run in no workflow; Go has no controlled scheduling; `sync_cycles` still lacks a Kotlin column and `host_gone` still lacks one.
- **The service-announcement trust boundary**: `UndeclaredPolicy` defaults to `Publish`, so a host that sets no policy still publishes names a runtime did not declare, for Cordis compatibility. It is not a permission, authentication or security boundary; it is a host's policy for which names a runtime's rows may announce.
- **Events' explicit non-guarantees**: concurrent emits have no order, concurrent registration and dispatch have no order, the fate of a call in flight when an entry is withdrawn, and listener completion order (part of the 10 explicitly-not-guaranteed rows in [the guarantee register](../guarantees.en.md)).
- **Network smoke and agent trial**: the two-machine network smoke and the pre-release agent trial ([#663](https://github.com/arcships/rutis/issues/663)) have not run; the loopback smoke is in [the release guide](../release.en.md), section "0.23.0".

## Compatibility

- The session protocol is **5** (`ENDPOINT_PROTOCOL` in `crates/rutis-bridge/src/session/mod.rs`); protocol 5's `chunked` capability is declared by all seven implementations (Rust, Node, Bun, Python, Go, Swift and Kotlin); an earlier end that does not declare it never receives `chunk` frames and keeps the 16 MiB limit.
 a protocol-4 or older end is refused at the handshake, so no mixed session exists. The handshake adds no "required capability"; an absent `awaited` is read with the old semantics (waited for).
- The plugin API is still 3 and `rutis.json`'s `format` is still 1; the configuration gains no field, the persisted sample is copied from 0.22.0, and its expectations do not change.
- No public Rust API is removed or renamed, and the kernel's public API snapshot is unchanged. `rutis-bridge` gains `UndeclaredPolicy` and `rutis-loader`'s `Instance` gains the `rows` field: both are additions.
- A dylib plugin is rebuilt with 0.23.0's SDK, as with every release.
- npm, PyPI, Go, Swift and Kotlin take the train's 0.23.0; the Kotlin SDK keeps the train's version, and Maven Central is published by the rules of `release.yml` (the four secrets of the environment `maven`; the `maven` job skips when one is missing).

## Upgrading

Most plugins and hosts need no code change. Two things to do: upgrade the host and every runtime, node and SDK to 0.23 together (a protocol-4 peer is refused at the handshake); and change a tool that pins the WebSocket subprotocol to `rutis.5`. The behaviour changes to meet: a cancelled call is now acknowledged by the callee and gets no reply; an asynchronous call that says `awaited: false` is no longer treated as a wait edge; a dispatch after a row ends does not see the row; an emit a cleanup hands over during unload is delivered. A Swift plugin whose `apply` is defined in top-level code marks it `@Sendable` or moves it to a file of its own under the Swift 6 mode. See [migrating to 0.23](../migration-0.23.en.md) for each change.
