# rutis 0.12.1

[English](0.12.1.en.md) · [0.12.0 发布说明](0.12.0.md)

0.12.1 修复 `rutis-bridge` 的 `build::Exports`：导出类型所在的 crate 有 glob 导入成环时，生成器不结束，`cargo build` 卡住（[#459](https://github.com/arcships/rutis/issues/459)）。其余包没有改动，只为与列车对齐升到 0.12.1。

## 修复

- **glob 导入成环时 `Exports::generate()` 不结束**：crate 根用 `pub use m::*;` 重导出各模块、模块里又写 `use crate::*;`（或 `use super::*;`、更长的环）是常见写法，也是 Rust 允许的。生成器查一个名字时会沿每个 glob 往下找，却不记得哪些 `(模块, 名字)` 正在查，只靠 48 层的深度上限停下；只在标准 prelude 里的名字（`Result`、`Vec`、`String`）于是要在环里绕到底，每层分出与 glob 数相同的分支，构建脚本占满 CPU 一直跑下去。现在正在查的名字不再重入（与 rustc 的做法相同，这条路径上什么也没有，再回到 prelude），每个名字的结果在一次生成里只算一次。#459 的六模块布局从五分钟以上不结束变为生成器本身不到一秒。
- 同一轮检查补上的另外两处：互相指向的类型别名（`type A = B; type B = A;`，rustc 也拒绝）不再让生成器栈溢出，相关方法照常带构建警告省略；`#[path]` 指回正在读的文件的模块不再无限递归读取，跳过并给出构建警告。

## 发布包

以下包版本均为 **0.12.1**：crates.io 的 `rutis`、`rutis-bridge`、`rutis-loader`、`rutis-host`、`rutis-sdk`、`rutis-dylib`、`rutis-dylib-meta`、`rutis-dylib-launcher`；npm 的 `@arcships/rutis`、`@arcships/rutis-runtime`、`@arcships/rutis-bun`、`@arcships/rutis-host` 及五个平台包；PyPI 的 `rutis`、`rutis-host`；Go 模块 `github.com/arcships/rutis/go/rutis`（tag `go/rutis/v0.12.1`）；GitHub 发布页的 `rutis-host` 二进制。`rutis-cli` 仍独立发版。

## 兼容

- 与 0.12.0 完全兼容：没有 API、协议或配置变化，0.12.0 与 0.12.1 的宿主和运行时可以混用。没有环的 crate 生成的代码与 0.12.0 相同。
- 在 `build.rs` 里使用 `rutis_bridge::build::Exports` 的项目建议升级；其他用法可以留在 0.12.0。
- dylib：SDK 身份包含依赖树里的包版本。用 0.12.1 重新构建 SDK 和宿主后，0.12.0 时期编译的 dylib 插件要用新的 SDK 重新编译；继续使用原来的 SDK 构建包则不受影响。
