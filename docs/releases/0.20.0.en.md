# rutis 0.20.0

[中文](0.20.0.md) · [0.19.3 release notes](0.19.3.en.md)

0.20.0 lets a plugin write optional dependencies: `optional` beside `inject`, read with `ctx.get`, and the plugin runs without them. A row's `inject` counts as that row's declaration in all six languages, and rutis now gates and leases it for a runtime's rows. A service in the same process is the object itself in Go and Kotlin too, and the test tools take a plugin definition the plugin hands over. Unloading now runs cleanups and service withdrawals on one reverse stack, which is not compatible. Read [Migration to 0.20](../migration-0.20.en.md) before upgrading.

## Read this first: unload order (breaking)

A row's unload runs **one** stack: `provide` puts "withdraw this service" on it, `ctx.effect` and the cleanup `apply` returns put cleanups on it. Unloading runs it in reverse, one entry at a time, each withdrawal in the place it was registered ([#1010](https://github.com/arcships/rutis/pull/1010), design: [Unload order](../design-unload-order-2026-11-01.en.md)). All six languages (Go, Python, Bun, Kotlin, Swift, Node) behave this way.

- **A cleanup registered from a cleanup does not run**: all six write `rutis: row <row> is not active: cleanup is not registered` (Node: `plugin <plugin>`). Kotlin used to write that line and not run the cleanup either, Go, Python, Bun and Swift dropped it silently, and Node handed it to Cordis's disposals.
- **One cleanup cannot wait for another**: with one entry at a time, waiting for another cleanup (a promise the later one would resolve, say) waits for good.
- **Node no longer starts every cleanup at once**: `_unload` used to start them all with `Promise.all`.

Which cleanups read the service their row provides (registered before or after `provide`), what another row reads while this one unloads, and the 0.19-to-0.20 table for all six are in [Migration to 0.20, "Unload order"](../migration-0.20.en.md#unload-order-1010).

## Optional services

- **`optional` sits beside `inject`, and `ctx.get` reads it** ([#999](https://github.com/arcships/rutis/pull/999), design: [Optional dependencies](../design-optional-deps-2026-10-28.en.md)). A plugin that summarizes with `llm` when there is one and truncates the text otherwise used to have to put it in `inject`, and the row waited for it as long as the host did not have it. In `optional` the row starts as usual, does not sit in `waiting for` because of it, and `ctx.get('llm')` returns the empty value when it is not there (`undefined`, `None`; Go's `ctx.Get(name, &target)` returns `false, nil`; Swift `nil`, Kotlin `null`). A host service there when the row starts is leased in until the row stops; one that comes later needs the row restarted. A service another row in the same process provides follows that process's table at each `get`. The meaning is Rust's `Option<Arc<T>>`. The syntax per language is under [Optional services in the plugin API](../guide/plugin-api.en.md#optional-services).
- **`use` does not take `optional`**: a name only in `optional` gets the old line from `ctx.use`, `service llm is not available to this plugin, which does not declare it in inject: add 'llm' to its inject` (Go: `… in Inject: add "llm" to its Inject`); read an optional service with `ctx.get`, as Rust's `ctx.require` calls `Option<Arc<T>>` undeclared. `get` on a name declared nowhere says `service llm is not available to this plugin, which does not declare it: add 'llm' to its optional (or to its inject, if it cannot run without it)`.
- **One name in both lists fails the row**: `llm` in the plugin's `inject` and `optional` gives `llm is in both inject and optional; keep it in one`; in the row's `inject` and the plugin's `optional`, `llm is in the row's inject and the plugin's optional; keep it in one`.
- **`rutis-host check` prints `optional`**: a line `optional: ["llm"]` after `inject:` (none when empty), and an optional service nobody provides does not fail the check.
- `optional` needs rutis-host 0.20 or later: an older host does not know it, does not lease those names, and `get` keeps returning the empty value rather than failing.

## A row's `inject`, and runtime rows

- **A row's `inject` counts as that row's declaration, the same in all six languages** ([#1000](https://github.com/arcships/rutis/pull/1000), design: [A row's `inject` and `use` checking declarations first](../design-declared-services-2026-10-29.en.md)). What `use` may read is the plugin's `inject`, the row's `inject`, and the names the plugin provides now; `get` adds the plugin's `optional`. Two places loosen: Go, Swift and Kotlin used to answer `not-declared` for a name in the row's `inject`, and now get the object itself when this process has it, or the proxy when it was leased in; and a plugin reading what it provides now gets that object from `use` and `get` alike (after the withdrawal it is undeclared again).
- **One place tightens: a plugin declares what it uses** (same design). In Node, Bun and Python, `use` used to look in the process's service table first and only then at the declarations, so a plugin that declared a name in neither its `inject` nor its row's `inject` got it whenever another row in that process happened to declare it — what it got depended on what else was loaded. `use` and `get` now check the declarations first, and such a plugin gets `service llm is not available to this plugin, which does not declare it in inject: add 'llm' to its inject`. This is what [#676](https://github.com/arcships/rutis/issues/676) asks for, not a regression; what to change is in [Migration to 0.20](../migration-0.20.en.md#use-checks-declarations-first-1000).
- **A runtime row is gated and leased through its row `inject`** ([#1001](https://github.com/arcships/rutis/pull/1001), design: [A runtime row's row `inject`](../design-row-inject-gate-2026-10-31.en.md)). When a service in the row's `inject` comes from the host or another process and this process does not have it, Bun, Python, Go, Swift and Kotlin rows used to start anyway and fail `use` with `service llm is not available`, while a Node row showed as running in rutis and in fact sat in the Cordis gate inside the process. All six now agree: `chat: waiting for llm (no row provides it)` (with `; did you mean <name>?` in the brackets when a close name exists), which is what `rutis-host check` always said; the row starts when the service arrives and the plugin gets it, stops when the provider goes and starts again when it comes back, and adding `inject` to a row restarts it once. A name the service catalog does not share (one an application registers as a Rust type) is neither gated nor leased, exactly as before, as [Migration to 0.20](../migration-0.20.en.md#a-runtime-rows-row-inject-1001) says.

## Services in the same process

- **Go: an interface, `any` and a matching function field get the provider's object itself** ([#1015](https://github.com/arcships/rutis/pull/1015), design: [Go: the provider's object itself in this process](../design-go-local-objects-2026-11-01.en.md)). Two Go plugins in one process used to pass objects only through package-level variables: `ctx.Use` took a struct of function fields or a `*advanced.Service`, an interface target said `use hello: the target must point to a struct of function fields or a *advanced.Service, not rutis.Greeter`, and a field whose type was exactly the provider's method but did not end in `error` said `use canvas: field Draw: func(string) string must return an error last`. Now a target that can hold this process's provider object (an interface it implements, its own type, `any`) gets that object, and calls are plain Go calls; an `any` target with a provider in another process gets its `*advanced.Service`. A non-empty interface target only holds in this process: across processes it says `use workspace: editor.Workspace is an interface, which only a service provided in this process fills: for one of another process, use a struct of function fields or *advanced.Service`. See [Go plugins: use a service](../guide/go-plugin.en.md#3-use-a-service).
- **Kotlin: `use` gives this process's object first** ([#1006](https://github.com/arcships/rutis/pull/1006)). `ctx.use(name, type)` used to take the proxy table first and fail with an `IllegalArgumentException` when the interface was not marked `@RutisClient` (`<type> has no proxy: annotate it @RutisClient and apply the rutis-ksp processor`), and only then look at this process's object — even when the provider was right there and implemented the interface. It now looks at this process's object first and returns it when it implements `type`; `@RutisClient` is needed only for a proxy (this process's object does not implement `type`, a far or host service). An interface used only in this process needs no annotation any more.

## Test tools

- **A plugin definition a test double received can be handed to `load`** ([#1004](https://github.com/arcships/rutis/issues/1004), [#1008](https://github.com/arcships/rutis/pull/1008), [#1012](https://github.com/arcships/rutis/pull/1012), design: [Test tools: `load` mounts a definition the plugin under test hands over](../design-test-tool-definition-load-2026-11-01.en.md)). When the plugin hands the result of `definePlugin` to a service the test provides, the test can now hand that value to `load`, and it runs as a row in the runtime that made the definition: config validation and defaults, `inject` gating, service announcements, listeners going with the row, unloading — all as `load(file)`. Before, that value could not be handed over at all: the session on the test's side did not declare `plugins`, so the plugin's call handing the definition over failed with `… cannot send a plugin definition: the far end does not accept plugin definitions (it did not declare the capability plugins)`. The row id follows `load(file)` too: the definition's name when `id` is not given, with `-2` on a clash; an explicit `id` that is taken fails with `a row <id> is loaded already`. Loading one definition twice makes two rows, each unloaded on its own; the source row ending does not take this row with it — the test (or the test tool at the end of the test) unloads it. A forged handle fails with `PluginTestError: load needs a plugin definition a test double received`. The Python, Go, Swift and Kotlin test tools always worked this way.
- **TypeScript and Bun: a timeout inside `load` no longer keeps the test run alive** ([#997](https://github.com/arcships/rutis/issues/997), [#1017](https://github.com/arcships/rutis/pull/1017)). When a test timed out before `load` had its host up, the `load` used to keep going: once the host was up that call held the process, while the test that started it had ended and its `after` hook would never run, so `npm test` hung until it was killed from outside. A test ending (a timeout included) now abandons the `load` in flight: `rutis-host` is stopped, the rows and services it loaded are taken down, and the next `load` starts a host again. On Node 22 the cleanup at the end of a test still holds the process, so the remaining tests in the file are not cancelled.
- **Bun: the hook at the end of a test registers no hooks** ([#994](https://github.com/arcships/rutis/issues/994), [#1011](https://github.com/arcships/rutis/pull/1011)). The cleanup at the end of a test (unloading the host and so on) still holds the process, but no longer registers `after` / `onTestFinished` from inside that hook: a hook registered in a hook never runs, and Bun should not take hooks from a hook — calls started there used to be mixed into later tests.
- **Python: a fake service whose name is taken fails only that `load`** ([#995](https://github.com/arcships/rutis/issues/995), [#1007](https://github.com/arcships/rutis/pull/1007)). The test's services used to be provided by the test plugin itself, so a name the host already had (say `rutis/sessions`) failed that plugin; after it failed, restarted and failed again, `rutis-host test` was gone and every later `load` and unload said `service rutis-host/test is not available`. Each service is now a row of its own, `rutis-test/<name>`, and the clashing `load` fails with that row's status — `rutis-test/rutis/sessions: rutis/sessions is already provided by the host` — while the same host serves the tests after it. The same problem in Node and Bun was fixed in 0.19.3 ([#993](https://github.com/arcships/rutis/pull/993)).

## Connections and runtime processes

- **A far end that stopped reading no longer holds up other clients** ([#1005](https://github.com/arcships/rutis/issues/1005), [#1009](https://github.com/arcships/rutis/pull/1009)). When a far end stopped reading (a terminal UI suspended, a slow link), the thread sending a frame used to sit in the channel's write; and since the session's event table changes when a client attaches (a listener is registered), that synchronous write landed on the attaching thread, so other clients in the same process could not start. A session now has a writer thread of its own: calls, replies and releases queue their frames in order and return, and the blocking falls on that writer. The backlog a host allows is an option it turns on, `SessionOptions::outbound_limit`, unbounded by default — a slow far end holds up only its own session and no events are dropped; with a limit set, the session ends with `the far end is not reading: N messages, B bytes waited for it`. `rutis.json` does not set it; `rutis-host/dial`, `rutis-host/listen` and `sessions.open(far)` use the default. Frames still queued when a session ends are dropped with it.
- **A Python runtime exits within its deadline when the host is gone** ([#985](https://github.com/arcships/rutis/issues/985), [#1014](https://github.com/arcships/rutis/pull/1014)). The Python runtime's cleanup deadline is armed by a timer thread: when that thread cannot start (no threads left in the process, possible on a loaded machine) nothing was left to end the process, and it stayed for good. It now exits with 1 at once, saying why — a process with no deadline is past it already. The same for `rutis-host test` with a Python runtime: when the runtime never answers, the test now fails within its hang guard and prints what the runtime was doing (whether the process is still there, which calls into rows have not returned) instead of hanging for ever.
- **`Process::mount` has a limit for the runtime process's greeting** (same #985, [#1014](https://github.com/arcships/rutis/pull/1014)). A runtime that started but never greeted used to make it wait for ever. It is 30 s now (`rutis_bridge::runtime::GREETING`, the one constant rutis-host's `SpawnPlugin` uses), `Mount::greeting` changes it, and `Duration::MAX` means no limit (a process stopped at its first line for a debugger); with no greeting in time it fails with `Error::Transport`, `the runtime process <name> started but did not greet within <n>s`, and ends that process. `Mount` therefore has one more public field, `greeting`; see [Migration to 0.20](../migration-0.20.en.md#the-greeting-limit-of-a-runtime-process-1014).
- **A runtime that ran and then ended is no longer reported as never having started** ([#1023](https://github.com/arcships/rutis/issues/1023), [#1024](https://github.com/arcships/rutis/pull/1024)). `rutis-host` waits for its three local runtimes — Node, Bun, Python — one after another when it starts, and exits with 1 when it reaches one that is gone. It used to say the runtime did not start whether or not it had run: `rutis-host: the node runtime did not start: runtime ended: the process exited with exit status: 7`, and one whose process a plugin exited or that crashed before its turn was reported the same way. Now it says which: one that ran (was ready) and then ended has ended, `rutis-host: the bun runtime ended: exited with exit status: 7` (`exited with signal: 9 (SIGKILL)` for a process killed by a signal); one that never was ready still did not start, `rutis-host: the py runtime did not start: the runtime ended before it greeted: the process exited with exit status: 1`. Only those three runtimes are in that order; the Go and Swift runtimes start through their own `runtimes.go.start` / `runtimes.swift.start`, and the host's startup does not wait for them. The exit code and the unloading of the rows and runtimes already started are unchanged. See [rutis-host, "While the host starts"](../guide/rutis-host.en.md#while-the-host-starts).

## Memory and diagnostics

- **Each instance holds less, and closing instances keeps no peak capacity** ([#979](https://github.com/arcships/rutis/issues/979), [#1016](https://github.com/arcships/rutis/pull/1016); the numbers and the breakdown are in [An instance's footprint](../performance-instance-footprint-2026-11-02.en.md)). Each row has a monitor task, and the rare "the row stops itself" branch is now boxed (`Box` is allocated only when a row really stops itself): the future goes from 1,872 B to 344 B, about 13.4 KiB less per instance of 8 rows. In a release build with 1000 instances: 63.3 KiB to 50.9 KiB per instance (−20%), and 71.5 KiB to 59.1 KiB with event listeners (−17%); the residue after closing 1000 instances goes from 6,001,908 B to 22,708 B. `close_memory` is tightened into a resource baseline: it fails when an instance, the closing peak or the residue after closing goes over its threshold, and runs once a night in a release build.
- **A row waiting for the old name `loader` is no longer told to annotate a type** ([#996](https://github.com/arcships/rutis/issues/996), [#1013](https://github.com/arcships/rutis/pull/1013)). The loader provides its own Rust handle `Loader` into the context, and the type name derives to `loader` by the default rule, so a row still asking for the old name was told "this Rust service is not exported: add `#[rutis::service]` to its impl" — advice that does not apply: the handle is not a service someone forgot to annotate. A handle provided by rutis's own plugins is no longer a candidate, so the row's status is back to `waiting for loader (no row provides it)`, as `rutis-host check` says with `cannot run: nothing provides loader`. An unannotated Rust service the application provides still gets that hint.

## Behaviour changes

| Where | Before | Now |
| --- | --- | --- |
| Cleanups and service withdrawals when a row unloads | The five withdrew before the cleanups; Node started every disposal at once | One reverse stack, one entry at a time, each withdrawal where it was registered |
| What `use` and `get` may read | The plugin's `inject` (the row's `inject` counted only in Node, Bun and Python, whose `use` also looked in the table first) | The plugin's `inject` ∪ the row's `inject` ∪ what the plugin provides now; `get` adds `optional` |
| A plugin declaring a name in neither, another row in the process declaring it | Node, Bun and Python got it | `not-declared` |
| A plugin reading what it provides (`use`, `get`) | Bun and Python's `use` got it, Node's only after `apply`; `get` and Go, Swift and Kotlin's `use` said `not-declared` | The object itself while it provides it, `not-declared` after the withdrawal |
| A service in a runtime row's `inject` that is not there (Bun, Python, Go, Swift, Kotlin) | The row started, `use` said `unavailable` | The row waits: `waiting for <name>` |
| The same, with the provider withdrawn | The row kept running | The row stops and starts again when it comes back |
| Go `ctx.Use` with an interface, `any` or a matching function field | "must point to a struct of function fields …" | The object itself in this process; `any` across processes gives `*advanced.Service` |
| Kotlin `use` of an interface without `@RutisClient`, provider in this process | `has no proxy: annotate it @RutisClient …` | The object itself |
| TypeScript and Bun tests: a double's definition handed to `load` | Could not be handed over at all (`… the far end does not accept plugin definitions …`) | Mounted as a row |
| TypeScript tests: a timeout inside `load` | `npm test` hung until killed | That `load` is abandoned, the next one starts a host |
| Python tests: a fake service's name is taken | `rutis-host test` gone, every later `load` said `service rutis-host/test is not available` | Only that `load` fails |
| A far end that stopped reading | The sending thread sat in the write; other clients in the process could not start | Frames queue; the block falls on the session's writer thread |
| Frames not written when a session ends | None: a frame went into the channel when it was made | Dropped with the session |
| The Python runtime's deadline timer thread cannot start | The process stayed for good | It exits with 1 at once |
| `Process::mount` with a runtime that started but never greeted | Waited for ever | Fails after 30 s (or the limit set), and the process ends |
| `rutis-host` starting, with a runtime that ran and then ended before its turn | `the <name> runtime did not start: runtime ended: the process exited with exit status: N` | `the <name> runtime ended: exited with exit status: N` (a signal: `exited with signal: 9 (SIGKILL)`) |
| An instance of 8 rows, resident (release, 1000 of them) | 63.3 KiB | 50.9 KiB |
| Residue after closing 1000 instances | 6,001,908 B | 22,708 B |
| Why a row waiting for the old name `loader` waits | It was told to add `#[rutis::service]` to a Rust service | `waiting for loader (no row provides it)` |

## Compatibility

- The session protocol is still 4, `rutis.json`'s `format` is still 1, and the plugin API version is unchanged: no new handshake limit between a host, a runtime and an SDK. Unload order and `use`'s declared set live in each runtime, so mixing in an older runtime package leaves that one on the old behaviour.
- The new forms need tools of the same version: `optional` needs rutis-host 0.20 or later; handing a double's definition to `load` needs `@arcships/rutis` and the runtime package at the same version (an older SDK says `load needs a plugin made with definePlugin`, an older runtime package fails at the call handing the definition over: `cannot send a plugin definition: the far end does not accept plugin definitions (it did not declare the capability plugins)`).
- dylib plugins are rebuilt with the 0.20.0 SDK, as with every release.
