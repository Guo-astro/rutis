# rutis 0.15.0

[中文](0.15.0.md) · [0.13.0 release notes](0.13.0.en.md)

0.15.0 brings two new languages and app hosting: macOS plugins in Swift, plugins in Kotlin, and iOS and Android apps that offer what they and their device can do to rutis as ordinary rutis plugins, the app only starting and stopping the connection. A Rust service marked `#[rutis::service]` on its type is available to every language. 0.14 was not released on its own; its work (the Swift and Kotlin SDKs, `restart` for the Go runtime) is in this release. Upgrading needs almost no code changes; see [migrating to 0.15](../migration-0.15.en.md).

## New

- **The Swift SDK and macOS plugins** ([#386](https://github.com/arcships/rutis/issues/386), [#387](https://github.com/arcships/rutis/issues/387), [write a Swift plugin](../guide/swift-plugin.en.md)): a plugin is compiled into a binary, and a binary is one runtime process in the host; `runtimes.swift` in `rutis.json` is written like `runtimes.go` (`start`, `idle`, `restart`) and by default starts a binary when a row uses it. `rutis-host new --lang swift`, `dev` and `check` support Swift. For capabilities that need the user's permission, such as calendars and reminders, the prompt belongs to the plugin binary.
- **The Kotlin SDK** ([#390](https://github.com/arcships/rutis/issues/390)): the plugin API, unified events, values and test tools as in the other languages; the KSP processor `rutis-ksp` generates the method tables and proxies at compile time, with no reflection at run time. Published to Maven Central for the first time.
- **App hosting on iOS and Android** ([#389](https://github.com/arcships/rutis/issues/389), [#391](https://github.com/arcships/rutis/issues/391), [Swift apps](../guide/swift-app.en.md), [Android apps](../guide/kotlin-app.en.md)): the plugins are compiled into the app; the app starts and stops the connection with `RutisApp` and observes its state, and rutis loads, configures and unloads the plugins as its configuration says. Either side may connect: the app dials a listener of rutis (a remote runtime's `listen` and `instances`, one instance per device), or the app listens and rutis dials it. A remote runtime's `language` accepts `"swift"` and `"kotlin"` / `"kt"`.
- **Sample plugins** ([#388](https://github.com/arcships/rutis/issues/388)): `contacts`, `notify` and `device` for Android (`kotlin/rutis/android-sample`), and an iOS sample app; permission prompts and denial are checked on simulators and emulators, and the guides have a real-device checklist.
- **Mark Rust services `#[rutis::service]`** ([#510](https://github.com/arcships/rutis/issues/510), [embedding in a Rust application](../guide/rust-host.en.md#mark-the-type-rutisservice)): mark a service's `impl` and provide it as usual, and the rows of every language call it by name, built-in and dylib plugins alike, with no `build.rs` list. The macro lives in the new crate `rutis-macros`, re-exported by `rutis`, so nothing is added to `Cargo.toml`. `rutis-host types` writes TypeScript declarations from a crate.
- **`restart` for the Go runtime**: `runtimes.go` takes `restart` (`"no"`, `"on-failure"`, `"exit"`), as Node, Python and Bun do.
- **`rutis-host check` checks the plugin API of binaries**: a Go or Swift binary below plugin API 3 (built with an SDK older than rutis 0.13) is an error saying to rebuild it.

## Fixes

- **A local runtime has 30 s to greet**: counted from starting the process, interpreter and JVM start-up included, so slow but healthy machines (several runtimes starting at boot, small boards, a cold JVM) no longer see `did not greet in time`. A process that exits still fails at once; network links keep 10 s (#582).
- **Dialing on Bun 1.4.4**: an access point refusing the upgrade fails the dial at once, and a rejected certificate is reported as `auth-rejected`, instead of waiting for the deadline or being retried; older Bun versions are unaffected (#583).
- **Events and synchronous waits**: the Node runtime stays non-reentrant; listener calls it holds during a synchronous wait run in order once the wait ends, and a same-name emit on the fast path queues behind them. On reentrant runtimes (Python, Bun), an emit listener run on top of a wait that calls back into the waiting chain used to hang; it is now refused with `SyncWaitCycle` and the rest completes (#520, #527, #535, #557, #561). Runtimes take emit replies in frame order; when a row unloads its queued emits are dropped, so a filter that never answers no longer blocks later emits (#511, #513, #564). When a Rust application calls a service synchronously from a plain thread and an emit arrives during the wait, that emit no longer panics (`no reactor running`) or is dropped (#579).
- **Marked services**: a marked value is served by the build that provided it, so a dylib plugin rebuilt at the same version reloads without a version bump; calls by name pick read interceptors by the calling row; `check()` gates the entry by name; the macro handles `#[cfg]`, lifetimes and `Self` (#522, #531, #534, #555, #558, #560).
- **Kotlin apps**: writes on a listening connection have a deadline and no longer block reads, heartbeats or `stop()`; a `bail` dispatched through rutis on the Android main thread is refused (emit still works); dialing heartbeats time out as configured; an unloaded row can no longer provide services (#521, #556). `kotlinx-serialization-json` is an api dependency, so apps using `schema` need not add it (#553).
- **Swift apps**: `RutisApp`'s start and stop take effect in call order; a listening `stop()` returns once the port is released, so a `start()` right after (back from the background) no longer finds it in use; with port 0, every start reuses the port the first one got; stopping closes every dialed connection (#519, #532, #554, #562).
- **Go and Swift runtimes**: a runtime that does not stop on a restart is killed after `RUTIS_SHUTDOWN_TIMEOUT` plus 2 s, and the next one starts only once it is gone; a failed start shows as stopped with why and is tried again only when its file changes or on `restart`; a restart whose new binary cannot be read keeps the old one running; `rutis-host dev` keeps the previous build when a restart fails (#524, #563, #565, #566). Go's `Provide` and `On` no longer panic on an unloaded row (#526, #532).
- **Closing a session on macOS**: when the host closes a session without exiting, a local runtime always reads the end and exits after its cleanup deadline (#528, #533).
- A service a connected-in runtime provides without declaring it now reaches the other rows of its instance (#506).

## Tests and quality

- **Cross-version meetings work again** (`bridge/cross-version-meetings`): the gate's cross-version tests meet 0.13.0; both ends declare `events-v2`, plugins call each other and events cross both ways. Releases before 0.13 are still refused at the handshake (`events/old-peer-refused`).
- **Tests that need system permissions or devices run locally** (#514): the macOS permission prompts and the tests on iOS and Android simulators and emulators are not run in CI but by the maintainers on their own machines; CI runs every other test as before.
- No more reserve-then-release ports: child processes bind `:0` themselves and report the address, fixing an intermittent failure on Windows (#455).

## Compatibility

- **Almost no code changes** (the one exception: for an error of a `build.rs` export that is a struct with one field, `code` is now the type name). `format` of `rutis.json` stays 1 and old files read as before; the plugin API stays 3 and the session protocol versions are unchanged. 0.13 and 0.15 hosts, runtimes and nodes can be mixed.
- In `rutis-loader` the Go runtime types are aliases of generic types (`GoResolver` = `BinaryResolver<Go>` and so on), and existing code compiles as before; `cargo semver-checks` reports three of them as removed, a false alarm. `session::Dispatch` and `peer::Handler` each gained a method with a default implementation. The behaviour changes of Go and Swift runtime starts and restarts and of the local greeting deadline are there too. Details in [migrating to 0.15](../migration-0.15.en.md).
- For authors of runtimes and test tools: take emit replies in frame order; the events expectations file has a few new keys. See [migrating to 0.15](../migration-0.15.en.md#events).
