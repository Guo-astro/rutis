# rutis 0.15.0

[中文](0.15.0.md) · [0.13.0 release notes](0.13.0.en.md)

0.15.0 brings two new languages and app hosting: macOS plugins in Swift, plugins in Kotlin, and iOS and Android apps that offer what they and their device can do to rutis as ordinary rutis plugins, the app only starting and stopping the connection. A Rust service marked `#[rutis::service]` on its type is available to every language. 0.14 was not released on its own; its work (the Swift and Kotlin SDKs, `restart` for the Go runtime) is in this release. Upgrading needs no code changes; see [migrating to 0.15](../migration-0.15.en.md).

## New

- **The Swift SDK and macOS plugins** ([#386](https://github.com/arcships/rutis/issues/386), [#387](https://github.com/arcships/rutis/issues/387), [write a Swift plugin](../guide/swift-plugin.en.md)): a plugin is compiled into a binary, and a binary is one runtime process in the host; `runtimes.swift` in `rutis.json` is written like `runtimes.go` (`start`, `idle`, `restart`) and by default starts a binary when a row uses it. `rutis-host new --lang swift`, `dev` and `check` support Swift. For capabilities that need the user's permission, such as calendars and reminders, the prompt belongs to the plugin binary.
- **The Kotlin SDK** ([#390](https://github.com/arcships/rutis/issues/390)): the plugin API, unified events, values and test tools as in the other languages; the KSP processor `rutis-ksp` generates the method tables and proxies at compile time, with no reflection at run time. Published to Maven Central for the first time.
- **App hosting on iOS and Android** ([#389](https://github.com/arcships/rutis/issues/389), [#391](https://github.com/arcships/rutis/issues/391), [Swift apps](../guide/swift-app.en.md), [Android apps](../guide/kotlin-app.en.md)): the plugins are compiled into the app; the app starts and stops the connection with `RutisApp` and observes its state, and rutis loads, configures and unloads the plugins as its configuration says. Either side may connect: the app dials a listener of rutis (a remote runtime's `listen` and `instances`, one instance per device), or the app listens and rutis dials it. A remote runtime's `language` accepts `"swift"` and `"kotlin"` / `"kt"`.
- **Sample plugins** ([#388](https://github.com/arcships/rutis/issues/388)): `contacts`, `notify` and `device` for Android (`kotlin/rutis/android-sample`), and an iOS sample app; permission prompts and denial are checked on simulators and emulators, and the guides have a real-device checklist.
- **Mark Rust services `#[rutis::service]`** ([#510](https://github.com/arcships/rutis/issues/510), [embedding in a Rust application](../guide/rust-host.en.md#mark-the-type-rutisservice)): mark a service's `impl` and provide it as usual, and the rows of every language call it by name, built-in and dylib plugins alike, with no `build.rs` list. The macro lives in the new crate `rutis-macros`, re-exported by `rutis`, so nothing is added to `Cargo.toml`. `rutis-host types` writes TypeScript declarations from a crate.
- **`restart` for the Go runtime**: `runtimes.go` takes `restart` (`"no"`, `"on-failure"`, `"exit"`), as Node, Python and Bun do.
- **`rutis-host check` checks the plugin API of binaries**: a Go or Swift binary below plugin API 3 (built with an SDK older than rutis 0.13) is an error saying to rebuild it.

## Fixes

- A service a connected-in runtime provides without declaring it now reaches the other rows of its instance (#506).
- Event order: runtimes take emit replies in frame order, and the host always answers an emit with a plain value; the Node runtime starts emit-mode listener calls in frame order also during a synchronous wait (#511, #513, #520). Plugin code is unchanged, and 0.13 hosts and runtimes connect as before.
- Fixes from the app hosting review: the Swift and Kotlin `RutisApp` start and stop in call order, listening has an upgrade deadline, and writes have a deadline and do not block reads or heartbeats (#519, #521); a Go or Swift runtime that ends before supervision starts is still handled as `restart` says (#518).

## Tests and quality

- **Cross-version meetings work again** (`bridge/cross-version-meetings`): the gate's cross-version tests meet 0.13.0; both ends declare `events-v2`, plugins call each other and events cross both ways. Releases before 0.13 are still refused at the handshake (`events/old-peer-refused`).
- **Tests that need system permissions or devices run locally** (#514): the macOS permission prompts and the tests on iOS and Android simulators and emulators are not run in CI but by the maintainers on their own machines; CI runs every other test as before.
- No more reserve-then-release ports: child processes bind `:0` themselves and report the address, fixing an intermittent failure on Windows (#455).

## Compatibility

- **No code changes.** `format` of `rutis.json` stays 1 and old files read as before; the plugin API stays 3 and the session protocol versions are unchanged. 0.13 and 0.15 hosts, runtimes and nodes can be mixed.
- In `rutis-loader` the Go runtime types are aliases of generic types (`GoResolver` = `BinaryResolver<Go>` and so on), and existing code compiles as before; `cargo semver-checks` reports three of them as removed, a false alarm. `session::Dispatch` and `peer::Handler` each gained a method with a default implementation. Details in [migrating to 0.15](../migration-0.15.en.md).
- For authors of runtimes and test tools: take emit replies in frame order; the events expectations file has a few new keys. See [migrating to 0.15](../migration-0.15.en.md#events).
