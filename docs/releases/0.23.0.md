# rutis 0.23.0

[English](0.23.0.en.md) · [0.22.0 发布说明](0.22.0.md)

**0.23.0 发布准备中（2026-11-19）。** 本稿只写已合并的改动（`origin/main` `8e9975de`，2026-11-19）。版本号与持久化样本已在发布 PR 里，发布门里能在本机跑的部分已跑过；整套发布门（PR 上的 `release-dry-run` 与 tag 上的 `release.yml`）、两台机器的网络冒烟和发布前的 agent 试用（#663）还没做，文末「发布前还要做」列出。

0.23 是 1.0 前的 beta：会话协议从 4 升到 5，取消由被调方恰好结算一次（新的 `ack` 帧），异步调用在帧上说明它的结果会不会被等待（`awaited`），0.22 及更早的宿主、运行时、节点和 SDK 在握手时被拒，同一部署必须一起升级；插件看得到的 API 仍是 3，`rutis.json` 的 `format` 仍是 1，Rust 公开 API 不删除、不改名。事件与 loader 修了行结束、卸载期间的撤表与投递顺序，事件热路径与 `instance_rows` 做了性能改造；形式化证据补上 Kani 的第一批结论、Swift 6 严格并发、Kotlin `RutisApp` 的 Fray 用例，以及 `call-lifecycle` 的取消确认模型。升级前看[迁移到 0.23](../migration-0.23.md)。

## 行为变化

| 位置 | 以前 | 现在 |
| --- | --- | --- |
| 排队中被取消的调用（协议 4） | 丢掉，不回复；调用方的取消表项留到会话结束 | 丢掉，方法不运行，参数引用归还，被调方发 `ack`，调用方清掉表项（[#1099](https://github.com/arcships/rutis/issues/1099)） |
| 运行中被取消的调用 | 跑到结束；被调方按各实现决定照常回复或丢掉，调用方丢弃迟到回复 | 跑到结束；结果被丢弃，被调方发 `ack`，不再有回复 |
| 等待中的 `await` 被取消 | 丢掉，不回复 | 丢掉并确认 |
| 回复在读到取消之前已经写出 | 那个回复是迟到回复，被调用方丢弃 | 那个回复就是结算，不再发 `ack`，调用方丢弃该回复 |
| `ack` 之后又收到回复 | （没有 `ack`） | `response for unknown call`：会话以传输错误结束，在途调用以 `peer-gone` 失败 |
| 对端说协议 4 | 可以通信 | `incompatible session: the far end speaks protocol 4, this side 5: upgrade the far end`，链路停下，不重试 |
| WebSocket 子协议 | 拨号方可以写 `rutis.4` | 只认 `rutis.5`；`rutis.4` 按更旧的拨号方被拒 |
| 发出即不管的异步调用 | 仍按“会等”记等待边，偶发误报 `SyncWaitCycle` | 帧上写 `awaited: false` 的调用记为入口，不再被当成一跳；运行时无法判断的普通异步调用仍缺省这个字段，按“会等”处理 |
| 超过 16 MiB 的调用参数或返回值 | 发送端超限拒绝，调用失败 | 双方声明 `chunked` 时自动切片、重组后照常调用/返回；七种实现都支持，更早版本的对端没有声明时仍按原上限失败（[#1361](https://github.com/arcships/rutis/issues/1361)、[#1363](https://github.com/arcships/rutis/issues/1363)） |
| 行结束后的分发 | 会话撤表是异步的，回复之后到达的分发仍可能选中已结束的行 | 内核在调用线程上同步撤表，回复之后的任何分发都看不到这一行（[#1318](https://github.com/arcships/rutis/issues/1318)） |
| 卸载时清理交出的 emit | 随这一行排队的 emit 一起丢掉，`rows.unload` 却是 Ok | 清理交出的那条保留到投递，别的行听得到；会话结束时仍未投递的以会话结束的错误失败（[#1327](https://github.com/arcships/rutis/issues/1327)） |
| 运行时行宣告一个没声明的服务名 | 一律按名字发布（Cordis 兼容） | 默认仍是 `Publish`；宿主设了 `Refuse` 或 `Allow(names)` 时，被拒绝的名字不发布，只有那一行失败并写明名字（[#1040](https://github.com/arcships/rutis/issues/1040)） |
| 被顶替的内存通道 | 可能读到 `Ok(None)`，而不是 4002 | 两个方向先写同一个关闭原因再唤醒，Windows 上也读到 4002（[#1295](https://github.com/arcships/rutis/issues/1295)） |

其余修复：

- **Python 重载**：同一秒内把文件改成同样长度的新内容时，重载会用旧的 `.pyc`；现在删掉时间戳变了的模块的 `.pyc` 再编译。`.pyc` 路径改用 `importlib.util.cache_from_source`，Python 3.15 没有 `__cached__` 也能算（[#1080](https://github.com/arcships/rutis/issues/1080)）。
- **dsh**：YAML 里进制前缀后再带符号的数不再 panic；表达式嵌套超过 64 层报错，不再栈溢出（[#1080](https://github.com/arcships/rutis/issues/1080)）。
- **Swift 夹具与 SDK**：取消后等 `ack` 而不是 `return`；会话与应用的 `dispatch`／`apply` 标 `@Sendable`；`receive` 只解一层 `Result`；Security 的证书与身份用不可变盒跨任务（[#1099](https://github.com/arcships/rutis/issues/1099)、[#1273](https://github.com/arcships/rutis/issues/1273)）。
- **会话一致性用例**：不连接、不回答的对端有上限，过时的 offers 与替换时序不再让用例偶发失败；`grant_rollback` 每个 proptest 用例用新的 link（[#1080](https://github.com/arcships/rutis/issues/1080)）。
- **跨版本测试**：协议 5 下按发布代际拒绝 0.19–0.22 的对端，0.19 之前仍按旧文案与 `rutis-bridge/peer` 行断言（[#1080](https://github.com/arcships/rutis/issues/1080)）。

## 已知不保证

- **1.0 的长期契约不在这一版**：Rust API 的稳定化流程、插件 API 3 之外的重新设计、`rutis.json` `format` 1 之外的格式都不做。0.23 是 beta，不是 1.0。
- **跨帧大消息在七种实现之间启用**：Rust、Node、Bun、Python、Go、Swift、Kotlin 都声明 `chunked`；更早的、没有声明 `chunked` 的端与任何端的调用仍受原来的 16 MiB 单消息限制；`max_transfer` 默认 256 MiB，超过时明确失败（[#1361](https://github.com/arcships/rutis/issues/1361)、[#1363](https://github.com/arcships/rutis/issues/1363)）。
- **协议 5 只在本仓库的七种实现内验证**：0.22 及更早的宿主、运行时、节点和 SDK 在握手时被拒（`SESS-79`），没有协议 4 与协议 5 混跑的会话；见过更早协议 5 预发布构建的对端会按 `SESS-66` 失败带 `awaited` 的调用，必须换成 0.23 的构建（`SESS-81`）。
- **等待图的这些情形仍不保证**（`SESS-40`）：没有在帧上标 `sync` 的同步调用不在检测范围，可能死锁；帧上说 `awaited: false` 却实际等待结果的调用漏掉等待边，同样可能死锁；跨主机的环、可重入的代价、新旧版本混用的等待图、宿主工作线程用尽都不保证。
- **未知字段不是扩展机制**（`SESS-69`）：旧实现会按 `SESS-66` 失败该调用；新增帧或改变已有字段的含义要提升协议版本，新增能力要按声明使用。
- **形式化覆盖还没做完**：追踪表里 479 条现行协议规则未验证、364 条只有部分验证；登记表 219 行与手写 `ECA` 10 行还没有逐条重抽；残余缺口由 [#776](https://github.com/arcships/rutis/issues/776) 与 [#1270](https://github.com/arcships/rutis/issues/1270)–[#1274](https://github.com/arcships/rutis/issues/1274) 跟踪。Kani 的构造器错误路径、`parse_boot`、`boot_meta`／`is_sha256` 的 `&str` 包装仍无结论；dylib 没有 shuttle 模型；`rutis-host`、`rutis-loader` 的 6 个模型不在任何 workflow 里跑；Go 没有可控调度；`sync_cycles` 仍缺 Kotlin 列，`host_gone` 仍缺 Kotlin 列。
- **服务公告的信任边界**：`UndeclaredPolicy` 默认是 `Publish`；不设策略的宿主仍按 Cordis 兼容发布运行时没有声明的名字。它不是权限、认证或安全边界，只是宿主限制运行时行对外宣告名字的策略。
- **事件的明确不保证**：并发 emit 没有先后、并发登记与分发没有先后、撤下时在途调用的结局、监听器的完成顺序（[保证登记表](../guarantees.md)里 10 条明确不保证的一部分）。
- **网络冒烟与 agent 试用**：两台机器的网络冒烟与发布前的 agent 试用（[#663](https://github.com/arcships/rutis/issues/663)）还没做；本机回环冒烟见[发布](../release.md)的「0.23.0」一节。

## 兼容

- 会话协议是 **5**（`crates/rutis-bridge/src/session/mod.rs` 的 `ENDPOINT_PROTOCOL`）；协议 5 的能力 `chunked` 由七种实现（Rust、Node、Bun、Python、Go、Swift、Kotlin）声明；更早的、没有声明的端不会收到 `chunk` 帧，仍按 16 MiB 上限。
0.22 及更早的端在握手时被拒，没有混跑的会话。握手与能力声明不新增“必需能力”；`awaited` 缺省时按旧语义（会等）读。
- 插件 API 仍是 3，`rutis.json` 的 `format` 仍是 1；配置没有新增字段，持久化样本从 0.22.0 复制，期望不变。
- Rust 没有删除或改名公开 API；内核的公开 API 快照不变。`rutis-bridge` 新增 `UndeclaredPolicy`，`rutis-loader` 的 `Instance` 新增 `rows` 字段：都是新增。
- dylib 插件照每次发布一样用 0.23.0 的 SDK 重新构建。
- npm、PyPI、Go、Swift、Kotlin 的版本都随列车到 0.23.0；Kotlin SDK 仍随列车打版本，Maven Central 按 `release.yml` 的规则发布（environment `maven` 的四个 secret，缺一个时 `maven` 任务跳过）。

## 升级

大多数插件与宿主不用改代码。要做的只有两件事：宿主和每个运行时、节点、SDK 一起升级到 0.23（协议 4 的对端在握手时被拒）；固定 WebSocket 子协议的工具改成 `rutis.5`。会碰到行为变化的地方：被取消的调用现在由被调方确认、不再回复；`awaited: false` 的异步调用不再被当成等待边；行结束后的分发看不到已结束的行；卸载时清理交出的 emit 会送到。Swift 插件若在顶层代码里定义 `apply`，按 Swift 6 模式标 `@Sendable` 或移到单独文件。逐条改法见[迁移到 0.23](../migration-0.23.md)。
