# rutis 0.21.0

[English](0.21.0.en.md) · [0.20.1 发布说明](0.20.1.md)

0.21 让出错时说清楚：值传不过去时带原因（`non-finite`、`cycle`、`too-deep`、`type`、`tag`、`limit`），返回值解不开有单独的码 `bad-result`，参数不对时照收底层解码器的原文，同名服务、等待的原因、同步等待成环都说开发者写的那次调用。三处不兼容：交来的函数默认异步、Rust 的 `rutis::Error::Value` 换了变体形状、出错文字几乎都换了。升级前看[迁移到 0.21](../migration-0.21.md)。

## 先看这三处（不兼容）

- **交来的函数默认异步**（[#932](https://github.com/arcships/rutis/issues/932)、[#1065](https://github.com/arcships/rutis/pull/1065)）。按引用传来的函数（另一个插件交给你的回调、宿主给的回调）现在与服务方法一样调用：不在同步调用里时返回 Promise（Node、Bun）或可 await 的对象（Python），`await` 它得到结果；在 `sync` 方法、同步 `waterfall` 里照旧同步返回结果。以前一律同步等结果，写成 `async` 的假服务会撞上 `SyncWaitCycle`。改法只有一处：`const text = f()` → `const text = await f()`，改过的写法在 0.20 的 Node、Bun 上也能运行。见[迁移到 0.21](../migration-0.21.md#交来的函数默认异步932)。
- **Rust 的 `rutis::Error::Value` 变成带 `reason` 的结构体变体**（[#936](https://github.com/arcships/rutis/issues/936)、[#1070](https://github.com/arcships/rutis/pull/1070)）。`Value(String)` → `Value { message, reason }`，新增 `Error::value()` 与 `Error::why()`；按变体匹配的宿主要改。见[迁移到 0.21](../migration-0.21.md#rust-的值错误带上-reason936)。
- **出错文字换了，按码匹配**（[#933](https://github.com/arcships/rutis/issues/933)、[#936](https://github.com/arcships/rutis/issues/936)、[#937](https://github.com/arcships/rutis/issues/937)）。`code` 与 `data` 的键是契约，文字不是。对照表与各语言怎么读码见[迁移到 0.21](../migration-0.21.md#出错文字变了933-936-937)。

## 值传不过去时说清为什么

- **`bad-value` 带 `reason`**（[#936](https://github.com/arcships/rutis/issues/936)、[#1062](https://github.com/arcships/rutis/pull/1062)、[#1070](https://github.com/arcships/rutis/pull/1070)，设计见[值传不过去时的报错统一](../design-value-errors-2026-11-03.md)）。`data` 从 `{argument?, part, limit?}` 多一个 `reason`：`non-finite`、`cycle`、`too-deep`、`type`、`tag`、`limit`。以前程序分不出「NaN」和「循环」，只能读文字。
- **四句话统一**：`the number NaN is not finite`、`the value holds itself (a cycle)`、`the value nests deeper than 64 levels`、`a <类型> cannot cross between processes`。以前「嵌套过深」有四种说法，Swift 还在括号里猜「是不是循环」；现在循环与深度分开，循环先于深度——同一个对象出现在兄弟位置（`[shared, shared]`）不算环。
- **循环真的查了**（[#1074](https://github.com/arcships/rutis/pull/1074)）。Go、Python、Node、Bun 本来就查；Kotlin 与 Swift 的 `cyclic` 以前是死代码，Kotlin 的自指容器在数据侧甚至是 `StackOverflowError`——现在六种语言的运行时都按「这条路上的容器」查。Rust 一侧做不到，`Exact` 旁边写明了原因：serde 的 `Serializer` 一次只给一个字段，拿不到容器身份，`too-deep` 是那一侧唯一能给的拒绝。
- **返回值解不开是新码 `bad-result`**（同 #936）。消息是 `<服务>.<方法>: the result: <解码器自己的那句>`，`data` 是 `{service, method, expected}`，`expected` 是声明的类型（`a string`、`a Forecast`）。
- **参数不对时照收解码器的原文**（[#1073](https://github.com/arcships/rutis/pull/1073)）：`argument 1: expected an integer, got a string`（Rust 用 serde 的、Go 用 encoding/json 的、Kotlin 用 kotlinx.serialization 的）。以前各家都转述成 `argument 1 should be an integer, got "x"`。Swift、Python、Node 仍是旧形状。

## 出错信息说清是谁

- **同名服务给出改法**（[#937](https://github.com/arcships/rutis/issues/937)、[#1064](https://github.com/arcships/rutis/pull/1064)、[#1068](https://github.com/arcships/rutis/pull/1068)）：`weather is already provided by store: rename one of them`，宿主自己持有时 `… the host: rename it`。六种语言一致。
- **`no-method` 说提供者**：这一侧知道是谁提供的时候，后面多 `; it is provided by row store`，`data.provider` 是 `store`。找自己的服务找不到、名字被别人占着的开发者因此看得见。
- **等待的原因**：`waiting for lmm (nothing provides it yet; did you mean llm?)`、`row b waits for weather too: they inject each other`、状态词 `stopping`、`not running (its group is not running)`。
- **`SyncWaitCycle` 不再露内部编号**（[#1072](https://github.com/arcships/rutis/pull/1072)，措辞由[诊断设计](../design-diagnostics-2026-10-26.md) §4.3 采纳）：`<开发者写的那次调用> would wait on itself: it is awaited inside the synchronous call that produces it (synchronous calls)`。以前是 `await requires the Node thread occupied by its parent synchronous call; path: test:5 -> rutis-test:3 -> rutis-test:4`。
- **代理的显示**：`[remote object]`、`<remote object>` → `<object of another process>`。

## 测试工具

- **宿主给出这一行**（[#933](https://github.com/arcships/rutis/issues/933)、[#1063](https://github.com/arcships/rutis/pull/1063)）：`state(id)` 读一行的状态；`Options.name` 给这次 `load` 的行一个名字；`Failure.error` 是被测那一行自己的错误（以前只有一行字）。`FiberView::running(limit)` 等一行真的跑起来。
- **失败时说清在等什么**：`timeout`、`not-running`、`no-service` 三个码，`Line` 里是那一行自己的说法加上位置行（`in <行>:` 与 `at <文件>:<行>`）；`apply` 里抛出的错误是 `failed in apply: <原文>`。
- **测试之间不串**：上一个测试没结束的东西不会混进下一个。

## 发布门

- **用这次构建的包跑指南示例**（[#1071](https://github.com/arcships/rutis/pull/1071)）：`install.yml` 在 `linux-x64` 上用发布门自己构建的产物跑只装 npm、PyPI 的示例（含 open-host 第 5 节的两份）。Python 侧是本地的 PEP 503 简单索引在前、PyPI 在后，`rutis` 一定来自门里构建的那份，示例自己的构建后端（`hatchling`）照常从 PyPI 取。

## 修掉的问题

- **过滤器必须同步问**（[#1065](https://github.com/arcships/rutis/pull/1065)）：交来的函数改成异步之后，过滤器的裁决变成 Promise，恒真，`h.filter(() => false)` 全放行。现在过滤器在同步调用里问（Node、Bun 的 `withinSync`，Python 的 `_blocking`）。
- **Python 的 `await f(...)` 把它自己返回的 Promise 一并等完**（同 #1065）：session relay 的 `near.receive()` 会把队列的 promise 原样交回来，以前只等一层，消息根本没入队。
- **Python 监听器立刻关闭不再算失败**（[#1052](https://github.com/arcships/rutis/issues/1052)、[#1075](https://github.com/arcships/rutis/pull/1075)）：`close()` 与 `serve_forever()` 抢跑时，监听线程不再带一个没人接的 `OSError: Bad file descriptor`。同一份 PR 里，`test_websocket` 的「关掉后不再服务」改成按语义断言（Linux 是 `ConnectionRefusedError`，macOS 是握手后立刻 EOF），本机 Python 用例从恒有 4 个 error 变成全绿。

## 兼容

- 会话协议仍是 4，`rutis.json` 的 `format` 仍是 1，插件 API 仍是 3：线上格式、能力、握手都没变。交来的函数是异步还是同步由**发起调用的那一侧的运行时**决定，新旧版本可以混用（[迁移到 0.21](../migration-0.21.md#交来的函数默认异步932) 的「影响」）。
- `rutis-host types` 写出的类型不用重新生成：回调的返回类型本来就写 `string | Promise<string>`。
- 持久化样本从 0.20.1 复制，`rutis.json` 与 dsh 用户层的期望不变。
- dylib 插件照每次发布一样用 0.21.0 的 SDK 重新构建。
