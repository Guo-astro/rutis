# rutis 0.21.0

[中文](0.21.0.md) · [0.20.1 release notes](0.20.1.en.md)

0.21 makes errors say what happened: a value that cannot cross carries a reason (`non-finite`, `cycle`, `too-deep`, `type`, `tag`, `limit`), a result that does not decode has its own code `bad-result`, a refused argument quotes the decoder, and an already-provided name, a wait, or a synchronous wait cycle says the call the developer wrote. Three things are incompatible: a received function is asynchronous by default, Rust's `rutis::Error::Value` changed shape, and almost every error text changed. Read [migrating to 0.21](../migration-0.21.en.md) before upgrading.

## First, the three incompatible ones

- **A received function is asynchronous by default** ([#932](https://github.com/arcships/rutis/issues/932), [#1065](https://github.com/arcships/rutis/pull/1065)). A function handed over by reference (a callback another plugin gave you, one the host gave you) is called like a service method now: outside a synchronous call it returns a Promise (Node, Bun) or an awaitable (Python), and awaiting it gives the result; inside a `sync` method or a synchronous `waterfall` it still returns the result itself. Before, it always waited synchronously, so a fake service written `async` hit `SyncWaitCycle`. The change is one line: `const text = f()` → `const text = await f()`; the new form runs on 0.20's Node and Bun too. See [migrating to 0.21](../migration-0.21.en.md#a-received-function-is-asynchronous-by-default-932).
- **Rust's `rutis::Error::Value` is a struct variant with a `reason`** ([#936](https://github.com/arcships/rutis/issues/936), [#1070](https://github.com/arcships/rutis/pull/1070)). `Value(String)` → `Value { message, reason }`, with `Error::value()` and `Error::why()` new; a host that matches on the variant changes. See [migrating to 0.21](../migration-0.21.en.md#rusts-value-errors-carry-a-reason-936).
- **The error texts changed: match on codes** ([#933](https://github.com/arcships/rutis/issues/933), [#936](https://github.com/arcships/rutis/issues/936), [#937](https://github.com/arcships/rutis/issues/937)). The codes and the keys of `data` are the contract; the texts are not. The table and how to read codes in each language are in [migrating to 0.21](../migration-0.21.en.md#the-error-texts-changed-933-936-937).

## A value that cannot cross says why

- **`bad-value` carries a `reason`** ([#936](https://github.com/arcships/rutis/issues/936), [#1062](https://github.com/arcships/rutis/pull/1062), [#1070](https://github.com/arcships/rutis/pull/1070); design: [one shape for a value that cannot cross](../design-value-errors-2026-11-03.en.md)). `data` grows from `{argument?, part, limit?}` to include `reason`: `non-finite`, `cycle`, `too-deep`, `type`, `tag`, `limit`. A program could not tell "NaN" from "a cycle" before; it had to read the text.
- **Four sentences, one per runtime**: `the number NaN is not finite`, `the value holds itself (a cycle)`, `the value nests deeper than 64 levels`, `a <Type> cannot cross between processes`. "Nested too deep" had four different wordings, and Swift guessed "(a cyclic reference?)" in brackets; a cycle and a depth are separate now, and a cycle comes first — the same object in two places (`[shared, shared]`) is not a cycle.
- **Cycles are actually detected** ([#1074](https://github.com/arcships/rutis/pull/1074)). Go, Python, Node and Bun already did; Kotlin's and Swift's `cyclic` were dead code, and in Kotlin a self-holding container was a `StackOverflowError` on the data side — all six runtimes walk the containers on the path now. Rust cannot: next to `Exact` it says why (serde's `Serializer` hands over one field at a time and has no identity for a container), and `too-deep` is the only refusal that side can give.
- **A result that does not decode is the new code `bad-result`** (same #936). The message is `<service>.<method>: the result: <the decoder's own sentence>`, `data` is `{service, method, expected}`, and `expected` is the declared type (`a string`, `a Forecast`).
- **A refused argument quotes the decoder** ([#1073](https://github.com/arcships/rutis/pull/1073)): `argument 1: expected an integer, got a string` (serde's sentence in Rust, encoding/json's in Go, kotlinx.serialization's in Kotlin). Every runtime used to paraphrase it as `argument 1 should be an integer, got "x"`. Swift, Python and Node keep the old shape.

## Errors say whose they are

- **A taken name says what to do** ([#937](https://github.com/arcships/rutis/issues/937), [#1064](https://github.com/arcships/rutis/pull/1064), [#1068](https://github.com/arcships/rutis/pull/1068)): `weather is already provided by store: rename one of them`, and `… the host: rename it` for a name the host holds itself. All six runtimes say it.
- **`no-method` names the provider**: when this side knows who provides it, `; it is provided by row store` follows and `data.provider` is `store`. A developer looking for their own service that someone else took sees it.
- **Why a row waits**: `waiting for lmm (nothing provides it yet; did you mean llm?)`, `row b waits for weather too: they inject each other`, the state words `stopping` and `not running (its group is not running)`.
- **`SyncWaitCycle` shows no internal ids** ([#1072](https://github.com/arcships/rutis/pull/1072); the wording was adopted by the [diagnostics design](../design-diagnostics-2026-10-26.en.md) §4.3): `<the call the developer wrote> would wait on itself: it is awaited inside the synchronous call that produces it (synchronous calls)`. It used to read `await requires the Node thread occupied by its parent synchronous call; path: test:5 -> rutis-test:3 -> rutis-test:4`.
- **How a proxy prints**: `[remote object]`, `<remote object>` → `<object of another process>`.

## The test tool

- **The host names the row** ([#933](https://github.com/arcships/rutis/issues/933), [#1063](https://github.com/arcships/rutis/pull/1063)): `state(id)` reads a row's state; `Options.name` gives this `load` a name; `Failure.error` is the tested row's own error (it used to be one line of text). `FiberView::running(limit)` waits for a row to be really running.
- **A failure says what it waited for**: the codes `timeout`, `not-running` and `no-service`, a `Line` carrying the row's own words plus the position lines (`in <row>:`, `at <file>:<line>`), and `failed in apply: <the original>` for an error thrown in `apply`.
- **Tests do not leak into each other**: what a test left unfinished does not reach the next one.

## The release gate

- **The guides' examples run on this build's packages** ([#1071](https://github.com/arcships/rutis/pull/1071)): on `linux-x64`, `install.yml` runs the examples that install only from npm and PyPI (including the two in open-host's §5) against what the gate built. On the Python side a local PEP 503 index comes first and PyPI after it, so `rutis` is always the gate's build while an example's own build backend (`hatchling`) still comes from PyPI.

## Fixed

- **A filter is asked synchronously** ([#1065](https://github.com/arcships/rutis/pull/1065)): once a received function became asynchronous, a filter's verdict was a Promise — always truthy — and `h.filter(() => false)` let everything through. A filter is asked inside a synchronous call now (Node and Bun's `withinSync`, Python's `_blocking`).
- **Python's `await f(...)` settles the promise the function itself returns** (same #1065): a session relay's `near.receive()` hands its queue's promise back, and awaiting one level left the message unqueued.
- **Closing a Python listener right after it starts is no longer a failure** ([#1052](https://github.com/arcships/rutis/issues/1052), [#1075](https://github.com/arcships/rutis/pull/1075)): when `close()` races `serve_forever()`, the serving thread no longer dies with an unclaimed `OSError: Bad file descriptor`. The same PR makes `test_websocket`'s "nothing serves it any more" a semantic assertion (Linux refuses, macOS completes the handshake and ends it at once), so a local Python run went from four permanent errors to green.

## Compatibility

- The session protocol is still 4, `rutis.json`'s `format` is still 1, the plugin API is still 3: the wire format, the capabilities and the handshake are unchanged. Whether a received function is asynchronous or synchronous is decided by the runtime that **makes** the call, so old and new versions mix (see "Who is affected" in [migrating to 0.21](../migration-0.21.en.md#a-received-function-is-asynchronous-by-default-932)).
- The types `rutis-host types` writes need no regeneration: a callback's return type already reads `string | Promise<string>`.
- The persisted samples are copied from 0.20.1, and the expectations for `rutis.json` and the dsh user layer are unchanged.
- A dylib plugin is rebuilt with 0.21.0's SDK, as with every release.
