# rutis 0.20

[English](0.20.en.md) · [0.19.3 发布说明](0.19.3.md)

0.20 里插件可以写可选依赖：`optional` 写在 `inject` 旁边，用 `ctx.get` 读，没有也能运行；行的 `inject` 在六种语言里都算这一行的声明，运行时的行也由 rutis 门控并租借；同一进程里的服务在 Go、Kotlin 也拿到对象本身；测试工具收下插件交出的定义。卸载顺序改成清理与服务撤回在同一个逆序栈里跑，这一处不兼容。升级前看[迁移到 0.20](../migration-0.20.md)。

## 先看这一处：卸载顺序（不兼容）

一行卸载时只跑**一个**栈：`provide` 记下"撤回这个服务"，`ctx.effect` 与 `apply` 返回的清理也记进去；卸载时逆序、一条一条跑，撤回在自己的位置上发生（[#1010](https://github.com/arcships/rutis/pull/1010)，设计见[卸载顺序](../design-unload-order-2026-11-01.md)）。六种语言（Go、Python、Bun、Kotlin、Swift、Node）都是这个行为。

- **清理里登记的清理不运行**：六家都写一行 `rutis: row <行> is not active: cleanup is not registered`（Node：`plugin <插件>`）。Kotlin 以前写了那一行、照样不运行那条清理，Go、Python、Bun、Swift 静默丢弃，Node 交给 Cordis 的处置表。
- **清理之间不能互相等**：一条一条跑之后，等另一条清理（例如等一个由后跑的清理兑现的 Promise）就永远等不到。
- **Node 不再同时开始全部清理**：以前 `_unload` 用 `Promise.all` 同时开始。

`provide` 之前／之后登记的清理读自己提供的服务、别的行在这一行卸载期间读它，以及六家 0.19 与 0.20 的对照，见[迁移到 0.20 的「卸载顺序」](../migration-0.20.md#卸载顺序1010)。

## 可选服务

- **`optional` 写在 `inject` 旁边，用 `ctx.get` 读**（[#999](https://github.com/arcships/rutis/pull/999)，设计见[可选依赖](../design-optional-deps-2026-10-28.md)）。有 `llm` 就用它总结、没有就截断原文的插件，以前只能写进 `inject`，宿主没有它时这一行一直等。现在把它写进 `optional`：行照常启动，不因它停在 `waiting for` 里，`ctx.get('llm')` 在没有时返回空值（`undefined`、`None`；Go 的 `ctx.Get(name, &target)` 返回 `false, nil`；Swift `nil`，Kotlin `null`）。宿主提供的服务在这一行启动时在就租借进来、留到它停止，之后才出现的要重启这一行；同一进程里别的行提供的，按每次 `get` 那一刻的表。语义与 Rust 的 `Option<Arc<T>>` 相同。各语言的写法见[插件 API 的可选服务](../guide/plugin-api.md#可选服务)。
- **`use` 不认 `optional`**：只写在 `optional` 里的名字，`ctx.use` 报的还是原来那句 `service llm is not available to this plugin, which does not declare it in inject: add 'llm' to its inject`（Go：`… in Inject: add "llm" to its Inject`）；可选的服务用 `ctx.get` 读，与 Rust 的 `ctx.require` 对 `Option<Arc<T>>` 报未声明相同。`get` 一个哪里都没声明的名字报 `service llm is not available to this plugin, which does not declare it: add 'llm' to its optional (or to its inject, if it cannot run without it)`。
- **同一个名字两处都写，这一行失败**：插件的 `inject` 与 `optional` 里都有 `llm` 时 `llm is in both inject and optional; keep it in one`；行的 `inject` 与插件的 `optional` 里都有时 `llm is in the row's inject and the plugin's optional; keep it in one`。
- **`rutis-host check` 打印 `optional`**：`inject:` 之后多一行 `optional: ["llm"]`（为空时没有这一行），可选的服务没人提供不算失败。
- `optional` 要 rutis-host 0.20 或以后：旧宿主不认它，不租借这些名字，`get` 一直返回空值，不报错。

## 行的 `inject` 与运行时行

- **行的 `inject` 算这一行已声明，六种语言一致**（[#1000](https://github.com/arcships/rutis/pull/1000)，设计见[行的 `inject` 与 `use` 先查声明](../design-declared-services-2026-10-29.md)）。`use` 的已声明是插件的 `inject`、行的 `inject`，加上插件正提供着的名字；`get` 的再加插件的 `optional`。两处放宽：Go、Swift、Kotlin 的 `use`、`get` 对行 `inject` 里的名字以前报 `not-declared`，现在同进程里有的拿到对象本身，租借进来的拿到代理；插件读自己正提供着的服务，`use` 与 `get` 都给它本身（撤回之后与没声明的一样报 `not-declared`）。
- **一处收紧：插件要自己声明用到的服务**（同上）。Node、Bun、Python 的 `use` 以前先查进程里的服务表、查不到才看声明，于是插件和行都没声明、而同一进程里别的行声明了同一个名字时，这个插件拿得到——取决于进程里还装着什么。现在 `use` 与 `get` 都是先查声明，这种插件报 `service llm is not available to this plugin, which does not declare it in inject: add 'llm' to its inject`。这是 [#676](https://github.com/arcships/rutis/issues/676) 要的结果，不是回归；要改的地方见[迁移到 0.20](../migration-0.20.md#use-先查声明1000)。
- **运行时的行按行 `inject` 门控并租借**（[#1001](https://github.com/arcships/rutis/pull/1001)，设计见[运行时行的行 `inject`](../design-row-inject-gate-2026-10-31.md)）。行 `inject` 里的服务由宿主或别的进程、进程里还没有时，以前 Bun、Python、Go、Swift、Kotlin 的行照常启动、`use` 报 `service llm is not available`，Node 的行在 rutis 里显示运行、实际停在进程里的 Cordis 门控上。现在六种语言一样：`chat: waiting for llm (no row provides it)`（有相近的名字时括号里加 `; did you mean <名字>?`），与 `rutis-host check` 早就报的一致；服务来了行启动、插件拿到它，服务走了行停下、回来后重新启动；给一行加上 `inject` 时这一行重启一次。服务目录不共享的名字（应用登记成 Rust 类型的）不门控、不租借，行为与以前一样，见[迁移到 0.20](../migration-0.20.md#运行时行的行-inject1001)。

## 同一进程里的服务

- **Go：接口、`any` 与同类型的函数字段拿到提供方的对象本身**（[#1015](https://github.com/arcships/rutis/pull/1015)，设计见[Go：同一进程里拿到提供方的对象本身](../design-go-local-objects-2026-11-01.md)）。同一进程里的两个 Go 插件以前只能用包级全局变量互相传对象：`ctx.Use` 只认函数字段的结构体与 `*advanced.Service`，接口目标报 `use hello: the target must point to a struct of function fields or a *advanced.Service, not rutis.Greeter`，类型与提供方方法相同、但不以 `error` 结尾的字段报 `use canvas: field Draw: func(string) string must return an error last`。现在目标能装下本进程提供方的对象（它实现的接口、它自己的类型、`any`）时直接给这个对象，调用是普通的 Go 调用；`any` 目标、提供方在别的进程时给 `*advanced.Service`。非空接口目标只在同一进程成立：跨进程报 `use workspace: editor.Workspace is an interface, which only a service provided in this process fills: for one of another process, use a struct of function fields or *advanced.Service`。见 [Go 插件：使用服务](../guide/go-plugin.md#3-使用服务)。
- **Kotlin：`use` 先给本进程的对象**（[#1006](https://github.com/arcships/rutis/pull/1006)）。`ctx.use(name, type)` 以前先取代理表，接口没标 `@RutisClient` 就以 `IllegalArgumentException` 失败（`<类型> has no proxy: annotate it @RutisClient and apply the rutis-ksp processor`），之后才看本进程的对象——提供方就在这个进程、对象实现了你的接口时也一样。现在先看本进程的对象，实现了 `type` 就返回它本身；要代理（本进程的对象不实现 `type`、远端或宿主服务）时才要 `@RutisClient`。只在本进程用的接口不必再标注。

## 测试工具

- **测试替身收到的插件定义可以直接交给 `load`**（[#1004](https://github.com/arcships/rutis/issues/1004)、[#1008](https://github.com/arcships/rutis/pull/1008)、[#1012](https://github.com/arcships/rutis/pull/1012)，设计见[测试工具：`load` 装接受测插件交出的插件定义](../design-test-tool-definition-load-2026-11-01.md)）。插件把 `definePlugin` 的结果交给测试的服务，测试收下的那个值现在可以直接交给 `load`，作为一行跑在定义它的运行时里：配置校验与默认值、`inject` 门控、服务公告、监听者随行、卸载都和 `load(file)` 一样。以前这个值交不出来：测试那一侧的会话没有声明 `plugins`，插件交出定义那次调用就失败，`… cannot send a plugin definition: the far end does not accept plugin definitions (it did not declare the capability plugins)`。行 id 也照 `load(file)`：不给 `id` 时是定义的名字，重名加 `-2`；显式 `id` 撞上是 `a row <id> is loaded already`。同一个定义 `load` 两次是两行，各自卸载；来源行结束不带走这一行，由测试（或测试结束时的测试工具）卸它。伪造的句柄报 `PluginTestError: load needs a plugin definition a test double received`。Python、Go、Swift、Kotlin 的测试工具本来就这样做。
- **TypeScript 与 Bun：超时落在 `load` 里时测试照样能退出**（[#997](https://github.com/arcships/rutis/issues/997)、[#1017](https://github.com/arcships/rutis/pull/1017)）。测试在 `load` 还没起完宿主时超时，以前这次 `load` 继续跑，宿主起来后这次调用占住进程，而发起它的测试已经结束、它的 `after` 钩子不会再跑，`npm test` 挂住要外面杀掉。现在测试结束（含超时）时进行中的 `load` 被放弃：`rutis-host` 停掉，下一次 `load` 重新起一个宿主，已经装载的行和服务也撤下。Node 22 上测试结束时的清理照样占住进程，不会取消同一文件里后面的测试。
- **Bun：测试结束的钩子里不再注册钩子**（[#994](https://github.com/arcships/rutis/issues/994)、[#1011](https://github.com/arcships/rutis/pull/1011)）。测试结束时的清理（卸载宿主等）照样占住进程，但不再在钩子里注册 `after` / `onTestFinished`：钩子里注册的钩子不会跑，Bun 也不该从一个钩子里收钩子（以前表现为 `SyncWaitCycle: await requires the Bun thread occupied by its parent synchronous call`，那里起的调用混进后面的测试）。
- **Python：假服务撞名只让那次 `load` 失败**（[#995](https://github.com/arcships/rutis/issues/995)、[#1007](https://github.com/arcships/rutis/pull/1007)）。测试给的服务以前由测试插件自己提供，撞上宿主已有的名字（例如 `rutis/sessions`）时失败的是那个插件，它重启再失败后 `rutis-host test` 不再可用，之后每次 `load`、卸载都报 `service rutis-host/test is not available`。现在每个服务单独一行 `rutis-test/<名字>`，撞名的那次 `load` 以那一行的状态失败：`rutis-test/rutis/sessions: rutis/sessions is already provided by the host`，同一个宿主照常服务后面的测试。Node、Bun 的同类问题 0.19.3 已修（[#993](https://github.com/arcships/rutis/pull/993)）。

## 连接与运行时进程

- **停住读取的对端不再挡住别的客户端**（[#1005](https://github.com/arcships/rutis/issues/1005)、[#1009](https://github.com/arcships/rutis/pull/1009)）。一个对端停住读（终端界面被挂起、链路很慢）时，以前向它发一帧的那个线程会停在通道的写里；会话的事件表一变（新客户端连上时注册监听者），这次同步写就落在连上的线程上，同一进程里其他客户端于是起不来。现在会话有自己的写线程：调用、回复、释放只把帧按顺序入队后返回，阻塞只落在写线程上。积压的上限是宿主打开的选项 `SessionOptions::outbound_limit`，默认不限——慢端只影响它自己那条会话，不丢事件；配了上限才按 `the far end is not reading: N messages, B bytes waited for it` 结束会话。`rutis.json` 不设它，`rutis-host/dial`、`rutis-host/listen` 与 `sessions.open(far)` 用默认。会话结束时队列里还没写出的帧随会话丢弃。
- **宿主没了，Python 运行时在时限内退出**（[#985](https://github.com/arcships/rutis/issues/985)、[#1014](https://github.com/arcships/rutis/pull/1014)）。Python 运行时的清理截止时间由一个计时线程武装：线程起不来（进程没有线程可用，负载高时可能）就再没有东西结束这个进程，它会一直留着。现在计时线程起不来时立刻以 1 退出并说明原因——没有截止时间的进程等于已经到期。用 Python 运行时的 `rutis-host test` 也一样：运行时一直不回话时，测试按挂起防护的时限失败，并打印运行时当时在做什么（进程还在不在、哪些进入行的调用没回来），不再永久挂住。
- **`Process::mount` 等运行时进程问候有了时限**（同 #985、[#1014](https://github.com/arcships/rutis/pull/1014)）。以前一个起来了却一直不问候的运行时会让它永远等下去。现在 30 秒（`rutis_bridge::runtime::GREETING`，与 rutis-host 的 `SpawnPlugin` 同一条常量），`Mount::greeting` 可改、`Duration::MAX` 不限（调试器停在下一条语句的进程）；到时限还没问候时以 `Error::Transport` 失败，文字是 `the runtime process <名字> started but did not greet within <时限>s`，并结束这个进程。`Mount` 因此多一个公有字段 `greeting`，见[迁移到 0.20](../migration-0.20.md#运行时进程的问候时限1014)。

## 内存与诊断

- **每个实例的常驻占用更小，关闭后不再留着峰值容量**（[#979](https://github.com/arcships/rutis/issues/979)、[#1016](https://github.com/arcships/rutis/pull/1016)，数字与组成见[实例的常驻占用](../performance-instance-footprint-2026-11-02.md)）。每行一个监视任务，它把少见的"行自停"分支放进 `Box::pin`（`Box` 只在行真的自停时才分配），future 从 1,872 B 降到 344 B，一个 8 行的实例省约 13.4 KiB。release 构建、1000 个实例：每实例 63.3 KiB 降到 50.9 KiB（−20%），带事件监听者的 71.5 KiB 降到 59.1 KiB（−17%）；1000 个实例关完之后的残留从 6,001,908 B 降到 22,708 B。`close_memory` 随之收紧成资源基线：每实例、关闭峰值、关完后的残留超过阈值就失败，每晚以 release 构建跑一次。
- **要旧名 `loader` 的行不再被建议加标注**（[#996](https://github.com/arcships/rutis/issues/996)、[#1013](https://github.com/arcships/rutis/pull/1013)）。加载器把自己的 Rust 句柄 `Loader` 提供进上下文，它的类型名按默认规则正好派生成 `loader`，于是还在要旧名 `loader` 的行等到的原因是"这个 Rust 服务没导出，给它的 impl 加 `#[rutis::service]`"——这条建议不适用：句柄不是谁忘了标注的服务。现在 rutis 自己的插件提供的句柄不算候选，行状态回到 `waiting for loader (no row provides it)`，与 `rutis-host check` 的 `cannot run: nothing provides loader` 一致。应用自己提供的未标注 Rust 服务照旧给出这条提示。

## 行为变化

| 位置 | 以前 | 现在 |
| --- | --- | --- |
| 行卸载时的清理与服务撤回 | 五家撤回在清理之前，Node 同时开始全部处置 | 一个逆序栈，一条一条，撤回在自己的位置上 |
| `use`、`get` 的已声明 | 插件的 `inject`（行 `inject` 只在 Node、Bun、Python 算；这三家的 `use` 先查进程里的表） | 插件的 `inject` ∪ 行 `inject` ∪ 插件正提供着的名字；`get` 再加 `optional` |
| 插件和行都没声明，同一进程里别的行声明了 | Node、Bun、Python 拿得到 | `not-declared` |
| 插件读自己正提供着的服务（`use`、`get`） | Bun、Python 的 `use` 拿到，Node 的要等 `apply` 之后；`get` 与 Go、Swift、Kotlin 的 `use` 报 `not-declared` | 提供着的时候给对象本身，撤回后 `not-declared` |
| 运行时行的行 `inject` 里的服务不在（Bun、Python、Go、Swift、Kotlin） | 行照常启动，`use` 报 `unavailable` | 行停在 `waiting for <名字>` |
| 同上，提供方撤回 | 行继续运行 | 行停下，回来后重新启动 |
| Go `ctx.Use` 的接口、`any`、同类型函数字段目标 | 报 "must point to a struct of function fields …" | 本进程给对象本身，`any` 跨进程给 `*advanced.Service` |
| Kotlin `use` 一个没标 `@RutisClient` 的接口，提供方在本进程 | `has no proxy: annotate it @RutisClient …` | 给对象本身 |
| TypeScript 与 Bun 测试：替身收到的定义交给 `load` | 交不出来（`… the far end does not accept plugin definitions …`） | 作为一行装上 |
| TypeScript 测试：超时落在 `load` 里 | `npm test` 挂住，要外面杀掉 | 放弃这次 `load`，下一次重新起宿主 |
| Python 测试：假服务撞名 | `rutis-host test` 不再可用，之后每次 `load` 报 `service rutis-host/test is not available` | 只有那次 `load` 失败 |
| 一个停住读取的对端 | 发帧的线程停住，同进程里别的客户端起不来 | 帧入队，阻塞在会话自己的写线程 |
| Python 运行时的截止时间计时线程起不来 | 进程一直留着 | 立刻以 1 退出 |
| `Process::mount` 等一个起来了却不问候的运行时 | 永远等 | 30 秒（或设的时限）后失败，进程结束 |
| 一个 8 行实例的常驻（release，1000 个） | 63.3 KiB | 50.9 KiB |
| 1000 个实例关完后的残留 | 6,001,908 B | 22,708 B |
| 要旧名 `loader` 的行等到的原因 | 建议给 Rust 服务加 `#[rutis::service]` | `waiting for loader (no row provides it)` |

## 兼容

- 会话协议仍是 4，`rutis.json` 的 `format` 仍是 1，插件 API 版本不变：宿主与运行时、SDK 之间没有新的握手限制。卸载顺序与 `use` 的声明集合在各自的运行时里实现，混用旧版本的运行时包时那一家还是旧行为。
- 新写法要有同版本的工具：`optional` 要 rutis-host 0.20 或以后；测试替身收到的定义交给 `load` 要 `@arcships/rutis` 与运行时包同版本（旧 SDK 报 `load needs a plugin made with definePlugin`，旧运行时包在插件交出定义那次调用就失败：`cannot send a plugin definition: the far end does not accept plugin definitions (it did not declare the capability plugins)`）。
- dylib 插件照每次发布一样用 0.20 的 SDK 重新构建。
