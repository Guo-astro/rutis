# rutis 0.20.1

[中文](0.20.1.md) · [0.20.0 release notes](0.20.0.en.md)

0.20.1 is a patch release: it fixes bugs found after 0.20.0 and the two load-dependent failures of 0.20.0's release gate. **Nothing has to change in a plugin, in `rutis.json` or in `rutis.dev.json`, and there is no new form to migrate to**: put every rutis package at the same version. Everything you can see differently is in "Behaviour changes" below.

## `rutis-host dev`

- **Only the files a plugin loads reload** ([#1046](https://github.com/arcships/rutis/issues/1046), [#1047](https://github.com/arcships/rutis/pull/1047)). `dev` used to count a change to any file of the project as a change to the project's own row: running the tests once, editing a `README` or adding an image restarted that row and every row that uses it. What counts now is what a plugin loads: source modules (`.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.py`, `.pyi`), manifests and configuration (`.json`, `.yaml`, `.yml`, `.toml`) and `.env`. A test file (`*.test.*`, `*.spec.*`, `*.bench.*`, `test_*.py`, `*_test.py`, `*_test.go`, and anything under the project's `test`, `tests`, `__tests__`, `__mocks__`, `coverage` or `htmlcov` directories), a document, an image or a lockfile (`package-lock.json`, `pnpm-lock.yaml`, `uv.lock`, `Cargo.lock` and the like) changes nothing, and neither does the `coverage/` report a test run writes. The directories in between count from the project, so a project that lives under a directory called `tests` still works — the whole project does not become test files. A file of another extension (a template the plugin reads, say) does not reload either: change one of its modules to reload it. See [rutis-host: developing a plugin with `dev`](../guide/rutis-host.en.md#developing-a-plugin-with-dev).
- **The Node inspector's address can be changed with `RUTIS_NODE_INSPECT`** ([#1046](https://github.com/arcships/rutis/issues/1046), [#1048](https://github.com/arcships/rutis/pull/1048)). `dev --debug` used to pin the Node inspector to `127.0.0.1:9229`, so when the port was taken the only way was to end the process holding it. `RUTIS_NODE_INSPECT=host:port` (or a bare port, on `127.0.0.1`) changes it, and what `rutis-host dev: debugging: …` prints is what the Node process uses. A malformed value is refused before start, rather than printing an address nobody listens on: `RUTIS_NODE_INSPECT=<value> is not an address: set it to <host>:<port>, such as 127.0.0.1:9230, or to a port`.
- **`services: none` is no longer printed** ([#1046](https://github.com/arcships/rutis/issues/1046), [#1049](https://github.com/arcships/rutis/pull/1049)). Every start and every rebuild printed `rutis-host dev: services: none` first: it said that while the row had not run yet, or while its service was briefly gone during a reload, and `dev`'s examples do not show the line. With no row providing a service nothing is printed now (`rutis-host status` still says it), and `rutis-host dev: services: <name> (<provider>), …` is printed as before when a service appears or changes.

## Unloading a row

- **A row's cleanup can emit again** ([#1041](https://github.com/arcships/rutis/issues/1041), [#1050](https://github.com/arcships/rutis/pull/1050)). The row used to be withdrawn the moment `rows.unload` went out, so `ctx.emit` in a cleanup failed with `row <row> is not loaded in this runtime` and the rest of that cleanup did not run; Cordis handed the error to its logger, and with no logger it said nothing. What is withdrawn now is the row's **listeners**: its entries leave the listener table when the unload starts, the row still counts as loaded, and what a cleanup emits is dispatched as usual — the other rows' listeners hear it, and the row's own do not, so it cannot re-enter. That lasts until the runtime answers `rows.unload`: after the answer its emits are refused as before (`BindingError`, `row <row> is not loaded in this runtime`) and the emits it queued are dropped. A cleanup's fire-and-forget `emit` can still be dropped when that answer goes out; wait for it (`parallel`, `serial`) to be sure it arrives. Cordis plugins that add `turn/end` and `session/flush` in dispose (DSH and the like) therefore behave as they do under Cordis itself. All six languages (Node, Bun, Python, Go, Kotlin, Swift) agree, the conformance list has the case `unload/cleanup-emits`, and a listener registered from the unload stack is still not kept (Go and Swift say `row <row> is not active`, Node's Cordis fiber `INACTIVE_EFFECT`). See [Plugin API: events](../guide/plugin-api.en.md#events).

## The two from 0.20.0's release gate

- **`dev` no longer reports a row that is on its way back as `stopped`** ([#1044](https://github.com/arcships/rutis/issues/1044), [#1051](https://github.com/arcships/rutis/pull/1051)). After a reload, the rows that use the reloaded row are `Pending` / `Loading` for a while; `dev` used to take one snapshot, call that "on its way back" a `stopped` row, and then never say it came back. A row that restarted and is on its way back (loading its new version, or waiting for a row that is itself on its way back) is now `restarted`, its state line says `waiting for …` until it runs (`caller: waiting for weather (row weather has not provided it)`), and `running` once it does; `stopped` is only for rows that are not coming back (`failed`, gone, or waiting for a service nobody provides any more).
- **The remote runtimes' tests wait for the hello frame** (same #1044, [#1051](https://github.com/arcships/rutis/pull/1051)). The heartbeat timer can write a ping ahead of the frame a test waits for, and the tests assumed hello was the first frame, so they occasionally read the wrong one and failed the release gate; they now wait for `"op":"hello"`, and print the frames they did read when it does not come. Tests only: no behaviour changes.

## Behaviour changes

| Where | Before | Now |
| --- | --- | --- |
| `dev`: a test file, a document, an image or a lockfile changes | The project's own row reloads, and the rows that use it restart | Nothing happens |
| `dev`: a test run writes a `coverage/` report | Reload as above | Nothing happens |
| `dev`: the project lives under a `tests` directory | The whole project counted as test files | Reloads the files a plugin loads, as usual |
| `dev --debug`: the Node inspector | Pinned to `127.0.0.1:9229` | Still that unless set; `RUTIS_NODE_INSPECT` changes the address, a malformed one is refused before start |
| `dev`: no row provides a service | `services: none` at every start and rebuild | Nothing printed |
| `ctx.emit` in a cleanup while its row unloads | `row <row> is not loaded in this runtime`, the rest of the cleanup does not run | Dispatched; the other rows hear it; refused (`BindingError`) once `rows.unload` is answered |
| `dev`: a row that restarted and is on its way back | Reported as `stopped` | `restarted`, its state line `waiting for …` |

## Compatibility

- Nothing changes in a plugin, `rutis.json` or `rutis.dev.json`. The session protocol is still 4, `rutis.json`'s `format` is still 1, and the plugin API version is unchanged: no new handshake limit between a host, a runtime and an SDK.
- `rutis.json` and dsh's user layer are unchanged: the persisted samples are copied from 0.20.0, which this version adds no fields to, and what they read as is the same.
- `RUTIS_NODE_INSPECT` is for the Node inspector of `dev --debug` only; unset, the address is still `127.0.0.1:9229`.
- dylib plugins are rebuilt with the 0.20.1 SDK, as with every release.
