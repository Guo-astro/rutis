# 跨进程调用链里的会话标签（设计稿）

[English](design-session-tags-2026-10-12.en.md)

状态：已实现（本 PR）。日期：2026-10-12。基准：`main` `41c4c00`。Issue：#325（S4 场景 #188 中发现）。
依据：[质量规范](quality-standard.md) Q6.2.8、Q6.13.2、Q9.1、Q9.2.2、Q9.2.3、§9.3；[多语言 M1 设计](design-multilang-m1-2026-10-04.md) §7.2（`rebase`）；[多语言运行时设计](design-multilang-runtimes-2026-10-03.md) §九（同步等待环检测，#228 策略 B）；[远程插件设计](design-remote-plugins-2026-10-03.md) §6.2。

## 一、结论

| # | 结论 | 章节 |
| --- | --- | --- |
| C1 | 原因：会话标签（`s1`、`s2`…）来自进程内计数器，只在一个进程内唯一；调用链经 link 跨进程原样传递，另一个进程把对方的 `s1/…` 当成自己会话 `s1` 的条目还原，与自己的调用号相撞 | 二 |
| C2 | 调用链里的一个条目要在**链经过的所有进程**中唯一地指出"哪个会话的哪个调用"，并且只有这个会话所在的进程把它还原成原生调用号 | 三 |
| C3 | 选方案 A：标签改为 `s` + 进程随机数（15 位十进制）+ 计数器。线格式、帧的含义都不变，`rebase` 和等待环检测的逻辑不变 | 四、五 |
| C4 | 不需要协议版本变化（§9.3）：标签仍是 `s[0-9]+`，四种运行时的 origin 校验照常接受；新旧版本混用时新标签不会和旧标签相撞 | 五 |
| C5 | 现有验证没发现它，是因为多跳测试都在一个进程里（标签天然唯一），违反了 Q6.13.2"两个独立的宿主进程之间验证"；补上两进程的重现测试，S4 全场景去掉 `#[ignore]` | 六 |

## 二、现状（基准 `41c4c00`）

- `crates/rutis-bridge/src/session/rpc.rs:495`：`static NEXT_TAG: AtomicU64 = AtomicU64::new(1)`；`:806` 每个会话 `tag: format!("s{}", NEXT_TAG.fetch_add(1, …))`。每个新进程都从 `s1` 开始。
- `rpc.rs:485` `rebase(path, from, to)`：不带标签的条目加上 `from` 的标签；带 `to` 标签的条目去掉标签、还原为 `to` 里的原生调用号；其他带标签的条目原样保留。调用处：`rpc.rs:994` `forward`、`:1000` `forward_async`（`services.rs:297`、`:306`，`runtime/rows.rs:56`），`rpc/relay.rs:51`（引用的 origin）、`:117`（中继转发）。
- `rpc/waits.rs:135` `decode`：把 `s1/node:3` 解成"会话 `s1` 的调用 `node:3`"，用于等待环检测（`:149` `forward`）。等待表是宿主（进程）范围的。
- 接收方的校验：Rust `rpc.rs:1589`、Node `node/rutis-runtime/src/session.mjs:320`（以及 Python、Bun、Go 的同一检查）——调用帧的 `path` 含本帧 `id` 时判为非法帧并**结束整个会话**。
- origin 条目的格式校验：Node `session.mjs:143-144`、Bun `bun/rutis-bun/src/session.ts:149-150`、Python `python/rutis/rutis/peer.py:51`、`:54`、Go `go/rutis/internal/peer/peer.go:40-41`：`^(node|rust|s[0-9]+/[a-z0-9-]+):[1-9][0-9]*$`（compat）、`^(s[0-9]+/)?[a-z0-9-]+:[1-9][0-9]*$`（端点格式）。嵌套标签 `s1/s2/node:1` 被各自的测试明确拒绝（`node/rutis-runtime/test/session.test.mjs:92`、`python/rutis/tests/test_origin_ids.py:14`、`go/rutis/internal/peer/peer_test.go:367`）。

#325 的过程（两个进程 A、B，都是先开运行时会话、后开 link，标签序号相同）：

1. A 的运行时调用宿主（A 会话 `s1` 里的 `node:6`，链上还有 A 宿主发出的 `rust:7`），宿主经 link 转发：`rebase` 后链为 `["s1/rust:7", "s1/node:6"]`。
2. B 从 link（B 的 `s3`）收到，转给 B 的运行时会话（B 的 `s1`）：`rebase(…, "s3", "s1")` 把 `s1/rust:7` 当成 B 自己的条目还原为 `rust:7`。
3. B 宿主这次调用自己运行时用的 id 恰好也是 `rust:7`：帧 `{"id":"rust:7","path":["rust:7","node:6","s3/a:3"]}`，运行时判为非法帧，结束会话。

id 不相同时也错：B 把 A 的调用当作自己正在同步等待的调用（反向调用投错线程），等待环检测（`decode`）把 A 的调用算进 B 的会话，可能误报或漏报。

## 三、一个条目要标识什么

调用链（`path`）的作用：被调方认出"这个进来的调用属于我正在同步等待的那个调用"（在等待的线程上嵌套执行，不死锁）；宿主据此建等待图（调用链边）。所以：

- R1 一个条目在链经过的所有进程里唯一地指出（会话，调用号）；链跨任意多个进程、往返任意次都不歧义。
- R2 回到所属会话时还原为原生调用号（运行时只认识自己的原生调用号，`session.mjs:342` 等）。
- R3 等待环检测（#228 策略 B）照常：每个宿主只对本进程的会话建图；别的进程的条目不能被解成本进程的会话。
- R4 尽量不改线格式与帧含义；必须改则按 §9.3 作为协议版本变化处理。

## 四、方案

| 方案 | 做法 | 线格式 | 评价 |
| --- | --- | --- | --- |
| **A 进程随机前缀**（采用） | 标签 = `s` + 进程启动时生成的 15 位十进制随机数 + 计数器。条目跨进程原样传递，只有标签所属的进程会把它还原 | 不变（仍是 `s[0-9]+/<id>`） | 改动一处（标签的生成）；`rebase`、`decode`、运行时都不改。唯一性是概率性的：两个进程的随机数相等的概率约 10⁻¹⁵；标签变长（约 17 个字符） |
| B 用端点 id 限定 | 条目写成 `<端点 id>/s1/rust:7` 或 `s1@a/…` | **变**：四种运行时的 origin 正则拒绝（含 `/` 的多段或非数字标签）；compat 会话没有端点 id；`rutis-host` 之外嵌入的宿主不一定有端点 id | 确定性唯一，但要协议版本变化、所有 SDK 同步升级 |
| C 在 link 边界嵌套 | 从 link 收到的带标签条目再加一层本 link 会话的标签（`s3/s1/rust:7`），发回时去掉 | **变**：嵌套标签被运行时拒绝（见二）；而且接收方分不清线上的 `s1/…` 是"对方的 s1"还是"我自己发出去又回来的 s1"，要再加一种标记 | 往返时必须区分"你的"和"我的"标签，这正是线格式里没有的信息 |
| D link 边界的别名表 | 每条 link 维护（对方标签 ↔ 本地别名）表，收发时互换 | 形式不变，**含义变**：线上标签属于哪一方的命名空间要双方约定；旧版本对端不知道约定 | 有状态（表的清理、重连）；和 C 一样要区分方向；新旧混用时不能工作 |

方案 A 的边界：

- 随机数来自 `getrandom`（已是 rutis-bridge 的依赖）；取不到系统随机数时退回到标准库 `RandomState` 的随机键、进程号和时间的哈希，仍随进程不同。
- 同一进程里的标签仍由计数器区分，固定 15 位的随机数在前，所以不同进程的标签只有在随机数相等时才可能相同。
- 旧版本（计数器标签 `s1`…）的标签最多十几位，与新标签（16 位以上）不会相等：新旧混用时，只有两个旧进程之间仍有 #325，升级任一方即可。

## 五、决定

采用方案 A（`crates/rutis-bridge/src/session/rpc.rs` `next_tag`）。

- 线格式、帧字段、握手、能力都不变，不是 §9.3 的不兼容变更；不需要协议版本变化，也不需要修改 Node、Python、Bun、Go 运行时（它们只对标签做 `s[0-9]+` 的格式校验，新标签满足）。
- 多方交互规则不变（Q6.2.8）：`rebase` 的三条规则、等待图的三类边都不变。[`specs/cross-runtime-sync`](../specs/cross-runtime-sync/README.md) 的模型把每个调用当作不同的身份；本修复恢复的正是这个前提，不需要重新做模型检查。跨进程的等待环仍不在检测范围内（每个宿主只看自己的表，与 #228 一致）。

行为与级别（Q9.1.1）：

| 行为 | 级别 |
| --- | --- |
| 调用链经 link 跨任意多个进程、往返任意次，每个进程只把自己会话的条目还原为原生调用号；另一个进程的调用不会被当成本进程的调用（不因此结束会话，不投错等待线程，不进入本进程的等待图） | 契约行为（`bridge/call-chains-across-processes`） |
| 标签的具体形式（`s` + 15 位随机数 + 计数器） | 实现细节（只锁定"仍满足 `s[0-9]+`"，因为它是线上可见的格式约束） |

风险评估（Q4）：影响高（远端运行时结束整个会话，经过它的调用全部失败，本机运行时不会被重新拉起）；可能性中（两个进程、各有本机运行时、调用链穿过 link，S4 里 5 次 3 次）——P0。控制：两进程的确定性测试在每次 CI 运行（rutis-bridge 测试），S4 全场景在 `e2e` 任务运行。

组件类型：Q6.2 跨进程协议、Q6.13 分布式与网络节点。Q6.13.2 要求在两个独立的宿主进程之间验证：新测试就是两个进程。

验收条件：

1. `crates/rutis-bridge/tests/session_tags.rs` 在 `main` 上失败（B 的运行时会话以 `invalid invocation identity/path` 结束），修复后通过；
2. `tests/e2e/tests/migration.rs::an_implementation_moves_from_python_to_a_node_to_rust_while_the_host_runs` 去掉 `#[ignore]`，本机连续 ≥ 20 次通过；
3. 标签满足 `s[0-9]+`，同一进程的标签共用随机数（`rpc/tests.rs::sessions_have_distinct_tags_and_forward_rebases_the_current_chain`）；
4. rutis-bridge、rutis-loader（含 `sync_cycles`）现有测试不变地通过。

## 六、验证

- 重现（Q9.2.2）：`session_tags.rs::a_call_chain_crossing_processes_keeps_each_process_s_calls_apart`。测试进程把自己的可执行文件作为两个子进程 a、b 启动（全新进程，标签序号确定），a、b 各有一个进程内的"运行时"会话（端点格式的 Rust 远端），并以 TCP 上的 link 相连。a 的运行时同步调用经 link 到 b 的运行时，b 的运行时再经 link 回调 a 的运行时（a 仍在同步等待第一次调用）。在 `main` 上每次都失败，失败信息与 #325 相同。
- 为什么现有验证没发现（Q9.2.3）：`multihop.rs`、`websocket_multihop.rs`、`fault_links.rs` 的多跳场景，以及 rutis-loader 的 `sync_cycles.rs`，所有节点都在一个测试进程里，共用一个计数器，标签天然唯一。缺的是"调用链穿过两个独立进程"这一类验证（Q6.13.2）。补上的就是这一类：两进程测试成为 rutis-bridge 测试的一部分，以后改 `rebase`、标签或中继时都会跑到；S4 全场景从 E2E 层面覆盖同一点。
