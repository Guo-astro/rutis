## 一、决策

| # | 决策 | 章节 |
| --- | --- | --- |
| D1 | 应用里的能力按 rutis 插件范式编写（`inject` / `provides` / `apply(ctx, config)` / `effect`），与其他语言的插件是同一个概念 | 三 |
| D2 | 插件的装载、配置、卸载由 rutis 驱动，应用不自行决定 | 三 |
| D3 | 插件编译进应用，随应用发布；设备上不装载新代码 | 三 |
| D4 | SDK 对应用只提供 `start` / `stop`；前后台、保活、唤醒属于业务层 | 四 |
| D5 | 应用连上时报它带的插件（`mount` 回复的 `plugins`，内容与 `--rutis-manifest` 的 `plugins` 相同） | 五 |
| D6 | 装哪些插件、用什么配置，由 rutis 配置里的行决定；应用带了、配置里没有的插件不装 | 五 |
| D7 | rutis 不建模设备：设备号、设备信息等是普通插件提供的服务；rutis 只做插件发现与连接 | 三 |
| D8 | 不设别名：多个应用连接带同名插件时，每条连接是一个实例，同名服务在各自实例内解析 | 五 |
| D9 | 应用推荐按 IP / 服务器名拨出到 rutis 的接入点（各 SDK 也支持监听，见拨出稿 R1）；连接、实例、身份、重连全部按拨出稿 | 六 |
| D10 | SDK 原生实现（Swift / Kotlin），不内嵌 Rust | 八 |

## 二、需求

核心需求：让 rutis 能使用 Apple 与 Android 设备上的能力（通讯录、通知、定位、健康数据、应用自身功能等）。

| 现实约束 | 对设计的影响 |
| --- | --- |
| 移动平台上开发者交付的是**一个应用**（签名、商店或侧载分发） | 集成单位是应用，插件随应用发布（D3） |
| 同一应用跑在不同设备、不同系统版本上，系统给的后台权限不同 | rutis 不对是否在线做假设，只看服务"在"或"不在"（D4）；设备差异由插件自己处理与提供（D7） |
| 设备在 NAT 后、地址会变、会休眠 | 应用拨出（D9） |
| 系统权限由用户授予在应用上 | 权限被拒 = `apply` 或方法调用失败，是范式内的普通错误 |

## 三、模型

```text
rutis（桌面 / 服务器）                          设备上的应用
 ├─ 接入点（监听，wss）  ◀──拨出──────────────  ├─ 业务代码：决定何时 start / stop
 ├─ 每条连接一个实例                             ├─ rutis SDK
 │    └─ 配置里的行：装哪个插件、用什么配置      │    └─ 编进应用的插件定义（范式）
 └─ 同实例的行按名字 inject 应用提供的服务      │         如 health、contacts、device
                                                 └─ 系统 API（授权归属应用）
```

- 范式与 [插件 API](guide/plugin-api.md) 一致：插件声明依赖与提供的服务，`apply` 里用服务、提供服务、登记清理；配置来自 rutis。
- 同一个插件定义既可以在 Mac 上 `serve` 成二进制，也可以交给应用托管（Swift SDK §二）。
- 插件之间：同一应用内互调拿对象本身；跨连接、跨语言按名字经 rutis。
- rutis 的职责只有两件：插件发现与连接。设备号、型号、系统版本等由插件提供（例如一个 `device` 插件），需要的行 `inject` 它即可。

## 四、SDK 对应用的面

| 原语 | 语义 |
| --- | --- |
| `start()` | 连上 rutis，报带的插件，此后插件由 rutis 驱动装载；断线自动重连，直到 `stop()` |
| `stop()` | 全部插件逆序清理，然后断开；可再次 `start()` |

SDK 保证：

- 无论 `stop`、网络中断还是进程被系统终止，rutis 侧看到的都是同一件事：实例关闭、服务撤销、使用者停下。
- 重新连上后按 rutis 当前配置重新装载，不依赖上一次连接的状态。
- 插件要持久化的数据由插件自己用平台存储 API 处理，SDK 不提供存储契约。
- 连接状态可观察，供业务层显示；SDK 不据此做任何生命周期决定。

SDK 不做：前后台切换处理、后台保活、推送唤醒、电池优化引导、权限对账。

## 五、装载与命名

- 应用带的插件：`mount` 回复的 `plugins`，每项与 `rows.schema` 回复相同（插件名、版本、`inject`、`provides` 与方法形状、配置 schema），不含设备信息。
- 装载沿用 rutis 现有的行：配置里写一行指向应用里的插件并给出配置；应用连上、带了这个插件，这一行就在该连接的实例里装载；没带则这一行在该实例里失败并说明"该连接不含插件 X"，不影响其他实例。配置写法见拨出稿 §四。
- 应用断开：实例关闭，这些行停下，使用者随之停下；重连后重新装载。
- 多连接同名插件 = 实例（[按需创建实例](design-loader-instance-mounts-and-services-2026-10-07.md)、[实例内服务名](design-instance-services-2026-10-08.md)）：实例内的服务名在本实例内解析，同实例的使用者只看到这条连接的服务；实例外的行不能使用某个实例的服务。
- 实例外（全局）同名服务仍按现有规则：后注册的被拒绝。

## 六、连接

全部按 [远程运行时：拨出与动态接入](design-remote-runtime-dial-2026-10-14.md)：

- 应用按 IP 或服务器名拨出到 rutis 的接入点；非回环必须 `wss://`（拨出稿 §三）。
- 每条连接一个实例（拨出稿 §四）。
- 连接以应用自报的 id 区分，过渡期用共享 token；身份、配对、吊销由将来的管理服务负责（拨出稿 §五）。
- 重连、同 id 接管、断开即关闭实例按拨出稿 §六，Swift / Kotlin 过同一套一致性测试。

## 七、平台参考（业务层，非 SDK 义务）

| 平台 | 后台能力 | 业务层常见做法 |
| --- | --- | --- |
| macOS 应用 | 可常驻 | 登录项、菜单栏应用，常开 |
| iOS / iPadOS | 切后台后很快挂起；仅少数类别可在后台运行 | 前台 `start`、后台 `stop`；需要时用推送唤醒后短暂 `start` |
| Android | 前台服务可常驻（带常驻通知，Android 14 起须声明类型）；厂商系统可能杀进程 | 需要常驻时开前台服务并引导电池优化白名单；否则跟随界面 |
| watchOS / visionOS | 更受限 / 同 iOS | 暂不覆盖 |

接入注意事项（iOS 本地网络权限、各能力的 usage description、Android 前台服务类型等）写进各平台 SDK 指南。

## 八、实现：原生

Swift 与 Kotlin SDK 各自用原生代码实现会话协议、运行时契约与两个方向的连接，与 Python、Node、Bun、Go 一致；不内嵌 Rust（拨出稿 R8）。

| 考量 | 结论 |
| --- | --- |
| 判据 | 内嵌 Rust 连接模块只有在所有远程插件语言都能接受时才划算 |
| 各语言 | Swift、Kotlin 能接受；Python、Node / Bun 要维护按平台的预编译包矩阵；Go 只能走 cgo，破坏纯静态交叉编译，与 Go 运行时"只依赖标准库"冲突 |
| 本地多进程 | 本来就需要各语言原生的会话实现；Rust 模块只接管远程连接时收益很小，接管会话则要重写现有运行时 |
| 先例 | 现有各语言的远程运行时都是原生实现 |

- 两份实现的一致性由现有的会话与运行时一致性测试（`runtime_conformance`、`multilang`）加拨出稿的 `dial_conformance` 保证。
- 内嵌 Rust 只在"设备上运行 rutis 本体"的需求出现时再评估，另立设计。
