# rutis 设计哲学

[English](design-philosophy.en.md) · [内核设计](design-rust-port.md) · [内核能力一览](core-features.md)

本文说明 rutis 为什么是现在这个样子，以及以后判断一项能力该不该做时依据什么。具体机制见各设计稿；这里只讲出发点和由它推出的原则。

## 一句话

**rutis 是一个连接和适应用的躯壳，为能自我迭代的软件而设计。** 它用 Rust 提供稳定的插件基础设施，并通过多语言插件和远程插件连接更多的运行时、系统进程和设备，让宿主程序自己建立、认识和迭代它与环境之间的连接。

## 一、出发点

### 为能自我迭代、适应环境的软件而设计

当软件本身就是一个 agent，或者由 agent 开发时，它最重要的能力是快速与环境和周边打交道、建立连接，并且能认识和迭代自己与环境连接的方式。

这里发起连接的主体是软件宿主本身，而不是环境的维护者。MCP 这类协议解决的是另一侧的问题：环境的维护者把能力包装成服务端，宿主使用别人已经做好的东西，能接触到什么取决于别人做了什么。rutis 关心的是宿主一侧：宿主需要连接某样东西时，自己写一个插件（用最合适的语言，也可以由 agent 来写），装进来、试用、修改、替换。这两者并不冲突，一个 MCP 客户端也可以只是宿主装进来的一个插件；但能力边界不应由环境决定。

所以 rutis 要给宿主的，是"适应的能力"本身：

| 宿主需要 | rutis 提供 |
| --- | --- |
| 建立连接 | 用任何已接入的语言写插件，在本机、别的进程或别的机器上运行 |
| 认识自己的连接 | `diagnostics()` 列出每个插件的状态、依赖和服务绑定；服务名目录；插件声明的依赖与服务形状；清理树 |
| 迭代连接 | 开发模式下改文件即重载；配置热更新；换提供者时消费者自动重载；loader 按配置持续对账 |
| 在迭代中不出错 | 依赖门控、恰好一次的清理、失败回滚：频繁地装上、卸下、替换，也不会留下残留 |

### 插件系统是一个小型应用操作系统

程序一旦接受插件，就要回答操作系统要回答的那些问题：谁先启动，缺了依赖怎么办，一个部件被替换时谁要跟着重启，卸载有没有留下东西，部件之间怎样调用。rutis 把这些问题收进一个小内核，用同一套生命周期规则回答：

| 操作系统 | rutis |
| --- | --- |
| 内核：小、稳定、很少改 | `rutis` 内核，只依赖 tokio、tokio-util、thiserror |
| 进程 | 插件 fiber；语言运行时、远端节点、dylib 也都是插件 |
| 系统调用 | 服务：按名字或类型提供和使用 |
| 驱动 | 挂载与桥：Cordis 挂载、语言运行时插件、节点连接 |
| 调度与监管 | 依赖门控、依赖驱动重载、loader 按配置持续对账 |
| 资源回收 | 恰好一次、LIFO 的清理，失败时回滚 |
| 可观测性 | `diagnostics()`、清理树、投递前观察 |

### Rust 为核心，其他语言做连接

稳定的部分用 Rust：内核、生命周期、调度与清理，要求长期不出错。连接和适应的部分交给最合适的语言：Python 有 ML 和数据生态，Node 有 npm 和已有的 Cordis 插件，Swift 能直接调用 macOS 系统框架，远端节点能触及另一台机器上的设备和进程。这正是 agent harness 的形状：一个稳定的躯干，加上可以随时生长、替换的触手。一旦不再局限于某一种运行时和语言，能解决的问题和能接触到的资源会成倍增加。

### 从尝试到稳定是一条路径

尝试与稳定必然是一个流程，多语言运行时自然覆盖了从代码尝试到正式落地的整条路径：

1. **尝试**：用 Python 或 TypeScript 快速写一个插件，可以由 agent 生成，在 `rutis-host dev` 下改了就重载。
2. **验证**：作为 loader 的一行在真实宿主里运行，和其他插件按服务互相依赖，服务的名字和形状在这一步稳定下来。
3. **固化**：被时间验证过的部分改写成 Rust（编进宿主，或作为 dylib 插件），换取稳定性和性能。

每一步之间，使用这项能力的插件都不用改：对它们来说，只是同一个服务换了一个提供者（见原则 10）。这和 [双核架构](design-dual-core-2026-08-20.md) 的"TS 是实验室，Rust 收毕业生"是同一个思路，推广到了任何已接入的语言。

### 三个承诺

1. **稳定的基础设施。** 插件系统本身必须比跑在它上面的任何东西都稳定，并且容易扩展、容易长期维护。所以内核用 Rust 写，范式只实现一份，每一条语义保证都用测试钉住。
2. **连接更多运行时和进程。** 能力本来就分散在不同的语言栈、进程和机器上。多语言插件和远程插件不是附加功能，而是这个系统存在的理由：每接一种运行时或一台机器，宿主能用的能力就多一块。
3. **让宿主适应环境与设备。** 有了连接能力，宿主可以按环境取用当地的能力：在 macOS 上用系统框架，在服务器上用 Python 的 ML 生态，在另一台机器上用那里的设备。一项能力也可以按上一节的路径渐进地固化，使用它的插件不需要改动。

## 二、与 Cordis 的根本区别

rutis 的生命周期模型来自 [Cordis](https://github.com/shigma/cordis)，两者的核心语义一致，见 [逐条对拍](cordis-spec-parity-2026-08-18.md)。根本区别在于面对的世界不同：

| | Cordis | rutis |
| --- | --- | --- |
| 世界观 | 封闭世界：所有部件在同一个 Node 进程里 | 开放世界：部件分散在不同语言、进程和机器上 |
| 能力从哪来 | 框架内部的插件生态（npm 上的 Cordis 插件） | 连接外部已有的运行时、进程和生态，不自建生态 |
| 主要用户 | 大量插件作者 | 组装系统的宿主作者 |
| 价值所在 | 插件好写，生态好长 | 能连接、能适应的范围，以及在每条边界上都成立的生命周期 |
| 可以依赖什么 | JS 单线程、同一个对象世界、Proxy 等语言特性 | 只能依赖显式的契约：跨进程以后，任何隐式约定都会失效 |

所以 rutis 不是 Cordis 的翻译。凡是只在封闭世界里成立的机制，比如 Proxy 属性访问、traceable 与 caller-shadow、`Context.filter`、`internal/*` 钩子面，rutis 都不照搬；凡是开放世界里才会遇到的问题，比如多线程下的顺序、跨进程撤销服务、断线重连、协议版本，rutis 都当作一等问题处理。

## 三、由出发点推出的原则

### 内核

1. **范式只实现一份，在 Rust 内核里。** 依赖门控、启动停止、重载、清理、配置热更新只在 rutis 里有一份实现。其他语言一侧不复刻框架（[多语言设计](design-multilang-runtimes-2026-10-03.md) §二）。
2. **兼容工作在外层完成，不改内核。** 接一种新运行时、一个新协议，需要的适配都放在桥、挂载和运行时插件里（[挂载需求](requirements-protocol-plugins.md) §1）。内核只因自身语义需要而改变。
3. **保证要显式写出来，并用测试钉住。** 单进程里免费得到的性质，例如事件按发射序处理，在多线程和跨进程后都会消失。rutis 把需要的保证逐条重建，写进决策表，用确定性的测试固定（[内核设计](design-rust-port.md) D31）。不提供的保证也写明。
4. **扩展点按具体需求开，开得窄。** 不提供万能钩子面。有真实消费方时，针对那个动作边界开一个接口，例如投递前观察、服务读写拦截（[观察与拦截设计](design-cordis-observation.md)）。

### 连接

5. **连接到的东西都是插件。** 语言运行时、远端节点、Cordis 挂载都是普通插件或 loader 的行，受同一套生命周期管理：运行时进程崩溃，依赖它的插件停下；连接恢复，它们重新启动。连接本身不享有生命周期之外的特权。
6. **其他语言的插件是叶子。** 每种语言一个运行时插件、一个进程，语言一侧只要一个很小的 SDK：`apply`、使用服务、提供服务、返回清理。唯一的例外是 Node 一侧保留完整的 Cordis，因为要复用 npm 上已有的 Cordis 插件。
7. **契约只约定跨边界真正需要的东西。** 跨语言调用需要服务名和方法形状（同步还是异步），这些就是契约；不为此建通用的类型 IR 或代码生成层。需要强类型的场景，例如 Rust 应用挂载 Cordis 插件，在那一条边界上单独生成。
8. **跨边界后做不到的事写成边界规则，不假装做到。** 跨进程的 `emit` 只是通知、waterfall 不转发、同步调用不能等待对方事件循环，这些都写在[边界规则](requirements-protocol-plugins.md) §5 里。宁可明确说做不到，也不静默降级。
9. **按需隔离。** 默认一种语言一个进程，同进程调用不走 IPC；不稳定的插件可以单独放进另一个运行时实例。

### 适应

10. **换实现语言等于换提供者。** 同一个服务从 Python 实现换成 Rust 实现，对内核来说只是一次普通的提供者替换：旧提供者卸载，新提供者出现，消费者被驱逐后自动重新装载。依赖驱动重载在 Cordis 里服务于热插拔，在 rutis 里也是"换语言、换位置不停机"的机制。
11. **使用方不关心提供方在哪里。** 一个插件依赖 `llm`，它可以来自同进程的 Rust 插件、Python 插件，或者另一台机器。依赖声明里不出现语言和位置。
12. **配置描述期望状态。** loader 用分层配置描述要运行什么，并持续对账。环境变化时改配置，由 rutis 把现状收敛到配置所描述的状态，而不是由宿主手写启动和停止的顺序。

### 显式

13. **显式优于隐式。** 服务用 `require` / `get` 显式获取，依赖在声明里写明，`TypedPlugin` 在编译期核对依赖。服务要替调用方登记资源时，由调用方显式传入自己的 `Ctx`，而不是像 Cordis 那样隐式改写 `this`。隐式机制在同一个对象世界里很顺手，但跨不过进程边界。

## 四、判断一项能力该不该做

提出新能力时，依次问：

1. **它扩大了 rutis 能连接或适应的范围，或者让宿主更能认识和迭代自己的连接吗？** 接一种运行时值不值得，看它带来多少生态能力，而不是为了多支持一种语言。Python 带来 ML 和数据生态，Swift 带来 macOS 系统能力；只能传数据的 Shell 类语言用不上服务、门控和清理这套范式，做成命令型工具运行时，不进插件协议。
2. **它能放在内核之外吗？** 能放在桥、挂载、运行时插件、loader 或 host 里的，就不进内核。
3. **它跨过边界后还成立吗？** 只在单进程或单语言里成立的机制，不进入跨边界的契约；确实需要的，在单一边界上局部实现，并写明范围。
4. **它有具体的使用方吗？** 没有消费方的扩展点和兼容层不做，有了再按那个动作边界开窄接口。
5. **它的保证能写成测试吗？** 说不清、测不了的语义承诺不做。例如内核不承诺依赖环检测：服务可以动态注册，环无法证明。

## 五、还开放的问题

- **权限。** 现在的信任粒度是"可信对端"：`Host` 只对可信对端打开，同组插件共享地址空间、必须互信。连接的设备和外部运行时越多，越需要能力级别的授权：哪个节点、哪个插件可以提供或使用哪些服务。
- **契约的演进。** 服务名加方法形状足够支撑现在的跨语言调用；"先 Python、后 Rust"的固化路径如果要做到无缝，同一服务在不同语言里的数据形状也要保持一致，这一层目前靠约定。
- **依赖环诊断。** 内核不承诺环检测，但 loader 和 host 已经掌握插件声明的 `provides`，可以把疑似的环作为诊断信息报告出来。
