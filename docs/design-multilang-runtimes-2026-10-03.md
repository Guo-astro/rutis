# 多语言插件：每种语言一个运行时插件（设计稿）

状态：设计稿，未实现。日期：2026-10-03。M1 的实施设计见 [多语言插件 M1](design-multilang-m1-2026-10-04.md)。
依据：[多语言决策记录](decision-multilang-2026-10-03.md)（#107，本文修订其中几项，见 §十）、[Cordis 运行时插件化](design-cordis-runtime-plugin-2026-10-03.md)（#109）、[rutis-loader 设计](design-rutis-loader-2026-10-02.md)、[兼容层设计](design-protocol-plugin-mount.md)、调研报告 [plan/analysis/multilang](plan/analysis/multilang/README.md)。
基准：`main` `a078630`。

## 一、要解决什么

rutis 现在有两种动态加载插件的方式：dylib（Rust 插件，进程内）和 Cordis（JS 插件，经 `CordisRuntimePlugin` 在一个 Node 进程里运行）。两者都是 loader 的行，可以写在同一份配置里。

其他语言里也有值得接的东西：

- **Python**：AI/ML、数据处理、各种 SDK，agent 用的工具大多先有 Python 版。
- **Swift / Objective-C**：macOS 的系统能力，如日历、通讯录、辅助功能、屏幕录制、Core ML。
- **Go**：基础设施类库、云厂商 SDK、网络工具。

本文设计怎样接它们，同时避开 #107 担心的两件事：不在每种语言里重造一个插件框架，进程数也不随插件数增长。

不在本文范围：

- **Shell、PowerShell**：它们只能传数据，用不上服务、依赖门控和清理这套范式。它们的价值在于给 agent 当工具，应该另做"命令型工具运行时"（运行时发现、带 JSON Schema 的参数、可取消），不进插件协议。
- **远程**：插件跑在别的机器上是另一个问题，不和多语言绑在一起做（远程稿 #110 仍是草稿）。
- 各语言运行时的具体实现细节：本文只定模型、契约和分阶段。

## 二、结论先说

1. **一种语言一个运行时插件，一个运行时一个进程**。照 #109 的运行时插件：运行时插件拉起这门语言的进程，提供运行时服务；这门语言的插件都是依赖它的 loader 行，装进同一个进程。装十个 Python 插件也只有一个 Python 进程。
2. **范式只在 rutis 里有一份**。依赖门控、启动停止、重启、配置分层、热更新，都由 rutis 和 loader 负责。每个其他语言的插件在 rutis 里就是一个行，也就是一个 fiber。
3. **其他语言的插件是"叶子"**。语言那一侧只要一个很小的 SDK：插件有 `apply(ctx, config)`，在里面用服务、提供服务、返回清理函数。没有子插件和本地依赖图，所以不需要在 Python、Swift 里复刻 Cordis 或 rutis。事件只有一条总线，由宿主分发（[事件协议](design-events-protocol-2026-10-18.md)）：`ctx.on` / `ctx.emit` 的监听器和宿主里的监听器在同一张表里，按登记顺序调用；监听随插件卸载注销，`internal/*` 不跨边界；`emit` 的监听器失败只在监听器所在的一侧报告，不影响发出方，也不结束进程。插件 API 为 3。
4. **Node 仍是完整的 Cordis**。因为要复用 npm 上已有的 Cordis 插件，它们之间本来就按 Cordis 的方式互相依赖。这是唯一需要完整框架的一侧。
5. **同进程的调用直接完成**。同一个运行时里的两个插件互相用服务时，调用在本地直接完成，不走进程间通信。rutis 只管"谁依赖谁、谁先停"，不经手调用本身。只有跨语言的调用才走 IPC（同步调用约 30µs，是 Node 侧实测的数字）。
6. **隔离按需多开**。不稳定的插件可以单独放进另一个运行时实例。这和现在"需要隔离的插件放进不同挂载"是同一条规则，默认不这么做。
7. **两类运行时**：
   - **按名字加载代码的**（Node、Python、Swift）：一个进程按名字装载多个插件，Swift 用 `dlopen` 加载插件 bundle（M3 设计已改为与 Go 相同的编译好的程序，见 [Swift SDK](design-swift-sdk-2026-10-12.md) 附录 A）；
   - **插件就是编译好的程序的**（Go）：Go 不能在运行时可靠地加载代码，一组插件编译进一个可执行文件，作为一个运行时进程拉起；换代码就是换二进制、重启这组插件。
8. **契约复用现在的协议**，不为这件事升协议版本：帧、引用、取消、同步调用链和 `rows.*` 控制操作都照用（§五）。要补的是服务按名字投到 rutis，以及方法形状（同步还是异步）。
9. **运行时不依赖任何行的服务**。运行时插件只依赖它启动本身需要的东西；插件要用的服务（宿主的或其他语言的），门控都落在具体的消费行上，调用路由在运行时启动后动态绑定和撤销。这样不同语言的插件互相使用服务时，运行时之间不会互相等（§四）。
10. **行分两段放行**。运行时进程起来后先提供 `<语言>Runtime`；再用它刷新绑在这个运行时上的行的解析结果（拿到插件声明的依赖），然后才提供 `<语言>RuntimeRows`，行依赖的是后者。插件声明的依赖只有进程起来后才读得到，这样可以保证行启动时依赖声明已经完整（§六）。
11. **先 Python，再 Swift，Go 等有具体需求再做**。

## 三、现状里能直接用的

| 现在有的 | 在本文里的角色 |
| --- | --- |
| `CordisRuntimePlugin`（#109）：拉起 Node 进程、注入宿主服务、提供 `CordisRuntime`、崩溃时撤销服务、不自动重启 | 运行时插件的样板，其他语言照这个模式各写一个 |
| `InteropResolver` + `JsRow`：按名字解析、行依赖运行时服务、`rows.load / update / unload / schema` | 行和运行时之间的控制操作，语言无关 |
| 线协议：帧、函数和异步结果引用、计数释放、`cancel`、`path` 调用链、`SyncWaitCycle` | 运行时进程和 rutis 之间的会话，语言无关 |
| `host_key` 宿主服务 | 其他语言的插件用 rutis 服务的方式 |
| Python runner 调研（`python.md`）：原型通过了嵌套同步回调、`SyncWaitCycle`、取消、无关调用延后，同步往返约 25–60µs | Python 运行时的会话层可以直接照这个原型做 |

协议里的调用号前缀是本端端点 id（§九），Rust 不再只接受 `node:` 开头。跨语言的运行时都用这一规则，不升协议版本。

## 四、模型

```text
rutis 宿主
 ├─ CordisRuntimePlugin ── Node 进程（完整 Cordis）── JS 行 × N
 ├─ PythonRuntimePlugin ── Python 进程（叶子 SDK）── Python 行 × N
 ├─ SwiftRuntimePlugin  ── Swift 辅助进程（叶子 SDK）── Swift 行 × N（bundle）
 ├─ GoRuntimePlugin     ── Go 可执行文件（一组插件编译在一起）
 ├─ dylib 行（进程内）
 └─ LoaderPlugin：所有行的期望状态
```

**运行时插件**（每种语言一个类型，可以有多个实例）：

- 配置：启动命令、项目位置（venv、bundle 目录、可执行文件）；
- 依赖：只有进程启动本身需要的东西，通常什么都不依赖。**插件要用的服务不放在这里**：#109 现在把宿主服务写进运行时的 `injects`，只有一个运行时时还行；有多个运行时，而且它们互相使用对方行提供的服务时，就会出现运行时之间互相等的环（Python 运行时等 JS 行的服务，JS 行等 Cordis 运行时，Cordis 运行时又等 Python 行的服务）。所以 M1 把宿主服务也从运行时的依赖里移出，改为按行门控（§五）；
- 提供，分两段（键都带实例名，例如 `TypeKey::keyed_dynamic::<PythonRuntime>("py")`，这样同一种语言可以开多个实例）：
  1. 进程起来、握手完成后，提供 `<语言>Runtime`；
  2. 用它刷新绑在这个运行时上的行的解析结果（§六），完成后提供 `<语言>RuntimeRows`；
- 进程崩溃时两个服务都撤销、不自动重启，是否重启由应用决定（与 #109、#71 一致）。

**插件（行）**：

- 依赖：所在运行时的 `<语言>RuntimeRows`，加上插件自己声明的依赖（§六）。它用到的其他服务，由这一行自己等，不由运行时等；
- apply 时请运行时装载插件，清理时卸载；只改易变字段的更新就地提交（照 #101 的做法）；
- 插件提供的服务投到 rutis，别的语言、Rust 插件都能按名字使用（§五）。

**放置**：行名带上运行时前缀，例如 `py:weather.plugin`、`swift:Calendar.bundle`、`go:tools/ping`。不带前缀的 npm 包名照旧走 Cordis 运行时，`dylib:` 照旧。前缀后面的部分由运行时自己解析：Python 是模块名，Swift 是 bundle，Go 是"可执行文件里的插件名"。

## 五、运行时契约

运行时进程和 rutis 之间的契约，就是现在 Node 运行时实现的那份，加三处补充：

| 项 | 现状 | 补充 |
| --- | --- | --- |
| 启动 | 固定执行 `node --import tsx runner.mjs` | 运行时插件的配置里给出启动命令；参数仍是 socket 路径和项目位置 |
| 装载 | `rows.load(key, entry, config, isolate, inject)` | `entry` 由运行时自己解释（模块名、bundle、插件名）。`isolate` 只对 Cordis 有意义，叶子 SDK 可以忽略 |
| 描述 | `rows.schema(entry)` 返回配置的 JSON Schema | 改成同时返回插件声明的依赖（§六），以及它提供的服务及其方法形状 |
| 服务 | 行模式下，行提供的服务不投到 Rust（`InteropResolver` 的现状） | 运行时用现有的服务槽位通知报出行提供的服务；rutis 按名字注册成服务，键为 `TypeKey::keyed_dynamic::<RemoteService>(name)`，并登记进 loader 的服务名目录 |
| 方法形状 | 只有构建期生成的挂载知道方法是同步还是异步 | 运行时报服务时一并报出每个方法是同步还是异步：Python 用 `inspect`，Swift 由 SDK 登记时声明。Node 的做法见 §九 |

调用方向：

- **其他语言的插件用 rutis 服务、或用另一种语言的服务**：走现有的 `host:<名字>` 调用。rutis 在调用时按名字找到这个服务的当前提供者，如果它来自另一个运行时，就转发过去。路由是动态的，运行时启动时不需要这些服务存在：
  - 叶子 SDK 的 `ctx.use(name)` 返回一个按名字调用的代理。消费行把 `name` 列在依赖里，所以 rutis 只在服务存在时启动它，服务撤销时让它停下；
  - Cordis 插件靠 Cordis 原生的 `inject` 等服务，所以 rutis 在服务出现、撤销时，用控制操作 `hosts.provide / hosts.withdraw` 在 Node 运行时的 Context 里动态注册、撤销对应的代理，取代 #109 那种启动时一次注册。转发要用到跨会话的引用转交（现在 `rpc.rs` 明确不支持），这是 M1 里唯一较大的会话层改动。
- **转发时改写调用链**：同步调用带着 `path`，对端拿它和自己正在等待的调用号比对，判断一个反向调用是否属于自己的调用链。所有运行时都用 `node:` 前缀，调用号只在各自的会话里唯一。所以 rutis 把一个会话里的调用转发到另一个会话时，要把 `path` 里来自其他会话的调用号加上会话前缀改写（例如 `py/node:3`），否则对端可能把它误认成自己的 `node:3`，造成错误路由甚至死锁。改写后的条目永远对不上对端的调用号，同一会话内的条目保持原样。Node 侧和 Rust 侧对 `path` 条目都只要求是字符串，所以不需要改协议。
- **同一个运行时里的插件互相使用**：运行时在本地直接把对象交给使用方，不经过 rutis。

## 六、叶子 SDK

Python 的形状（示意）：

```python
# weather/plugin.py
inject = ["llm"]                 # 声明依赖：rutis 等它就绪才启动，它撤销就停下

def apply(ctx, config):
    llm = ctx.use("llm")         # 用宿主、其他插件或其他语言提供的服务
    ctx.provide("weather", Weather(llm, config["city"]))
    return lambda: ...           # 清理
```

Swift 的形状（示意）：

```swift
final class CalendarPlugin: RutisPlugin {
    static let inject = ["llm"]
    func apply(_ ctx: Context, config: Config) async throws -> Cleanup {
        ctx.provide("calendar", Calendar(store: EKEventStore()))
        return {}
    }
}
```

SDK 只做这几件事：

- 插件入口（`apply`、`inject`、配置类型，配置类型可以导出成 JSON Schema）；
- `ctx.use` / `ctx.provide`：同进程直接给对象，跨进程给代理；
- 运行时进程：实现 §五 的契约，以及同步等待期间的重入（Python 的做法见调研 §3：I/O 线程加主线程按调用链执行反向调用）。

依赖写在插件里（`inject`），由 `rows.schema` 报给 rutis，rutis 把它写进这一行的依赖声明，于是原生门控生效。插件之间的依赖、启动顺序和停止顺序，全由 rutis 决定，SDK 里没有依赖图。

依赖只有运行时进程起来后才读得到。如果行在运行时启动前就解析了（#109 的 `InteropResolver` 这时返回没有 schema、只依赖运行时的结果），运行时一出现它就会直接启动，`inject` 还没拿到，可能在 `llm` 未就绪时就执行 `apply`。所以运行时插件在两段之间做一件事：

- 提供 `<语言>Runtime` 之后、提供 `<语言>RuntimeRows` 之前，用 loader 的公开 API（`entries()` + `reload(id)`）重新解析绑在这个运行时上、离线时解析的或版本已变的行，拿到完整的依赖声明；
- 这些行此时都在等 `<语言>RuntimeRows`，`reload` 不会让它们启动。依赖声明变了会重建 fiber，也不会让它们启动；
- 刷新完成后再提供 `<语言>RuntimeRows`，行按完整的依赖声明等待和启动。

这和远程稿修复启动循环时用的两段放行（`Peer` / `PeerRows`）是同一个做法。

## 七、各语言的要点

| 语言 | 运行时进程 | 要点 |
| --- | --- | --- |
| Python | 一个 Python 进程，按模块名装载 | 照调研原型实现会话层；每个运行时实例用一个锁定的环境（uv 项目），环境冲突时开第二个实例；需要 Python 3.10 或更高（3.10、3.11 上的 eager start 由 rutis 实现，见 [Python 3.10 设计](design-python-310-2026-10-11.md)） |
| Swift / ObjC | 一个签名的辅助程序，用 `dlopen` 加载插件 bundle（已修订：一个插件组一个签名二进制，另有应用托管，见 [Swift SDK](design-swift-sdk-2026-10-12.md)） | 系统授权（TCC）记在辅助程序上，所以它必须有自己的签名和用途说明；ObjC 代码由 Swift 侧直接调用；只支持 Apple 平台 |
| Go | 一组插件编译进一个可执行文件 | 不用 Go 的 `plugin` 包；换代码要重新构建并重启这一组；构建由部署方负责，宿主不临时编译 |

## 八、进程与效率

- 进程数等于用到的运行时实例数：一种语言默认一个，Go 是一组一个，需要隔离时才多开。
- 同一个运行时里的调用不走 IPC。
- 跨语言的同步调用约 30µs（Node 实测），Python 调研给出的是 25–60µs。对热路径上的高频调用，应该把调用双方放进同一种语言，或者改用异步方法。

## 九、行协议、同步等待与明确不保证

会话层（帧、值、引用、取消、大小上限、畸形帧）的现行规格是[会话协议规格](protocol-session.md)；行协议（`rows.*`、`hosts.*`、`mount`、`service`、行的结束与失败）的现行规格是[行协议规格](protocol-rows.md)。这一节只写多语言相关的部分：跨语言的服务投递、同步等待怎么检测，以及实现有意不承诺什么。

**行协议的多语言落点。** 方法形状跟着服务走：`HostDispatch::methods()`，没有时由租用它的地方给出（M1 §4.1）。事件不分语言，见[事件协议](design-events-protocol-2026-10-18.md)。调用号的本地前缀是本端端点 id（宿主给运行时的名字，如 `node`、`py`），不再是写死的 `node:`。

**同步等待的检测。** 只有标了同步的调用可能计入等待图：调用帧（`invoke`、`call`、`get`、`await`）带 `sync: true` 时，调用方在同步等待它（Cordis 插件的 `emit` 与 `waterfall` 也这样发）。握手能力 `reentrant-sync` 与 `sync-stack` 决定运行时的等待形状：不声明 `reentrant-sync` 的按不可重入处理；"延后"和"栈顺序"两类边只用于声明了 `sync-stack` 的对端。宿主按 `crates/rutis-bridge/src/session/rpc/waits.rs` 的 `forward` 给每次转发分类：

- 调用链的最后一项是已标记的调用（本端收到过带 `sync` 的调用），这次转发是**一跳**；调用方在同步等待、但链上没有已标记的调用（宿主自己发起的同步调用、同步分发）也是一跳，`src` 为空（#537，PR #597）。
- 链的最后一项已标记、但这次转发是异步的（转交的函数引用、`events.call`），也记为一跳：调用方仍等它落定。
- 其余在同步等待的转发是**入口**：没人同步等它，它是链的边界，等它之下发出的同步调用，但它之上的调用不等它（`events.call` 虽然带着发出方的链，也是入口）。
- 发回来源会话的转发不记（它在调用方的链上执行）；经 `unchained` 发出的通知不记（没有人等它）。
- 每次转发前用三类边建等待图（c → d 表示 c 要等 d 完成）：**调用链**（d 的 `path` 含 c 的调用号，且两者之间没有入口）；**延后**（c 进入一个不可重入、正在同步等待、且 c 不在其调用链上的运行时，c 等这个运行时发出的所有同步调用）；**栈顺序**（c、d 先后进入同一个声明了 `sync-stack` 的运行时，且 d 已经在那里开始执行）。同一个会话里的帧有序，所以栈顺序这条边不会误判。
- 这次转发会让图成环时不转发，直接向调用方返回 `SyncWaitCycle`，消息里列出环上的调用和（都是行发起时）行名；只有这一次调用失败。
- 等待表在收到返回、取消（只移除还没开始运行、或被异步等待的调用）和会话结束时清理；已经在运行的同步调用保留标记到它的回复。

**明确不保证。**

- **可重入的代价**：全部叶子运行时（Python、Bun、Go、Swift、Kotlin）都可重入，代价是插件的服务可能在它自己的同步调用中途被调用（"调用 rutis 服务时不要持有锁"，无法强制）。Node 运行时不可重入。
- **新旧版本混用**：没有在帧上标 `sync` 的运行时（旧版 SDK）发出的调用不进图，**这个会话不在检测范围内**，可能卡死；这样不会误报，而误报会拒绝原本能完成的调用。
- **跨主机的环**：每台宿主只看得见自己表里的那一段；跨主机的环谁也查不出（模型 `cross-host` 是反例）。Cordis 节点里几个连接共用一个泵时，同一节点里跨会话的等待宿主也看不见（`link-policy-b`）。
- **宿主的工作线程**：Rust 代码同步等待时占着宿主的一个工作线程，这些线程有界；同时进行的这种等待占满线程、其中一条又在等一个不在它链上、要新线程的进来调用时会卡住（`policy-b-workers1`）。宿主线程不在等待图里。
- **并发发出**：不同进程同时发出的调用和事件没有先后；事件侧见[事件协议](design-events-protocol-2026-10-18.md) §5.5。
- **运行时一侧的有界线程池**：Kotlin 的 IO 池、Swift 的协作池不是宿主能看到的资源；它们占满时运行时会自己排队，宿主看不见，与宿主线程问题同类。

不采用"所有叶子运行时都可重入，只有 Cordis 运行时不可重入，并拒绝两个不可重入运行时之间的同步调用"：一是挡不住一个 Node 加两个 Python 的例子（Node 同步调用 Python2 的 `s1`；`s1` 同步调用 Python1 并等待；Python1 自己（例如定时器）同步调用 Python2 的 `s2`；`s2` 同步调用 Node，Node 在等 `s1`，把它延后；`s1` 要等 `s2` 返回，于是 Node 等 `s1`、`s1` 等 `s2`、`s2` 等 Node），这个组合正是它设想的情况；二是会拒绝不会卡死的调用（例如另一个 Node 运行时空闲时调用它）；三是要求以后每种语言都可重入，"调用时不要持有锁"的负担落到所有插件作者身上。

进展：全部叶子运行时都选择可重入，并声明 `reentrant-sync`；Node 运行时不声明，另声明 `sync-stack`（一个线程、一个栈），Python 与 Bun 也声明 `sync-stack`，Go、Swift、Kotlin 不声明。这作为惯例记下，不作为强制规则——可重入仍按握手能力 `reentrant-sync` 判断（#228 的决定不变）。模型（[`specs/cross-runtime-sync/`](../specs/cross-runtime-sync/README.md)）把宿主建成参与者：宿主自己的同步调用是一跳，宿主的 `Workers` 有界；模型覆盖 3 个运行时、调用链不超过 3 跳、同时不超过 2 个顶层调用（另跑过 3 个顶层、4 跳的配置），在各种可重入组合下都没有卡死，也没有误报。

## 十、与 #107 决策记录的关系

| #107 的结论 | 本文 |
| --- | --- |
| PowerShell、Bash、AppleScript/JXA 不在 rutis 内做 | 保留。Shell 类改为另做命令型工具运行时，不进插件协议 |
| Python（min_cordis）库外、以后再说 | 修订：做 Python，但不是 min_cordis 那样的完整框架，而是叶子 SDK 加运行时插件 |
| 中立接口描述不做 | 部分修订：只做方法形状（同步还是异步），用于跨语言调用，不做类型 IR 和代码生成 |

| `node:` 前缀放宽不做 | 保留其意图：运行时一侧的调用号前缀是本端端点 id（宿主给的运行时名字，如 `node`、`py`），不再写死 `node:` |
| 反方向继续冻结 | 保留 |

#107 担心的"每种语言都停在 demo 水平""一人维护五种运行时"，本文用两点回应：每种语言只有一个很小的叶子 SDK，范式只在 rutis 里实现一份；语言按真实需求逐个接。
