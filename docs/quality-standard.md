# rutis 质量规范

[English](quality-standard.en.md) · [质量执行现状](quality-status.md)

状态：草案。适用范围：rutis 仓库内的全部代码、包、文档与发布产物。
配套：[质量执行现状](quality-status.md)（本规范逐条对应到当前实现、缺口与计划，随代码更新）。

本规范只定义规则和标准，不涉及具体的文件、测试、工具版本或 issue。实现、组件、语言和平台会变，规则不应随之改变；规则需要修改时，按 §12 的流程进行。

条款编号（如 `Q4.2`）供执行现状文档、设计文档和评审引用，编号一经发布不复用。

---

## 1. 质量目标

**Q1.1** rutis 是框架：使用者把插件、运行时、进程和机器接到它上面，把生命周期、依赖、清理和跨边界通信交给它负责。框架的一条保证失效时，使用者通常无法在自己的代码里发现或绕过。因此 rutis 的质量要求高于运行在它之上的任何东西。

**Q1.2** 这句话的具体含义是：

1. rutis 写下的每一条承诺都是可验证的，并且已被验证；
2. 承诺在声明支持的每个环境里都成立，而不只是在开发者的机器上；
3. 在故障条件下（进程崩溃、网络中断、输入畸形、资源不足），rutis 的行为也是写明的、可预期的；
4. 任何承诺被破坏时，能在发布之前被发现；
5. 用户看到的错误足以让他们自己定位问题。

**Q1.3** 质量控制本身也要可持续：每一项验证都要能说出它防止的是哪一类问题。不能对应到任何风险的验证手段不应引入；与已有手段重复的应当合并。

## 2. 质量维度

rutis 的质量从以下十四个维度定义。任何一项改动，都要逐个维度判断是否受影响（§9）。

| 编号 | 维度 | 定义 | 合格标准 |
| --- | --- | --- | --- |
| **Q2.1** | 功能正确性 | 写明的行为在所有允许的输入和执行顺序下成立，包括并发交错 | 每条承诺都有验证；并发相关的承诺按不同执行顺序验证，而不只是重复运行 |
| **Q2.2** | 故障行为 | 部件失效时，rutis 的行为符合写明的规则：失败显式、范围受限、可恢复 | 每种可能的故障（§5.2）都有写明的预期行为，并经过注入验证 |
| **Q2.3** | 故障隔离 | 一个部件的失效只影响写明的范围（同一进程、同一挂载、同一链接），不扩散 | 失效后，范围之外的部件继续工作，并且可以证明它们没有受到影响 |
| **Q2.4** | 资源完整性 | 结束、卸载、替换、关闭之后，rutis 及其拉起的一切不留残余：进程、连接、文件、句柄、线程、任务、内部记录 | 每次结束后都核对残余；反复执行时资源占用不增长 |
| **Q2.5** | 数据完整性 | rutis 持久化或转交的数据不丢失、不损坏、不被静默改写：配置、持久化的状态、跨边界传递的值 | 写入在失败时保持一致；多写者不互相覆盖；值跨边界往返后等价 |
| **Q2.6** | 兼容性 | 在声明支持的每个平台、语言版本、依赖版本范围内成立；不同实现之间可以互通 | 支持矩阵中的每个格子都实际验证过（§10） |
| **Q2.7** | 演进稳定性 | 公开接口、线协议、插件接口、配置格式、持久化格式的变化是有意的、可见的、有迁移路径的 | 不兼容的变化在发布前被检测并声明；不同版本相遇时行为明确 |
| **Q2.8** | 安全 | 只有经过验证的对端能够连接；凭据不泄漏；不可信的输入不会导致崩溃、越权或资源耗尽；内存安全边界清楚 | §5.3 的安全要求全部满足 |
| **Q2.9** | 性能与规模 | 在声明的规模内，延迟和资源占用符合声明，且不随运行时间增长 | 有性能声明的都有测量；长时间运行无增长趋势 |
| **Q2.10** | 可诊断性 | 出错时，用户从错误信息、状态输出和诊断接口能判断是哪个部件、什么原因、如何处理；诊断本身不改变系统状态 | 面向用户的错误满足 §5.6；诊断接口有验证 |
| **Q2.11** | 开发者体验 | 插件作者和嵌入方从文档出发，能走通第一条成功路径；本地测试工具的结论与真实宿主一致 | 首次使用路径经过黑盒验证；测试工具与真实运行时的行为差异有界、写明 |
| **Q2.12** | 可安装与可部署 | 每个分发渠道的产物在干净环境中能安装、运行、卸载 | 每个渠道、每个支持的平台都在干净环境中验证过 |
| **Q2.13** | 文档一致性 | 文档中的示例、参数、行为描述与实际一致 | 可执行的示例都被执行过；承诺都能对应到验证 |
| **Q2.14** | 发布完整性 | 发布的产物与源码对应、版本一致、可以重现 | 产物由自动流程从带标签的源码构建；同一发布中的各包版本一致 |

## 3. 承诺的分级

rutis 的行为分为四级，验证强度依级别而定。设计文档必须标明它定义的每条行为属于哪一级。

| 编号 | 级别 | 含义 | 验证要求 |
| --- | --- | --- | --- |
| **Q3.1** | 核心承诺 | 使用者依赖它来构建自己的系统，失效时无法自行绕过。包括：依赖门控（未就绪不启动、消失即停下、恢复后重启）；清理恰好执行一次；失败时回滚、旧状态继续工作；使用方只依赖服务名而不依赖实现；跨边界做不到的事显式报错而不静默降级；中断时调用显式失败、不报假成功、不自动重试副作用；结束后不留残余 | 风险一律按最高级（P0）对待；必须在每个支持的平台上、在故障注入下验证；必须由至少两种独立方式验证（§8.3） |
| **Q3.2** | 契约行为 | 写在设计文档或用户文档中的具体行为：顺序、参数、默认值、错误类别、超时 | 必须有自动化验证；登记在保证登记表（§9.4） |
| **Q3.3** | 实现细节 | 没有写进任何文档的行为 | 不要求验证；使用者不得依赖；测试不得锁定它（否则改实现会被误判为破坏） |
| **Q3.4** | 明确不保证 | 文档中写明不提供的行为（例如某些跨边界的顺序、某些检测） | 写明原因；如果有人可能误以为它被保证，应有验证锁定"确实不提供"，防止悄悄变成隐式保证 |

**Q3.5** 一条行为从"实现细节"升为"契约行为"或"核心承诺"时，必须同时补上对应级别的验证。从高级别降级视为不兼容变更（§9.3）。

## 4. 风险评估

**Q4.1** 每项设计、每个新组件、每次重大改动，都要做风险评估：在它所处的使用场景中，逐个质量维度（§2）列出可能出的问题。

**Q4.2** 影响的判断：

| 影响 | 标准 |
| --- | --- |
| 高 | 违反核心承诺；导致数据丢失、服务中断或安全问题；使用者无法在自己的代码中绕过 |
| 中 | 某些条件下功能不可用，但使用者能发现并绕过；错误信息不足导致排查困难 |
| 低 | 体验问题，不影响正确性 |

**Q4.3** 可能性的判断：

| 可能性 | 标准 |
| --- | --- |
| 高 | 正常使用就会遇到；相关代码频繁改动；已经发生过 |
| 中 | 在特定条件下会遇到：某个平台、某种故障、某种并发时序、某个版本组合 |
| 低 | 需要少见的条件组合 |

**Q4.4** 优先级与验证强度：

| 优先级 | 规则 | 必须达到的验证 |
| --- | --- | --- |
| P0 | 影响高且可能性中或高；或涉及核心承诺 | 自动化；受改动影响时在合入前运行，并在每日和发布前的完整运行中运行（Q12.3）；覆盖所有声明支持的平台 |
| P1 | 影响高且可能性低；或影响中且可能性中或高 | 自动化；至少在每日运行和发布前运行 |
| P2 | 其余 | 可以只靠评审、文档或手动验证 |

**Q4.5** 风险评估的结论（风险、级别、选定的控制）记录在执行现状文档中，并随设计变化更新。

## 5. 横向要求

这些要求不依赖组件类型，所有部分都适用。

### 5.1 承诺的可验证性

**Q5.1.1** 一条承诺如果无法写成验证，就不能作为承诺发布：要么改写成可验证的形式，要么降为"明确不保证"。

**Q5.1.2** 验证必须检查结果，不能只是执行代码。"代码被执行过"不等于"行为被验证过"。

### 5.2 故障

**Q5.2.1** 以下故障对 rutis 的任何部件都是常态，不是例外。每个部件的设计必须写明在这些故障下的行为，并经过注入验证：

| 类别 | 故障 |
| --- | --- |
| 进程 | 对端进程在任意时刻退出（正常、崩溃、被强制终止）；进程无响应；进程启动失败；进程在握手前退出 |
| 通信 | 连接在任意时刻断开；半开（一端认为连通，另一端已失效）；延迟；对端发送畸形、超长、不完整、顺序错误的消息 |
| 用户代码 | 插件在启动、运行、清理的任意阶段报错、panic、阻塞或不返回 |
| 配置 | 配置非法、缺失、引用不存在的东西、在运行中被改坏 |
| 环境 | 依赖的语言环境、包、文件、端口不存在或不可用；权限不足 |
| 宿主自身 | 宿主收到终止信号；宿主被强制终止 |
| 并发 | 同一对象上的操作以任意顺序交错；同一时刻的大量并发启动、调用、关闭 |
| 版本 | 两端版本不一致；协议或接口版本不匹配 |

**Q5.2.2** 故障下的合格标准：

1. 失败是显式的：调用方在有限时间内得到明确的失败结果和可区分的错误类别；
2. 不报告假成功；结果未知时不报告为未执行；
3. 有副作用的操作不被自动重试；
4. 失败范围符合写明的隔离边界（Q2.3）；
5. 失败后不留残余（Q2.4）；
6. 能恢复的情况下，恢复路径经过验证。

**Q5.2.3** 不提供超时、重试或自动重启的地方，必须写明，并说明使用者应当怎么做。

### 5.3 安全

**Q5.3.1** 信任边界必须写明：哪些是可信的（例如插件代码），哪些不完全可信（网络、远端机器、外部输入）。

**Q5.3.2** 跨越信任边界的连接必须经过身份验证；跨机器的通信必须加密；不加密的通信只允许在本机。

**Q5.3.3** 凭据不得出现在日志、错误信息、诊断输出、命令行参数、URL 和测试产物中。每项涉及凭据的功能都要验证这一点。

**Q5.3.4** 来自信任边界之外的输入（网络消息、对端发送的帧、配置文件、插件清单、协议握手）：

1. 有大小和深度上限，超限时显式拒绝；
2. 畸形输入不导致崩溃、无限内存、无限循环；
3. 拒绝时的错误类别可区分，且不泄漏内部信息。

**Q5.3.5** 授权必须基于已验证的身份，不得基于对端自报的信息。撤销身份或授权后，已建立和正在建立的连接都必须失效，且不得被迟到的结果绕过。

**Q5.3.6** 使用不安全代码（内存不安全的语言特性、外部函数调用、动态加载原生代码）的范围必须集中、写明；每处都要说明其安全前提。加载原生代码前必须完成身份校验，校验失败时不得执行被加载代码的任何部分。

**Q5.3.7** 依赖的第三方包要检查已知漏洞和许可证；新增依赖需要说明理由。

**Q5.3.8** 进程外运行不是隔离手段。如果某项功能需要隔离不可信代码，必须单独设计，不能以"运行在另一个进程里"代替。

### 5.4 资源完整性

**Q5.4.1** 每个持有资源的部件（进程、连接、文件、监听、线程、任务、内部注册）都必须写明资源何时释放、由谁释放。

**Q5.4.2** 每个可验证的场景结束时，都要核对残余：所有被拉起的进程已退出；所有监听已释放；所有临时文件已删除；测试进程本身的句柄、线程、任务数回到基线；内部注册表回到基线。

**Q5.4.3** 支持反复创建和销毁的部件，必须验证在大量重复后资源占用不增长。

**Q5.4.4** 宿主被强制终止时，它拉起的进程必须在有限时间内退出，不留下孤儿进程。每个支持的平台都要验证，因为各平台的机制不同。

### 5.5 数据完整性

**Q5.5.1** 持久化写入必须是原子的：失败时，存储中要么是旧内容，要么是新内容，不得是中间状态。

**Q5.5.2** 多个写者可能写同一份存储时，必须有冲突检测；任何一方的修改都不得被静默覆盖。

**Q5.5.3** 每种持久化格式都有版本。新版本必须能读取之前所有仍受支持的版本写下的数据，或者明确拒绝并说明迁移方法。

**Q5.5.4** 跨语言、跨进程传递的值，转换规则必须写明，并对每一对实现验证：值往返后等价；不能表示的值显式拒绝，而不是静默改变。

### 5.6 错误与诊断

**Q5.6.1** 面向用户的错误必须包含：出错的位置（哪个插件、哪一行配置、哪个文件、哪个对端）；原因；可行的处理方式（如需要安装的包、需要修改的字段）。

**Q5.6.2** 错误类别用于程序判断，错误文字只用于给人看。程序（包括 rutis 自身和测试）不得依据错误文字做分支。

**Q5.6.3** 常见错误的输出要锁定，变化时必须在评审中说明。

**Q5.6.4** 诊断接口（状态查询、自描述、追踪）不得改变系统状态，不得调用用户代码；它的一致性范围（是否原子快照）必须写明。

**Q5.6.5** 追踪和日志不记录跨边界消息的内容，只记录方向、长度和类别；需要记录内容时，必须显式开启，并注明可能包含敏感信息。

### 5.7 性能

**Q5.7.1** 写进文档的性能数字必须标明是"承诺"还是"参考值"。承诺必须有自动化验证和固定的测量环境；参考值必须注明测量条件。

**Q5.7.2** 必须声明设计的规模范围（插件数量、运行时数量、节点数量、实例数量、连续运行时间）。在声明范围内，长时间运行时资源占用不得有增长趋势。

**Q5.7.3** 性能变化的检测不得在噪声大于检测阈值的环境中设为强制门槛。

## 6. 按组件类型的验证要求

rutis 的组件按性质归入以下类型。一个组件可以属于多个类型，此时满足每个类型的要求。新增组件时，先确定它属于哪些类型。

### Q6.1 生命周期与并发核心

例：插件状态机、依赖门控、服务注册、事件派发。

1. 每条状态转换规则都有验证，包括在每个状态下收到每种请求的情况；
2. 并发相关的承诺，必须在单线程和多线程两种执行方式下都成立；
3. 对历史上出过问题的、或对执行顺序敏感的部分，必须用能够控制执行顺序的手段验证（系统地尝试不同的交错，失败时能给出具体顺序），不能只依赖重复运行；
4. 用户回调的任何异常（错误、panic、不返回）都不能破坏框架自身的状态；
5. 反复创建销毁后，内部记录回到基线；
6. 若有参照实现（行为来源），对参照实现中与语言无关的行为逐条对照验证，并记录每条差异的理由。

### Q6.2 跨进程协议

例：会话协议、运行时控制操作、节点操作。

1. 协议的消息集合、每种消息的字段、错误类别、版本号写成规范；
2. 每种实现（每种语言）对同一套一致性检查通过；
3. 畸形、未知、重复、乱序、引用不存在的消息，都有写明的处理方式并经过验证；
4. 版本或能力不匹配时，在握手阶段显式拒绝，并说明哪一端需要升级；
5. Q5.2 列出的通信故障都经过注入验证，满足 Q5.2.2；
6. 引用、句柄等跨边界的资源，有计数或租约规则，并验证在任意的获取与释放序列下不泄漏、不提前释放；
7. 取消必须传递到对端；多跳转发时必须逐跳传递；
8. 新的协议设计、或对多方交互规则的修改，在实现之前用模型检查验证死锁和关键不变式（§11.2）；
9. 线格式的变化按 §9.3 处理。

### Q6.3 通道与承载

例：本机 socket、继承的描述符、WebSocket、内存通道，以及以后新增的承载。

1. 每种承载都通过通道契约检查：顺序、不丢不重、消息边界、背压、关闭幂等且唤醒阻塞方、对端关闭可被观察；
2. 每种承载都有消息大小上限，超限时显式关闭；上限的边界值（恰好等于、多一字节）经过验证；
3. 需要发现失联的承载，验证在声明的时间内发现半开；
4. 承载的身份验证、拒绝类别在所有实现间一致；
5. 承载是否可用于某个平台，以支持矩阵为准（§10）。

### Q6.4 外部输入解析

例：协议帧解码、分帧、握手请求、配置文件、插件清单、配置合并规则。

1. 边界值验证：空、最小、最大、超过最大、嵌套最深；
2. 模糊测试：随机和变异输入下不崩溃、不无限占用内存或时间；模糊测试的语料保存在仓库中，发现的问题转成固定的测试；
3. 解析结果有可检查的性质时（例如编码后再解码等于原值、与参照实现一致），用随机输入验证这些性质；
4. 错误信息指出输入中出错的位置。

### Q6.5 资源持有者

例：拉起进程的部件、持有连接或监听的部件、创建临时文件的部件。

1. 满足 Q5.4 的全部要求；
2. 在同一进程中并发地大量创建时，不出现竞态（例如描述符被错误地继承到其他子进程）；
3. 资源的释放不依赖使用者主动调用；使用者遗忘或异常退出时，也有写明的回收路径。

### Q6.6 面向用户的入口

例：命令行工具、配置文件格式、项目模板。

1. 以黑盒方式验证：使用发布形态的程序，以用户的方式调用，不直接调用内部接口；
2. 每个命令的成功路径、常见错误路径、退出码都有验证；退出码规则写进用户文档；
3. 终止信号的处理在每个平台上都经过验证，满足 Q5.4.4；
4. 配置文件的每个字段都有验证；未知字段的处理方式写明；
5. 项目模板生成的项目，在干净环境中能直接安装依赖、通过自带测试、运行；
6. 输出满足 Q5.6；面向脚本的输出格式视为接口，变化按 §9.3 处理。

### Q6.7 插件 SDK 与测试工具

例：各语言的插件 SDK、不需要宿主的插件测试工具。

1. 各语言 SDK 的插件接口语义一致：声明、生命周期、值传递、同步与异步、取消、版本标记；差异必须写明；
2. 测试工具的结论必须与真实运行时一致：同一组用例在测试工具和真实运行时上运行，结果比对；已知的差异必须写明并有界；
3. 测试工具应当在本地提前暴露"进程内能用、跨进程就失败"的写法；
4. 插件接口版本不匹配时，错误信息说明需要升级哪一边。

### Q6.8 语言运行时

例：每种语言一个的运行时进程。新语言、新运行时（包括同一语言的另一种执行引擎）接入时，必须满足以下全部条件才能声明支持：

1. 通过会话一致性检查和运行时一致性检查的全部项目；
2. 在声明支持的每个平台、每种本机交接方式上通过；
3. 写明是否可重入，以及与其他运行时之间同步调用的规则；在已选定的跨运行时同步调用策略下没有死锁（以模型检查结论为准）；
4. 崩溃时只影响写明的范围（同一运行时实例），并经过验证；
5. 有对应的插件 SDK 和测试工具，满足 Q6.7；
6. 有最低版本声明，并进入支持矩阵（§10）；
7. 运行时不得能够在宿主不知情的情况下下载或执行未声明的代码。

### Q6.9 跨实现的服务契约

例：同一个服务名由不同语言、不同位置的实现提供。

1. 服务的方法形状（同步或异步）必须可声明；
2. 跨语言传递的值按一套写明的规则转换（插件 API "值怎样传递"）：每种运行时、每个 SDK 的测试工具都按这套规则传值，并经过验证；每种语言的实现都能给抛出的错误命名；
3. 实现替换时，使用方不需要修改，宿主不需要重启；替换期间的调用要么成功、要么显式失败，不挂起；替换后旧实现不留残余；
4. 同一服务的不同实现返回的数据是否一致（字段、缺省与 `null`、错误名、语义）由服务的作者负责，不在 rutis 的范围：rutis 不规定服务的数据形状，不提供契约格式或检查工具。

### Q6.10 持久化

例：分层配置的可编辑层、配置文件。

1. 满足 Q5.5 的全部要求；
2. 每种修改操作在保存、重新加载后得到相同的状态；
3. 保存失败、冲突、部分写入都有验证；
4. 每个发布版本保存一份持久化样本，后续版本必须能读取（Q5.5.3）。

### Q6.11 代码生成

例：从其他语言的类型声明生成 Rust 绑定。

1. 每种类型映射规则都有验证，包括可选、可空、二者同时的区别；
2. 无法生成的部分在构建时报告位置和原因，不静默跳过；
3. 生成的代码在真实的外部包上编译并调用验证；
4. 外部包或外部框架发布新版本时，有定期的验证发现不兼容（不阻断合入，只报告）。

### Q6.12 原生代码的动态加载

1. 加载前完成身份与兼容性校验；任何一项不符时拒绝，并且被拒绝的代码没有任何部分被执行；
2. 校验的每一种拒绝情况都有反例验证；
3. 替换失败时旧版本继续工作；
4. 构建可重现：同一源码在不同路径、不同机器上构建出相同的产物；
5. 每个支持的平台都要验证：合入前按改动范围运行，每日和发布前的完整运行中都运行（Q12.3），不能只在相关代码改动时验证。

### Q6.13 分布式与网络节点

例：节点之间的连接、远程运行时、租约与接管、重连。

1. 满足 Q6.2 和 Q6.3；
2. 两个独立的宿主进程之间验证，而不只是在同一进程内模拟；
3. 重连、接管、撤销的时序规则，在设计阶段用模型检查验证（§11.2）；实现阶段，用于验证的测试必须覆盖迟到消息和并发接管；
4. 在真实的网络条件下（延迟、丢包、断开）定期验证；
5. 重试和退避的参数是契约行为，必须精确验证，而不是只验证"会重试"。

### Q6.14 外部框架兼容层

例：挂载其他框架的插件、把其他框架的应用接成节点。

1. 以外部框架的原生行为为参照，用同一组场景比对；
2. 跨边界无法保持的行为写成边界规则；能检测的违规必须报错，并经过验证；
3. 用外部框架生态中真实发布的插件作为验证材料；
4. 外部框架的新版本定期验证（不阻断合入）。

### Q6.15 分发产物

例：各渠道发布的包、二进制、平台专用包。

1. 每个渠道、每个支持的平台，在不含仓库源码的干净环境中：安装 → 运行最小使用路径 → 卸载；
2. 验证运行的确实是本次构建的产物；
3. 发布后，用注册表上的产物再验证一次；
4. 同一次发布中的各包版本一致，由自动检查保证。

### Q6.16 开发与诊断通道

1. 只在开发构建或显式开启时存在；生产构建中不存在，并经过验证；
2. 只在本机可访问，访问权限受限；
3. 修改系统状态的命令与生产路径使用同一套校验，失败时不改变状态。

## 7. 测试本身的规则

**Q7.1 确定性。** 测试结果不依赖机器速度、负载或运行顺序：

1. 不用固定时长的等待做同步；等待某事发生用明确的同步点；断言某事不发生用可控的时钟，或改写为"另一件事已发生而此事仍未发生"；
2. 超时只用于防止挂死，不作为性能断言；
3. 有时间语义的承诺（心跳、退避、截止时间）用可控的时钟验证。

**Q7.2 可复现。** 使用随机性的测试必须输出种子，并能用种子重放；失败时保存足以重现的信息（种子、操作序列、全部进程的输出）。

**Q7.3 不掩盖失败。** 自动化流程不自动重试失败的测试。偶发失败视为缺陷：立即登记，在限定时间内修复或证明是测试本身的问题。被暂时跳过的测试必须注明原因和对应的缺陷记录。

**Q7.4 失败必须可见。** 后台线程、子进程、异步任务中的异常必须导致测试失败，不能只打印。

**Q7.5 隔离。** 测试之间不共享端口、文件、环境变量或全局状态。

**Q7.6 黑盒与白盒分开。** 验证用户入口的测试不使用内部接口；验证内部规则的测试可以使用。两者不能互相替代。

**Q7.7 参照可再生。** 用作比对参照的输出（期望文件、参照实现的结果），必须能由仓库中的命令重新生成，并定期核对再生结果与保存的一致。

**Q7.8 跳过必须说明。** 某个组合（平台、实现、版本）不运行某项验证时，必须写明原因；不允许静默跳过。

## 8. 验证的独立性与层次

**Q8.1** 验证分为三个层次，各自不能替代：

| 层次 | 回答的问题 |
| --- | --- |
| 规则层 | 单个组件的规则是否成立（单元、契约、一致性） |
| 组合层 | 组件组合起来、在真实进程中是否成立（集成、黑盒端到端、故障注入） |
| 环境层 | 在用户的真实环境中是否成立（支持矩阵、干净环境安装、长时间运行、真实网络） |

**Q8.2** 每条核心承诺必须在三个层次上都有验证。

**Q8.3** 核心承诺必须由至少两种独立的方式验证，例如：由 Rust 驱动的一致性检查和各语言 SDK 自身的测试；库级测试和黑盒测试；测试和模型检查。目的是防止验证代码与实现犯同一个错误。

## 9. 变更流程

### 9.1 设计

**Q9.1.1** 每份设计文档必须包含：

1. 它定义的行为，以及每条的级别（§3）；
2. 风险评估（§4）；
3. 验收条件，每条可以写成验证；
4. 所属组件类型（§6），以及对应要求如何满足。

**Q9.1.2** 涉及多方交互的协议，设计阶段必须完成模型检查后才能定稿（§11.2）。

### 9.2 实现

**Q9.2.1** 行为变更必须附带验证。

**Q9.2.2** 缺陷修复必须先有一个能重现缺陷的测试，修复后该测试通过，并以缺陷记录命名或引用。

**Q9.2.3** 修复缺陷时，还要问：为什么现有的验证没有发现它？如果答案是某一类验证缺失，补上这一类，而不只是这一个测试。

**Q9.2.4** 新增解析外部输入的代码，必须同时满足 Q6.4。

**Q9.2.5** 新增不安全代码，必须写明安全前提（Q5.3.6）。

### 9.3 不兼容变更

**Q9.3.1** 以下都是接口，其不兼容变化须遵守本节：公开的编程接口；线协议；插件接口；配置格式；持久化格式；命令行参数与退出码；面向脚本的输出格式；承诺的降级。

**Q9.3.2** 不兼容变化必须：

1. 在合入前被自动检测或在评审中明确标出；
2. 与版本号规则一致；
3. 附带迁移说明，迁移说明中的代码经过验证；
4. 不同版本相遇时（例如新宿主与旧运行时），要么正常工作，要么在建立连接时显式拒绝并说明原因；必须验证上一个发布版本与当前版本相遇的情况。

### 9.4 保证登记

**Q9.4.1** 所有核心承诺和契约行为，登记在保证登记表中：编号、出处、内容、级别、状态（已验证 / 部分验证 / 未验证 / 明确不保证）、对应的验证。

**Q9.4.2** 验证代码中标注它所验证的保证编号。

**Q9.4.3** 删除或跳过一项验证时，登记表中对应保证的状态必须同步修改。

**Q9.4.4** 每次发布，"未验证"的核心承诺必须为零；"未验证"的契约行为数量不得多于上一次发布。

---

## 10. 支持矩阵

**Q10.1** 支持矩阵的维度：操作系统与架构；每种语言环境的版本；可选依赖的版本范围；每种运行时与每种承载的组合；协议版本。

**Q10.2** 凡是声明支持的，必须实际验证：

1. 每个维度的**最低**声明版本和**最新**版本都要验证；
2. 声明的依赖版本下限，必须用下限版本验证；
3. 每种运行时 × 每种承载 × 每个平台的组合，要么验证，要么在矩阵中写明不支持的原因。

**Q10.3** 不再验证的环境，必须从支持声明中删除。不允许"声明支持但从未验证"。

**Q10.4** 新增平台、语言版本、运行时或承载时，必须先进入矩阵并通过验证，才能对外声明支持。

## 11. 验证手段的选用原则

### 11.1 按问题类型选择手段

| 问题类型 | 应选用的手段 | 不能替代它的手段 |
| --- | --- | --- |
| 单个规则是否成立 | 单元或契约验证 | — |
| 多个实现是否一致 | 一致性检查（同一套检查，每个实现都运行） | 各实现各写各的测试 |
| 与参照行为是否一致 | 差分验证（同一输入，比较输出） | 只读参照的文档 |
| 并发交错下是否成立 | 可控调度的模型检查 | 重复运行 |
| 协议设计本身是否正确 | 设计模型检查 | 实现测试 |
| 畸形输入下是否健壮 | 模糊测试与边界值 | 手写的少量异常用例 |
| 有明确性质的逻辑 | 随机输入的性质验证 | 少量固定用例 |
| 组合起来是否成立 | 黑盒端到端 | 库级集成 |
| 故障下是否成立 | 故障注入 | 正常路径测试 |
| 是否有缓慢泄漏 | 长时间运行与资源趋势 | 单次残余检查 |
| 环境差异 | 支持矩阵、干净环境安装 | 开发者本机 |
| 错误信息是否可用 | 输出快照 + 人工评审 | — |

### 11.2 模型检查的适用条件

**Q11.2.1** 设计模型检查用于同时满足以下条件的地方：

1. 多个独立的参与者，消息可能延迟、重排、丢失；
2. 设计尚未定稿，或者正确性只有文字推理支撑；
3. 错误只在特定交错下出现，难以通过测试稳定触发。

**Q11.2.2** 单进程的状态机、顺序逻辑不使用设计模型检查；其中对执行顺序敏感的部分，用可控调度的模型检查验证实现本身（Q6.1.3）。

**Q11.2.3** 设计模型必须写明：对应哪份设计、做了哪些简化、检查了哪些不变式。设计修改时，模型同步修改。

### 11.3 不采用的情况

**Q11.3.1** 以下情况不引入验证手段：

1. 不能说明它防止哪一类问题；
2. 与已有手段检查同一类问题，且没有更高的检出能力；
3. 只产出报告、没有人据此采取行动；
4. 在当前环境中误报率高于它的检出价值。

**Q11.3.2** 以覆盖率等执行量指标作为强制门槛是不允许的：它们说明代码被执行，不说明行为被检查（Q5.1.2）。这些指标只能用于发现完全没有验证的区域。

## 12. 持续集成

持续集成是质量控制的执行环节：本规范要求的验证，绝大多数由它自动运行。它本身也是一个需要设计和度量的系统：太慢，开发者就会绕过它或长时间等待；太少，问题就会漏到主线。

**Q12.1** 验证按发现问题需要的及时程度分级运行：

| 时机 | 运行的内容 |
| --- | --- |
| 每次合入前 | 受这次改动影响的 P0 验证（Q12.3）；静态检查；在各平台上跑完成本较低的部分 |
| 每日（主线有新的合入时）、发布前 | 全部验证：全部平台、全部支持矩阵格子；干净环境安装；跨版本相遇；构建可重现 |
| 每日 | P1 中耗时较长的验证：长时间运行、模糊测试、大规模模型检查、真实网络条件、外部生态新版本 |
| 发布前 | §13 |

**Q12.2** 合入前的验证必须控制在合理的时间内；超出时，应把成本高、检出率低的部分移到后面的层级，而不是删掉。

**Q12.3 按改动选择。** 合入前只运行受这次改动影响的验证；**每天至少一次**（主线有新的合入时）、以及**每次发布前**，运行全部验证。

1. 改动范围与验证之间的对应关系写在 CI 配置中，像代码一样评审；
2. 影响范围无法确定的改动（构建配置、依赖锁文件、CI 配置本身、被广泛依赖的公共部分）运行全部验证；
3. 某项验证在合入前被跳过、在每日或发布前的完整运行中失败时，修复之后要检查对应关系是否漏掉了这类改动，并修正对应关系（Q9.2.3）。

**Q12.4 取消被取代的运行。** 同一变更推送了新的提交后，为旧提交进行中的运行立即取消。每日的完整运行检查上一次成功运行以来合入的所有提交，不被取消；失败时开问题单，写明失败的验证和提交范围（上一次成功运行的提交到这次的提交）。

**Q12.5 统一的合入条件。** 合入条件由一个汇总检查表示：它在所有被选中的验证通过后通过；未被选中而跳过的验证不算失败；汇总检查本身任何情况下都运行，不能被跳过。

**Q12.6 时间以开发者等待的时间计。** 合入前和发布前验证的时间预算，从推送提交（或 tag）算到得到结果，包括排队时间，而不只是执行时间。下面的要求只针对合入前和发布前的验证；每日的完整运行不在开发者的等待路径上。

1. 先缩短关键路径（耗时最长的那一项），再优化其他项；关键路径上的验证可以拆成并行的部分；
2. 稀缺的执行资源（数量受限的平台、机器）上，每次运行占用的任务数尽量少；可以在同一台机器上依次完成的检查，合并成一个任务；
3. 构建可重现这类不能使用缓存的检查，不放在合入前的关键路径上，除非这次改动直接影响它。

**Q12.7 不重复。** 同一类检查在同一个层级只在一处运行（Q11.3.1）。

**Q12.8 主线失败优先处理。** 主线上的验证失败视为最高优先级的缺陷：查明是哪次合入引入的，修复之前，不再合入可能受影响的改动。

**Q12.9 度量持续集成本身。** 定期统计：从推送到得到结果的时间（含排队）、关键路径的组成、各任务耗时、偶发失败率、主线失败次数及其中合入前未被选中的次数。超出预算时，按 Q12.2、Q12.6 调整。

**Q12.10 CI 配置是代码。** CI 配置的修改与代码同等评审；修改 CI 配置的变更，合入前运行全部验证。

## 13. 发布门

**Q13.1** 满足以下全部条件才能发布：

1. 发布的提交上全部验证通过（每日或发布前的完整运行）；最近若干次每日验证全部通过；
2. 没有新增的偶发失败或被跳过的验证；
3. 核心承诺全部已验证；未验证的契约行为不多于上一次发布（Q9.4.4）；
4. 不兼容变化已检测、已声明、已附迁移说明且说明经过验证；
5. 本版本的持久化样本已保存；
6. 每个渠道、每个平台的产物在干净环境中验证通过；
7. 跨机器的真实环境验证已完成（可以是人工，结果需要记录）；
8. 发布说明列出本版本保证登记表的变化。

**Q13.2** 发布后，用注册表上的产物再验证一次；失败时撤回或标记该版本，并发布修正版本。

## 14. 本规范的维护

**Q14.1** 本规范的修改通过评审合入，修改说明必须指出：新增或修改的条款防止哪一类问题；对现有验证有什么影响。

**Q14.2** 条款编号不复用；删除的条款保留编号并标注"已废止"及原因。

**Q14.3** 执行现状文档按条款编号说明当前的满足情况；规范条款新增时，执行现状文档同步加上对应的行。

**Q14.4** 每次发布前，检查一遍执行现状文档中未满足的条款，确认它们都有计划或已被明确接受为暂时的例外；例外必须写明原因和期限。
