# 软件开始自己去适应世界

[English](software-that-adapts.en.md)

软件被写完的那一刻，就被固定在了当时的环境里。

之后，它所依赖的接口会升级，旁边会出现新的系统，旧的服务会下线。环境每变一次，软件都只能停在原地，等一个人来读文档、改代码、重新发布。几十年来，这几乎是软件的宿命：它能接触到什么，取决于别人为它准备了什么，也取决于有没有人愿意替它跟上变化。

模型让这件事第一次出现了松动。软件开始能读懂一个陌生的接口，写出接入它的代码，运行，看到结果不对，再改一版。过去要排进迭代计划的工作，现在可能只要几分钟。

当改代码不再昂贵，一个更深的问题就浮现出来：软件能不能持续地接触它所处的环境，在环境里试验、探索，并且一次次地调整自己去适应它？

rutis 是为这个问题而做的。下面借一个 agent 的成长经历，讲讲它在每一步遇到了什么，以及 rutis 是怎样回应的。

## 它想读一份日历

这个 agent 起初只运行在一台笔记本上。某天它需要读公司的日历，好替人安排会议。

公司的日历系统很老，没有人为它做过 SDK，更没有 MCP server。按过去的方式，这件事到这里就停了：环境没有准备好，软件也就做不到。

但这个 agent 能写代码。它读了日历系统的接口文档，写了一段接入代码，把它作为一个插件装进自己，对外提供一个名叫 `calendar` 的服务。安排会议的那部分逻辑，从此只依赖这个名字。

这一步里藏着 rutis 最根本的一个立场：**建立连接的，应该是软件自己，而不是环境的维护者。** 今天主流的做法，是环境一侧把能力包装好，软件去调用。这条路很好，但连接始终停在软件外面，软件的能力边界由外面有什么来决定。rutis 想反过来：软件需要接触什么，就自己写插件接上去，用最合适的语言，也可以由 agent 来写。接上之后，这个连接成为软件的一部分，有自己的生命周期，可以被观察，也可以被干净地拆掉。两种做法并不冲突，一个 MCP 客户端完全可以只是 rutis 里的一个插件。

“只依赖名字”这件事，在后面会显出它的分量。

## 一天改十次

第一版接入代码当然不完美。日历里有重复的会议，有时区问题，有的接口一调就超时。agent 一天里把这个插件改了十几次。

每改一次，都要在一个正在运行的系统里把旧的插件换下来，把新的换上去。真正的麻烦从这里开始：旧插件开的连接关了没有？它注册的定时器还在不在？安排会议的逻辑正在用旧的 `calendar`，换的那一刻它会怎样？新版本启动失败了，系统会不会停在一个半新不旧的状态？

换一次，这些问题或许可以靠小心来回避；换上几百次，任何一点残留都会累积起来，直到系统在某个说不清的时刻坏掉。

所以 rutis 的内核只做几件事，但每一件都写成承诺，并用测试钉住。一个插件声明了它需要哪些服务，这些服务都就绪了它才启动；它运行期间注册的服务、监听、后台任务和子插件，在它停下时按注册的逆序清理，并且恰好清理一次；启动失败的插件会回滚已经注册的东西，不留下半截状态；一个服务换了提供者，依赖它的插件会自己停下，等新的提供者就绪后再重新启动，与它无关的部分不受影响。

有了这些保证，替换一千次和替换一次一样安全。迭代因此可以切得很细：不需要整体发布，只换一块；也不需要先在测试环境里模拟，可以直接在真实运行的系统里验证，不对就换回去。

这一类“在运行中替换部件”的思路并不是 rutis 发明的，Erlang/OTP 和 Java 的 OSGi 都走过这条路。rutis 选择用 Rust 来实现它，一个重要的原因是“卸干净”这件事：在依赖垃圾回收的环境里，一条被遗忘的引用就足以让旧模块永远留在内存里；Rust 的所有权让每一份资源归谁、何时释放都变得明确。

## 它需要另一台机器

几周以后，agent 开始替人做更多事，其中不少要执行命令：跑测试、处理数据、调用只在某台机器上装好的工具。它不想在自己所在的笔记本上做这些，更合适的地方是一台隔离的沙箱，或者一台装好了 CUDA 的 GPU 机器。

在大多数系统里，这意味着另起一套远程调用：要定义协议，要处理连接断开，要想清楚远端的进程由谁启动、谁关闭。换句话说，在一个进程里已经解决过的那些生命周期问题，跨过机器之后要重新解决一遍。

rutis 没有把“远程”当成一个单独的问题。执行命令的能力被写成一个普通的 Python 插件，提供名叫 `shell` 的服务；它运行在沙箱机器上的一个 Python 运行时里。那台机器上只需要启动这个运行时并等待连接，装哪些插件、用什么配置、什么时候启停，都由 agent 所在的 rutis 决定。agent 这一侧依然只依赖 `shell` 这个名字，不知道、也不需要知道它在哪台机器上、用什么语言写成。

于是，换一台执行环境，只需要改配置里的一个地址。沙箱机器掉线时，依赖 `shell` 的部分会停下来等待，而不是报错退出；连接恢复后，插件会重新装载，这些部分也随之恢复。过一段时间，`shell` 插件从 Python 改写成 Go，agent 的代码也一行不动。

这正是 rutis 想做的事：插件机制只是基础，它真正想要的，是让这种细颗粒度的迭代越过进程、语言和设备的边界，蔓延出去。一个插件只认它依赖的服务的名字，服务在哪个进程、用什么语言、跑在哪台机器上，由 rutis 处理；断开时怎样等待，恢复时怎样跟上，也由 rutis 处理。

## 它开始为别人服务

再后来，这个 agent 的能力被做成了一个服务，其他系统开始依赖它。它的形态从一个桌面上的程序，变成了一个后端。

后端的各个部分有各自最合适的位置。主逻辑用 Rust 写，数据库客户端和它待在同一个进程里；某个第三方平台只有官方的 Python SDK，那部分就跑在一个 Python 进程里；推理放在 GPU 机器上；还有一个早年留下来的内部系统，只能先写一个适配插件接住它。

每一部分都是一个按名字提供服务的插件，它们在哪里、用什么语言，写在配置里，而不写在代码里。Python 进程崩溃了，它提供的服务被撤下，依赖这些服务的部分停下等待，其余部分照常运行；如果配置了重启，rutis 会按退避的节奏把这个运行时重新拉起来。运行中修改配置时，新配置会先被完整地检查，有任何一处不对，旧配置就继续运行，什么都不改变。

那个内部系统的适配插件，后来也走完了它的一生。它在真实的流量里运行了几个月，它提供的服务应该有哪些方法、返回什么，被一次次的调用摸清楚了。于是团队写了一个自己的实现，提供同一个名字的服务，把适配插件换了下来。依赖它的主逻辑没有改动，服务也没有重启。

这就是“只依赖名字”的分量。软件先去适配别人的接口，在使用中弄清楚它真正需要的是什么，最后可以用自己的实现取而代之。适配和替换是同一件事的前后两段，中间不需要一次单独的迁移。未来的软件不必等别人来适配自己，它可以花足够的时间去接纳别人、适配别人，甚至最终替换别人的接口和系统。

## 不止一个它

当这样的 rutis 宿主不止一个，事情又往前走了一步。

办公室里有一台机器能访问内网，家里有一台机器连着家里的设备，云上的那台有足够的算力。每一台都运行着 rutis，它们之间用加密的连接互相连上。在这条连接上，一个节点可以把自己的服务导出给对方，也可以把对方的服务导入成自己的；可以在对方的机器上运行一个插件，让它使用那里的服务，而配置和启停仍由自己决定；还可以把一边发生的事件转发到另一边。连接断了会自动重连，对方离线时依赖它的部分等待，回来后恢复。

这样一来，每个节点都在贡献它所在环境的能力。一个节点学会了接入某个系统，网络里的其他节点就都能用上这项能力。软件对环境的适应，不再局限于它运行的那一台机器。

沿着这个方向，手机和桌面应用也可以把通讯录、定位、通知这样的能力做成插件接进来。这部分目前还在设计阶段，但它遵循的是同一套规则。

## 什么放在底层，什么交给生态

回头看，能做到这些，靠的是 rutis 在技术栈上的一个基本取舍：把固定的、不容易变的部分交给底层语言，把变化的、需要生态的部分交给其他语言。

不变的是生命周期本身：谁先启动，依赖消失了怎么办，怎样清理，跨过进程边界之后哪些事做不到。这套规则在 rutis 里只用 Rust 实现一份，内核只依赖 tokio 等寥寥几个库，每一条保证都登记在案，并对应到具体的测试。

变化的是连接与适应。Python 有 AI 和数据处理的生态，Node 有 npm 和现成的 Cordis 插件，Go 有大量基础设施库，另一台机器上有那台机器的进程和设备。在这些语言一侧，rutis 只提供一个很小的 SDK，不在每种语言里重新造一套框架；一种语言一个进程，同一种语言的插件在同一个进程里直接互相调用。

这个取舍也有时间上的含义。一项能力往往先用 Python 或 TypeScript 写出来，快速试；在使用中，它的形状慢慢稳定下来；那些已经被时间验证过的部分，再用 Rust 重写，换取稳定和性能。什么值得固化，有一个朴素的判断：语义已经收敛的，属于机制而不是措辞的，对性能敏感的，处在信任边界上的。拿 agent 来说，组装提示词的机制会被固化下来，提示词的内容则永远不会。

因为使用方只认名字，这条从试验到固化的路可以一段一段地走。软件能接入多少种运行时，它的迭代就能连接到多少个生态。

## 一个让软件成长的容器

操作系统解决的是程序怎样运行：给它分配资源，把它和别的程序隔离开，调度它的执行。它默认程序是已经写好的，在其中运行，偶尔被整个换掉。

rutis 关心的是另一件事：一个在不断变化的程序，怎样在变化中保持正确。它管理的不是 CPU 和内存，而是能力之间的关系，谁提供什么，谁依赖谁，一部分换掉以后谁需要跟着重启，一条连接断开以后谁需要等待。它的边界也不是一台机器，而是程序伸展到的所有进程、语言和设备。

所以 rutis 并不取代操作系统，它运行在操作系统之上，做的是操作系统没有打算去做的事：为一个持续成长的软件，提供一个不会因为成长而出错的容器。

## 它的代价

这样的设计有它的代价，rutis 也把它们写在明处。

每接入一种语言，至少多一个进程；跨语言的同步调用大约需要 30 微秒，远慢于进程内的调用，调用频繁的路径应该放在同一个运行时里，或者固化到 Rust。跨过进程边界以后，有些在单进程里成立的语义不再成立，比如事件只能作为通知；rutis 的做法是把做不到的事写成明确的规则，而不是悄悄降级，一个会造成跨进程死锁的同步调用会直接返回错误，而不是卡住。同一个运行时里的插件共享一个进程，其中一个让进程崩溃，其他的也会一起停下，需要隔离时就多开一个运行时实例。节点之间的信任目前还只有“可信的对端”这一级，接入的设备越多，越需要更细的授权，这是接下来要做的事。rutis 也还在 0.x，接口仍在演进。

## 结语

软件第一次有机会自己去理解它所处的世界：不再等着别人为它准备好接口，而是自己走过去，接上，试用，改进，必要时取而代之。

这需要一个在频繁的变化中仍然可靠的地方，一个不被进程、语言和设备困住的地方。这就是 rutis 想成为的东西。

rutis 的生命周期模型来自 Shigma 的 [Cordis](https://github.com/shigma/cordis)。rutis 用 Rust 把它重新实现了一遍，并把它带到了更多的语言、进程和机器上。

想试一试，可以从一行命令开始：

```bash
npx @arcships/rutis-host new weather --lang node
```

Python、Bun 和 Go 也可以作为起点。项目在 [github.com/arcships/rutis](https://github.com/arcships/rutis)，设计上的思考写在[设计哲学](https://github.com/arcships/rutis/blob/main/docs/design-philosophy.md)里。
