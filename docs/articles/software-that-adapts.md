# 软件开始自己去适应世界

[English](software-that-adapts.en.md)

> rutis：一个支撑软件成长的容器

---

很长一段时间里，软件和环境的关系是固定的：软件被写好、发布出去，然后在一个它无法改变的世界里运行。世界变了——接口升级了，新的系统出现了，旧的服务下线了——软件就等着人去跟进。

这件事正在变化。

模型让软件第一次有了改自己的能力。写一段接入代码、试一下、发现不对再改，这些曾经要排进迭代计划的事情，现在可能只需要几分钟。改代码的成本塌下来以后，一个新的问题浮了上来：

**软件怎样持续地接触环境、适应环境，并在环境里做试验和探索？**

这是 rutis 想回答的问题。

---

## 一、当改代码不再昂贵

过去我们设计软件时，默认改动是昂贵的。所以要先把需求想清楚，把接口定稳，把依赖锁死，然后尽量少动。

当改动变得便宜，这套默认就不成立了。一个能自我迭代的软件，它的日常不是“运行”，而是“试”：

- 今天要接一个内网的日历系统，先写一版试试；
- 明天发现那个系统有更好的接口，换一版；
- 后天要用一台 GPU 机器上的模型，把一部分能力挪过去；
- 再过一阵，用得最多的那部分要更稳、更快，用另一种语言重写。

每一次都是一个小改动。但这样的小改动一周可能发生几十次，而且发生在一个正在运行的系统里。

难点于是从“怎么写出来”变成了“怎么持续地换”：换的时候，旧的连接、定时器、监听有没有留下来？依赖它的部分会不会跟着坏？换坏了能不能退回去？换到另一台机器、另一种语言上，用它的那些代码要不要跟着改？

这些问题决定了一个软件能不能真的“长”起来。

## 二、等别人适配，还是自己去适配别人

今天软件获得新能力，主流的方式是等别人来适配自己。

环境的维护者提供 API、SDK、开放平台，最近还有 MCP server。软件去调用它们。这条路很好，但它有一个前提：**软件能做什么，取决于外面有人为它准备了什么。** 连接停在软件的外面，它属于环境，不属于软件。

如果软件已经能自己写代码，这个前提就显得多余了。它完全可以反过来：

**自己花时间去接纳和适配别人。**

需要接触什么，就自己写一个插件接上去；用最合适的语言写，也可以交给 agent 来写；试用、修改、替换。这个连接从此是软件的一部分，有自己的生命周期，能被观察，也能被干净地拆掉。

再往前走一步，软件甚至可以**最终替换别人的接口和系统**。这听起来像一句口号，但在 rutis 里它有一个很朴素的机制：

> 使用方只依赖一个服务的**名字**，不依赖它的实现。

比如一个排程功能依赖名为 `calendar` 的服务。

1. 一开始，`calendar` 由一个插件提供，它只是包了一层公司现有的日历系统；
2. 用了一段时间，`calendar` 应该有哪些方法、返回什么，被真实的使用摸清楚了；
3. 后来，换成一个自己实现的版本，同样叫 `calendar`。

三个阶段里，排程功能一行代码都不用改，宿主程序也不用重启。**“适配”和“替换”是同一件事的前后两个阶段**，中间不需要一次额外的迁移工程。

两种姿态可以并存，一个 MCP 客户端完全可以只是 rutis 里的一个插件。但软件的能力边界，不应该由环境来决定。

## 三、地基：在运行中，只换一块

要让软件这样迭代，第一件事是把它拆成可以在运行时单独替换的块。这就是插件。

插件机制并不新，但“频繁地在运行中替换”对它提出了很高的要求。rutis 的内核为此只做几件事，并且每一件都写成承诺、用测试钉住：

- **依赖没到就不启动。** 插件声明自己需要哪些服务，它们都就绪了才开始运行；
- **注册过的东西，停下时恰好清理一次。** 服务、监听、后台任务、子插件，按注册的逆序清理，不多不少；
- **启动失败就回滚。** 已经注册的东西撤回去，不留下半截状态；
- **换掉一块，只有用到它的部分跟着重启。** 一个服务的提供者换了，依赖它的插件会自己停下，等新的提供者就绪后再启动，其他部分不受影响。

有了这几条，替换一次和替换一千次是一样安全的。软件就可以把迭代切得很细：不必整体发布，只换一块；也不必在测试环境里假装，可以在真实运行的系统里验证，不行再换回来。

同样叫“热更新”，有一类做法是在运行中替换机器码，rutis 做的是另一件事：**替换运行中的部件**。这条思路和 Erlang/OTP、Java 的 OSGi 一脉相承。Rust 的所有权模型让“卸干净”这件事有了更可靠的地基——在依赖垃圾回收的环境里，一条遗漏的引用就足以让旧模块永远卸不掉。

但插件机制只是地基。rutis 真正想做的，是让这种迭代**蔓延出去**。

## 四、让迭代蔓延出去：越过进程、语言和设备

如果迭代只能发生在一个进程、一种语言里，软件能接触的环境就被锁在那个生态里了。想用 Python 的模型生态，得把它拉进来；想用另一台机器上的设备，得另写一套远程调用；每跨一道边界，就要重新解决一遍“启动、依赖、清理”的问题。

rutis 的做法是让这道边界对插件消失：**一个插件不需要知道它依赖的服务在哪个进程、用什么语言写、跑在哪台机器上。** 它只认名字。至于服务从哪里来、断了怎么办、换了怎么跟，都由 rutis 处理。

下面三个例子，分别对应三种边界。

### 例一：一个 agent，它的 shell 跑在另一台机器上

假设 rutis 本身是一个 agent：模型调用、对话、决策都在本机。它需要执行命令，但不想在自己的机器上执行——也许要在一台隔离的沙箱里，也许要在装好了 CUDA 的 GPU 机器上。

可以把 shell 做成一个插件，跑在那台机器上的 Python 运行时里：

```python
import asyncio
from rutis import define_plugin


class Shell:
    async def run(self, command):
        proc = await asyncio.create_subprocess_shell(
            command, stdout=asyncio.subprocess.PIPE, stderr=asyncio.subprocess.STDOUT
        )
        out, _ = await proc.communicate()
        return out.decode()


def apply(ctx, config):
    ctx.provide("shell", Shell())


plugin = define_plugin(apply, provides={"shell": Shell})
```

那台机器只运行一个监听的 Python 运行时；装哪些插件、用什么配置、什么时候启停，都由 agent 所在的 rutis 决定：

```json
{
  "id": "agent",
  "runtimes": { "remote": [{ "name": "sandbox", "language": "python" }] },
  "rows": [
    { "id": "sandbox", "name": "rutis-bridge/peer",
      "config": { "peer": "sandbox", "dial": "wss://sandbox.example.com:7443/rutis", "runtime": "sandbox" } },
    { "id": "shell", "name": "sandbox:shell_tool" }
  ]
}
```

agent 这一侧只依赖 `shell` 这个名字。于是：

- **换一台执行环境**，只改配置里的一行地址；
- **那台机器掉线了**，依赖 `shell` 的部分停下来等待，而不是崩溃；连接恢复后自动重新装载；
- **执行环境本身也可以迭代**：shell 插件先用 Python 写，以后换成 Go 版，agent 的代码不动。

agent 的“手”伸到了别的机器上，而这只手和长在本机的手，用起来没有区别。

### 例二：一个 server，它的部件散落在不同进程和机器上

再看一个更常见的场景：一个后端服务。

它的主逻辑用 Rust 写，但它需要的东西各有各的最佳位置：

```
server 主逻辑（Rust）
  ├─ 数据库 client            同一个进程
  ├─ 某个第三方 API 的接入     Python 进程（直接用官方 SDK）
  ├─ 推理服务                 GPU 机器上的运行时
  └─ 旧内部系统的适配层        以后要换成自己的实现
```

每一块都是一个插件，按名字提供服务，主逻辑按名字使用。它们在哪里运行、用什么语言写，写在配置里，而不是写在代码里。

这带来几件事：

- **故障有边界。** Python 进程崩溃了，它提供的服务被撤下，依赖它们的部分停下等待；同一宿主里的其他部分照常运行。也可以让 rutis 在运行时崩溃后按退避策略自动重启它。
- **改配置不会把服务改挂。** 运行中重新读取配置是全有或全无的：新配置有问题，旧配置继续运行，什么都不变。
- **“先适配、再替换”就发生在这里。** 那个旧内部系统，先由一个适配插件包住；等接口在真实流量里稳定下来，换成自己的实现。主逻辑不知道这件事发生过。

### 例三：多个 rutis 组网，共享能力

最后一道边界是设备。每个 rutis 宿主都可以是网络里的一个节点。

```
 办公室的节点 ──导出 calendar──▶  云上的节点（跑着 agent）  ◀──导出 device── 家里的节点
              ◀──────── 共享服务 · 在对方那里运行插件 · 转发事件 ────────▶
```

节点之间用一条加密的连接相连。在这条连接上可以做几件事：

- **共享服务**：把本节点的某个服务导出给对方，或者把对方的服务导入成自己的；
- **在对方那里运行插件**：插件跑在对方的机器上，用对方的服务，但配置和启停由这一侧决定；
- **转发事件**：一边发生的事，另一边可以收到。

连接断了会自动重连；对方离线时，依赖它的部分等待，回来后恢复。

这就是“迭代蔓延出去”最直观的样子：**每个节点贡献它所在环境的能力**——办公室节点能碰到内网系统，家里的节点能碰到家里的设备，云上的节点有算力。一个节点学会了接入某个系统，整个网络里的软件就都多了这项能力。

再往前，手机和桌面应用也可以这样接进来：应用把通讯录、定位、通知这样的能力做成插件，连到 rutis，成为网络的一部分。这部分目前还在设计阶段，但方向是一样的。

## 五、不变的交给 Rust，变化的交给生态

能做到上面这些，靠的是 rutis 的一个基本分工：

**把固定的、不容易变的，交给底层语言；把变化的、需要生态的，交给其他语言。**

- **不变的部分**是生命周期本身：谁先启动、依赖消失了怎么办、怎样清理、跨过进程边界后哪些事做不到。这套规则在 rutis 里只用 Rust 实现一份，内核只依赖 tokio 等寥寥几个库，每一条保证都登记在案，并对应到具体的测试。
- **变化的部分**是连接与适应：Python 有 AI 和数据处理的生态，Node 有 npm 和现成的 Cordis 插件，Go 有大量基础设施库，另一台机器上有那台机器的进程和设备。这些语言一侧只有一个很小的 SDK，不重新造一套框架。

这个分工还有一层时间上的含义。一项能力通常先用 Python 或 TypeScript 写出来，快速试；在真实使用中，它的形状慢慢稳定；那些被时间验证过的部分，再用 Rust 重写，换取稳定和性能。项目早期的设计记录里有一句话概括得很好：

> TS 是实验室，Rust 收毕业生。

什么样的东西值得“毕业”？语义已经收敛的、属于机制而不是措辞的、对性能敏感的、处在信任边界上的。拿 agent 来说：**提示词的装配机制会被固化下来，提示词的内容永远不会。**

因为使用方只认服务名，这条从实验到固化的路可以一段一段地走，不需要哪一天停下来做一次大迁移。软件能接入多少种运行时，它的迭代就能连接到多少个生态。

## 六、一个支撑成长的新容器

如果把 rutis 放在操作系统旁边看，会更清楚它是什么。

| | 传统操作系统 | rutis |
| --- | --- | --- |
| 它的假设 | 程序已经写好，在里面运行 | 程序在不断生长，边运行边改变 |
| 它管理什么 | CPU、内存、进程 | 连接与能力：谁提供什么，谁依赖谁 |
| 它的边界 | 一台机器 | 跨进程、跨语言、跨设备 |
| 程序怎样获得新能力 | 安装软件、安装驱动 | 自己写插件接上去，试用、替换 |
| 它最关心的问题 | 隔离与调度 | 换掉一块之后，整个系统是否仍然正确、干净 |

rutis 不取代操作系统，它运行在操作系统之上。操作系统让程序能够运行；rutis 想让程序能够**成长**。在 rutis 的视角里，插件像进程，服务像系统调用，语言运行时和远端节点像驱动——它们都受同一套生命周期管理，没有谁享有特权。

## 七、代价，以及还没做到的

这样的设计有它的代价，rutis 也把它们写在明处：

- **进程与延迟。** 每种语言至少一个进程；跨语言的同步调用大约 30 微秒，远慢于进程内调用。调用频繁的路径，应该放在同一个运行时里，或者固化到 Rust。
- **跨边界的语义更弱。** 过了进程边界，事件只能是通知，有些在单进程里成立的写法不再成立。rutis 的原则是把做不到的事写成明确的规则，而不是悄悄降级；比如一个会造成跨进程死锁的同步调用，会直接报错，而不是卡住。
- **故障范围。** 同一个运行时里的插件共享一个进程，一个插件让进程崩溃，同进程的插件会一起停下。需要隔离，就多开一个运行时实例。
- **权限还很粗。** 目前节点之间的信任粒度是“可信的对端”。接入的设备和运行时越多，越需要更细的授权：哪个节点、哪个插件可以提供或使用哪些服务。这是接下来要解决的问题。
- **还在 0.x。** API 仍在演进，不兼容的变化会附迁移说明。

## 结语

软件第一次有机会自己去理解、接纳它所处的世界：不再等着别人为它准备好接口，而是自己走过去，接上，试用，改进，必要时取而代之。

这需要一个让它在频繁变化中不出错的容器，一个不被进程、语言和设备困住的容器。这就是 rutis 想成为的东西。

rutis 的生命周期模型来自 Shigma 的 [Cordis](https://github.com/shigma/cordis)。rutis 用 Rust 把它实现了一遍，并把它带到了更多的语言、进程和机器上。

**试一试：**

```bash
npx @arcships/rutis-host new weather --lang node
cd weather && npm install
npx rutis-host dev        # 运行插件，文件改动时自动重新加载
```

Python、Bun、Go 也一样可以作为起点。
