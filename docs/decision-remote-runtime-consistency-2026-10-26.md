# 决策记录：远程运行时一致性——先写成两层，审阅后精简（2026-10-26）

[English](decision-remote-runtime-consistency-2026-10-26.en.md)

本文记录一次从"梳理远程连接逻辑"开始的讨论：先定了一个两层设计，审阅发现过重，最后精简为补齐一致性。设计见 [远程运行时一致性](design-remote-runtime-consistency-2026-10-26.md)，issue [#695](https://github.com/arcships/rutis/issues/695)。

## 一、起点

梳理 0.17.1 的远程连接代码，发现同一个远程语言运行时接法不同，表现就不同：一台（link 行 + `runtime`）与多台（接入点）的配置写法、缺插件的报错、输出都不一样。

## 二、讨论经过

1. **接法不该改变插件怎么用。** 第一次讲解用了内部名词和多张表，没讲清楚；换成一个场景（GPU 机器上的一个插件，两种接法，用起来不一样）才讲清。结论：连接方式应与插件的生命周期、配置生效解耦。
2. **宿主要能自建连接**：中继、外部认证、换协议。会话协议不换（所有语言 SDK 的共同约定）。
3. **连接配置不该暴露给写配置的人**：配置只写运行时名和插件。
4. **定为两层**：远程插件层（发现、绑定、生命周期、握手）与连接插件（拨出或监听、认证、重连、传输），中间新增一个"连接登记处"交接接口；link 与接入点重写成内置连接插件；认证放开；中继示例与连接插件契约测试；拆成 4 个 issue。
5. **审阅：过重。** 自审与一次独立审阅结论一致，关键几条在代码里核实：
   - 代码里已经分好了层。link 只产出 `RuntimeSession#<名>`，接入点把每条连接交给外部传进来的 `Accept` 回调，二者都不认识 loader；前面"连接侧在做插件管理的事"的判断说过头了。
   - 差异来自一台与多台两套代码，不是连接方向：一台本来就能 dial 也能 listen。
   - 自建连接现在就能做：实现 `Transport`。唯一缺口是 rutis-host 给接入点写死了 WebSocket。
   - 新交接接口、认证放开、中继示例、契约测试都没有具体使用方。
   - 认证改为可等待不是局部改动：凭据判断在 WebSocket 库的同步回调里，准入在同步的 `recv` 里，要重写监听器路由。
   - 两层设计把吊销留在连接插件、把接纳移到上层，会让被吊销的 id 在行开始装载后才被发现，打破 #210 的保证。
   - 旧配置自动转换没有必要：旧写法本来能用；以前删除写法的先例是报错并给出新写法，没有转换过。
6. **精简**：保持现有分层与两个交接点，只补一致性：`runtimes.remote` 一条写全，`instances` 决定一台还是多台，可选 `transport`，共用发现与检查，缺插件报错一致，多台有输出。

## 三、决定

- 不新增交接接口，不重写 link 与接入点；运行时侧、会话协议、Rust API 不变。
- `runtimes.remote` 的 `dial`、`listen`、`instances` 三个字段独立；rutis-host 在内部生成现有的 link 与运行时接入；旧的 link 行写法照常可用，不转换。
- 可选 `transport`，一台、多台都用；自建连接 = 实现 `Transport`。
- 一台与多台共用发现与检查；缺插件统一为 `Unavailable`；多台的连接有输出。
- 排期 0.19：改动影响远程行为，要在 0.20 形式化覆盖之前完成。实施合为 #696（loader）与 #698（rutis-host）；原 #697 并入 #696，#699 不做。
- 审阅中发现的两个独立问题另开：#701 重连后重新解析所有行（0.17.2），#702 同一监听器上 token 冲突启动报错（0.18）。

## 四、没有采用的做法

| 做法 | 不采用的原因 |
| --- | --- |
| 两层设计：新增"连接登记处"交接接口，link 与接入点重写成连接插件 | 现有两个交接点已经起这个作用；重写能用的代码；吊销与接纳分到两层会打破 #210 |
| 认证放开：自定义凭据、可等待的判断 | 没有使用方；要重写监听器路由 |
| 中继示例、连接插件契约测试 | 没有使用方，也没有连接插件作者 |
| 旧配置启动时自动转换 | 旧写法本来能用；先例是报错并给出新写法 |
| 连接插件写成配置里的一行 | 把连接细节暴露给写配置的人 |
| 每条连接提供一个按连接 id 命名的服务 | id 由对方自报，会占用应用的服务键 |
| 允许替换会话协议 | 所有语言 SDK 的共同约定；对接别的协议在边界上写翻译插件 |
| 多台模式也按 `language` 解析裸名（如 npm 名） | 多台的行一律写 `<运行时>:<插件>`，明确；裸名在多个运行时之间有歧义 |

## 五、教训

- 判断"哪里耦合"之前，先在代码里找已有的交接点。这次第一版把一个外部传入的回调当成了直接调用，由此推出了一整层新设计。
- 每一项新能力先问是否有具体使用方（设计哲学 §七）。"宿主可能想做中继"是假设；现有的 `Transport` 已经覆盖它。
- 设计定稿后请一个没参与讨论的审阅者看一遍，专门问"是否过重"。
