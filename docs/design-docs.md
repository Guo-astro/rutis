# 设计稿约定

[English](design-docs.en.md)

rutis 的设计稿（`docs/design-<主题>-<日期>.md`）怎样写、写到什么程度算完成。依据是[设计原则](design-philosophy.md) §七与 [#690](https://github.com/arcships/rutis/issues/690)：开发者体验没有标准、不挡发布时，投入自然偏向内部正确性，所以每份设计稿都要先写清开发者看到什么。

## 文件与开头

- 文件名 `design-<主题>-<YYYY-MM-DD>.md`，两种语言各一份（`.md` 与 `.en.md`），内容一致；改一份就同步改另一份。
- 开头依次是：标题；另一种语言的链接；`状态：`（草稿 / 定稿，未实现 / 已实现）和日期（同日修订写明改了什么）；`Issue：` 对应的 issue，以及按本稿实施的 issue。

## 必有的节

节的名字与顺序可以按主题调整，但下面几项都要有：

1. **现在怎样 / 要解决什么**：开发者现在遇到的问题，最好引用评估记录（[#663](https://github.com/arcships/rutis/issues/663)）里的原话或输出。
2. **决策**：选了什么、为什么；放弃的做法写一句理由。默认值自己定下，不留"待定"。
3. **规则**：行为，写到实现的人不用再猜。跨语言的规则写明每种语言一样，或者哪里不一样、为什么。
4. **开发者看到什么**（必有，见下节）。
5. **兼容与迁移**：哪些写法、输出、协议变了，旧的一端遇到新的一端怎样；不兼容的改动写进对应版本的迁移指南（两份）。
6. **实施**：拆成哪些 issue，各自的完成条件。

## 「开发者看到什么」

没有这一节，或者只写了一切正常的情形，设计稿不算完成。评审先看这一节。

- **按角色写**，只写受这份设计影响的角色：插件作者、用 `rutis-host` 组装插件的人、宿主持有者（嵌入 rutis 的应用，或以 `rutis-host` 为运行时的产品）、部署的人。
- **正常时**：这个角色要写的代码和配置，以及他看到的输出，用一种语言写全（TypeScript 为例），其他语言只写不同之处。
- **出错时**：这个角色会碰到的每种错误，各写一行：怎样触发，**逐字**的输出（rutis 打印的那一行，以及宿主拿到的错误码），记在哪一行，怎样改。输出里只出现开发者写过的东西（行名、服务名、方法名、文件和行号、怎么改），不出现 rutis 内部的词（见[诊断设计](design-diagnostics-2026-10-26.md) §4.5）。
- **要懂的概念**：这份设计让这个角色多懂哪些概念，对照 #663 写下的各层概念预算；超出预算时写明理由，或者改设计。
- 实现的 PR 用验收测试逐字比较这一节写下的输出；输出改了，先改这一节。

参考：[诊断设计](design-diagnostics-2026-10-26.md) §八、[配置 Schema](design-config-schema-2026-10-27.md) §九、[对象引用](design-object-refs-2026-10-27.md) §八。

## 讨论与定稿

- 从开发者的角度开始讨论，先写他看到什么，再写内部怎样做。
- 一次定稿：评审意见改进同一份稿子，不另开"待讨论"一节。
- 实现时发现设计要改，先改设计稿（写明同日修订或新的日期），再改代码。
